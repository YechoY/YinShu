# 01 · 需求与验收

## 1.1 背景

用户在多个平台听歌，每个平台都有自己的歌单：

| 客户端 | 平台 | 歌单数据 | 同步机制 |
|---|---|---|---|
| 澜音 CeruMusic | Windows / Electron | 本地 SQLite `playlists.db` | v2 插件 SDK + 插件自造 WebDAV 文件 |
| 栖弦 CyShineMusic | Android / Flutter | 本地数据库 | 内置 WebDAV 同步，`cyshine-v1` 单文件 |
| LX Music | Windows / macOS / Android | 本地数据库 | 内置 WebDAV 同步，自有格式 |
| 其它 | — | — | 大多支持自定义 WebDAV 地址 |

现状：**每家的 WebDAV 文件格式不同、合并语义不同**，因此"澜音加的歌"到不了栖弦，"栖弦删的歌"在澜音复活，两端同时增删必然丢一边。用户要的不是"修补点对点同步"，而是**一个能让各平台数据互通的中枢**。

## 1.2 目标（用户原话为准）

> "只要能在几分钟内同步成功就行，要求在任意一端新增删除歌曲或者歌单，另外一方也会分钟级同步，如果各自都有新增或者删除就会自动合并更改"

> "希望是实现各平台的 webdav 歌单数据同步 …… 如果要实现各平台同步，最好就是解耦"

> "一个 url 链接，而且要有账户密码来表示身份"

> "希望任何支持使用 webdav 的客户端 …… 用户只需在要同步歌单的客户端 webdav 填写一个 url 就能实现"

> "要把它做成一个规范，可扩展，可读性高" + "同时要平衡性能哦"

## 1.3 用户故事

| 编号 | 角色 | 故事 | 验收要点 |
|---|---|---|---|
| US1 | 单人 · 多设备 | 我在手机栖弦加了一首歌、在电脑澜音删了一首歌，两边都在几分钟内变成一致 | V1 / V2 / V4 |
| US2 | 单人 · 多客户端 | 电脑上的澜音（插件）和手机上的栖弦格式完全不同，但两边的歌单自动一致 | V3 / V5（**LX 不做**，见 D18） |
| US3 | 新用户 | 我下载了某个支持 WebDAV 的播放器，只在同步设置里填了地址 + 账号密码，没有任何插件，歌单就同步过来了 | V5 |
| US4 | 家人共享（~~**不做**~~ → **已支持 2026-10-06，见 D23**，原"不做"见 §1.5） | 我给家人开一个账号，他/她登进来看到的是自己的空间 | V6 / V11（2026-10-06 起：给他人开账号并指向同一空间即可共用歌单，各自密码独立、可单独吊销） |
| US5 | 出问题时 | 同步出错了，我能看到"上次同步时间、这台设备做了什么、为什么"，而不是猜 | V4 / V8（可解释）/ V9（可撤销） |
| US6 | 家人 · 自助加入（新增，D24） | 我是空间管理员，生成一个邀请码发给家人；家人在登录页"邀请码注册"或登录后"输入邀请码加入"，就能和我共用同一份歌单，不需要我预先替他建号、也不能靠猜空间名闯进来 | V13 / V6 |
| US7 | 家人 · 只读成员（新增，D24） | 我把家里老人的账号加成 viewer（只读），他能在自己手机上看到/播放全家歌单，但任何误删、误改都传不回枢纽，不会动到别人的数据 | V12 |

## 1.4 验收口径

| 编号 | 验收标准 | 验证方式 |
|---|---|---|
| **V1** | **双向增删**：任意一端新增/删除**歌曲**，其它端在分钟级内跟进。**豁免（评审 I8）**：澜音端能**发起**删除（其删除会传播到其它端），但受 SDK 限制**不能接收**删除——其它端发起的删除在澜音侧表现为"待清理清单"。**注**：上游 SDK 正在补"删歌/建歌单"，补齐后此豁免取消（D18/`docs/10`） | 真机：栖弦 ↔ 枢纽 ↔ 澜音插件；澜音侧单独验证待清理清单 |
| **V2** | **双向增删歌单**：任意一端新增/删除**歌单**，其它端跟进 | 真机：同上 |
| **V3** | **自动合并**：两端各自独立增删后，合并不是"二选一"，而是**并集 + 删除生效** | 26 条合并用例 + 真实数据演练 |
| **V4a** | **移动端时延**：从"用户切回前台/打开 App"到对端可见 ≤ **3 分钟（P95，n≥10）**（含客户端 2 s 防抖；前提：客户端 `autoSync` 打开） | 计时实测 |
| **V4b** | **桌面端时延**：按客户端自身同步周期；**手动同步不计入自动验收** | 计时实测 |
| **V5** | **通用接入**：客户端填**一个 URL + 一组账号密码**即可接入，**不装插件、不改客户端代码**。**已适配方言**可双向同步；**未适配方言**可正常读写但与其它端不合并（隔离，补适配器后经用户确认并入）——统一表述，避免"任意客户端都能互相同步"的过度承诺（评审 I3） | 至少 2 个不同格式客户端双向一致 + 第三个未适配方言不污染其它端 |
| **V6** | **多用户隔离**：不同账号互不可见；同一账号下多设备/多客户端各自成立 | 两个账号交叉验证 |
| **V7** | **不丢数据**（最高优先级）：任何异常（断网、半包、并发写、格式未知、服务重启）都不导致歌单条目丢失。**边界**：指不因技术故障丢失；用户可见删除的可恢复窗口 = 墓碑（**GC 看确认水位，不设时间 TTL**，D21）+ 备份保留策略（评审 N4） | 故障注入 + 备份回滚演练 |
| **V8** | **可解释**（新增，评审 UX）：非技术用户能在状态页 30 秒内说清"上次同步做了什么、有没有要我决定的事" | 状态页走查 + 5 人可用性测试 |
| **V9** | **可撤销**（新增，评审 UX）：误删后非技术用户能在 3 次点击内恢复（状态页确认/回滚入口） | 走查 + 演练 |
| **V10** | **删除不复活**（新增，D20/D21）：**换设备/重装/清数据**后，已墓碑化的条目不因新设备提交而复活，而是在状态页出"待确认恢复"卡；用户点"恢复"才加回。**判据是提交者身份可信度，不是时间**（D21）；**同身份设备**本来就不会复活 | 用例 26 + 真机换设备/重装演练 |
| **V11** | **多账户共用歌单**（新增，2026-10-06 反转 D19，见 D23）：给他人开账号并指向同一空间 → 歌单互通（真合并、双向、删除自动生效）；各账号主题/音源/本地音乐互不覆盖（opaque 按客户端分桶）；待确认卡只能由本人或管理员确认 | A22–A25（`docs/07`）+ 真机双账号演练 |
| **V12** | **空间角色矩阵**（新增，D24）：owner / editor / viewer 三级权限与 docs/12 §4 矩阵一致——viewer 同步 GET 200 但同步 PUT、网页改删歌单/曲目、确认卡、成员管理全部 403；editor 可写但只能确认自己的卡；owner 全权本空间；全局 admin 对任何空间视同 owner。viewer 首次接入无需 PUT 即可拉取（引擎 `peek_view` 只读路径） | `test_spaces_http` 用例 5/8/11/12 + 角色矩阵走查 |
| **V13** | **邀请码四种失败路径 + 自助注册**（新增，D24）：有效码可加入/注册并获得码上角色；**不存在 / 已撤销 / 已过期 / 已用完**四种失效各自返回可区分文案与 400；重名注册 409；关闭 `allow_self_register` 后注册 403；普通账号建空间受配额（默认 3）限制、admin 不限；唯一 owner 不能退出/被降级 | `test_spaces_http` 用例 3/4/7/9/10/11/13 |

## 1.5 明确不做（本阶段边界）

| 不做 | 原因 / 何时再考虑 |
|---|---|
| 播放顺序、封面、播放源配置的精确同步 | 各客户端语义不同；用户验收只要求增删歌曲/歌单。**顺序变化不触发合并**（评审 I7：渲染按枢纽稳定顺序输出） |
| 秒级实时 | 需要常连推送；D1 已定"打开即同步"，分钟级足够 |
| ~~换设备/清数据后已删歌曲不复活~~ | **已移出"不做"**：D20 墓碑压制（用户 2026-10-05 选定"不要自己回来"）由枢纽侧实现，**无需改客户端** ⇒ 现为验收项 **V10**（唯一代价：换设备带来的旧副本里若含已删条目，需点一次确认；同身份设备不受影响，D21） |
| 私有协议客户端的接入 | 非 WebDAV 无法在不改客户端的前提下接入 |
| 修改客户端代码（第一阶段） | D3；后续如确有必要再单独立项（例外：**诊断按钮**属于可选改动，非同步逻辑） |
| ~~**共享空间与歌单级共享**~~ | 用户曾提"想分享歌单给别人"，随后定：**不做共享歌单，每人一个账号，简单些**（2026-10-05）。共享空间另有归因无解问题（评审 S4/M5）。**已于 2026-10-06 反转**：多账户共用空间歌单已支持（见 D23，`docs/09`）——现在做的是"同一空间多账号共用同一份歌单"，不是歌单级 ACL/权限 |
| **多平台换源引用**（同一首歌挂多平台 `platforms`） | 本阶段只保证"身份正确的同一首歌不被拆开"；换源播放是另一个功能（评审 I10） |
| **`appearance` / `musicSources` 的跨端语义** | 本阶段整段 LWW 透传，不参与合并（评审 I10） |
| **文档分片（每歌单一个文件 + index）** | 当单客户端文档稳定 > 800 KB 时启动（评审 I10 / Q8） |
| **只读凭据 / 独立同步密码** | 见 §1.6 与 `06` §6.2；"独立同步密码"建议随 M3 一起做（评审 M2） |

## 1.6 硬约束（方案必须绕开的事实）

| 约束 | 影响 |
|---|---|
| 客户端逻辑改不动（第一优先级） | 合并必须在服务端完成；服务端必须容忍客户端"整节替换 / LWW / 拿旧视图回写" |
| AList 忽略 `If-Match` | 服务端不能依赖条件写防并发，必须用"读-改-写 + 基线 + 抖动重试" |
| 历史上 AList 曾把 ~108 KB 的 PUT 写截断 | 单文档必须保持小（规范要求 < 1 MiB，实测控制更严），并做写后自校验 |
| 客户端文件里只有"最终状态" | 必须有服务端基线，否则删除与"未同步"不可区分 |
| HTTP Basic 明文回放 | 必须 HTTPS（现有 Cloudflare 隧道满足） |
| 澜音插件 SDK 无删歌/建歌单 API | 澜音端的"执行删除"是平台缺口，只能标记待清理（不影响枢纽侧一致性） |
| 栖弦无同步定时器 | 手机端"分钟级"实际是"打开即同步"（D1） |
| `ctx.storage ≤ 10 MiB`（澜音插件） | 插件只能做轻量客户端，状态存服务端 |
