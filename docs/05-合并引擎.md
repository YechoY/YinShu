# 05 · 合并引擎（本项目唯一会丢数据的地方）

> 全部风险集中在这一节。设计原则：**宁可少同步，不可错删除。**

## 5.1 概念

| 概念 | 定义 |
|---|---|
| 空间 `canonical` | 枢纽当前认定的"真相"：歌单集合 + 每歌单的曲目集合 + 墓碑 |
| 客户端交付基线 `base_served` | **枢纽上一次真正交付给该客户端的视图 + `served_revision`**（每个客户端一份）——删除判据的"交付过"半边（评审 S1 修正 + **R1 多设备修正**，见下） |
| 客户端提交基线 `base_submitted` | 该客户端上一次提交的视图（拥有水位）；**R1：与 `base_served` 的交集才是这台设备"真的拥有过"的条目，删除只对它成立** |
| 客户端视图 `C_new` | 本次请求里客户端提交的视图（它以为的世界） |
| 墓碑 `tombstone` | 显式删除标记：`{kind, key, deletedAt, origin}` |
| 版本 `revision` | 空间单调递增序号；每次成功合并 +1 |

**为什么必须有 base**：客户端文件里只有 `C_new`。只有枢纽知道"它上次看到了什么"，才可能区分：

- `base_served` 有、`C_new` 没有 ⇒ **这个客户端删除了**（删除生效）
- `base_served` 没有、`C_new` 有 ⇒ **这个客户端新增了**（并集）
- 别处存在、`C_new` 没有、`base_served` 也没有 ⇒ **它还没同步到**（**什么都不做**）← 这一条就是丢数据的根源

> **关键修正（评审 S1）**：删除只能相对"枢纽确实交付过的视图"判定，**绝不能相对"它上次提交的视图"判定**。枢纽每轮都会把合并结果（含别端新增）交付给客户端，客户端回写时会原样带回这些别端新增；若用 `base_submitted` 求差集，这些条目既会被误判成"客户端新增"（反复并入、`revision` 无限增长），也可能在客户端先回写时被误判成"客户端删除"。这是本设计唯一会静默丢数据的结构性错误。

> **多设备修正（2026-10-06，R1，多设备同步改造方案 §3.2）**：S1 还不够——对栖弦这类**先 GET 再按 section 级 LWW 决定写不写回**的"整段覆盖"客户端，**"交付过"≠"采纳了"**：A 机 GET 后可能保留自己的旧段回写，把 **B 机刚加的内容**（已在交付视图里、但 A 从未提交过）判成"A 的删除"（M1 时间线，两台手机都丢）。修复：删除判据 = `base_served ∩ base_submitted`（这台设备**自己提交过**的条目）。**第十一轮（D30）对手续为"整份替换"的方言（洛雪）放松为 `owned = base_served`，见 §5.3.2。** 这条把旧注释"base_submitted 仅审计"反转，改动时三处注释（engine.py 模块 docstring / Client.base_submitted / merge 结尾 I1）与本文必须同步。

> **P0.5（2026-10-06，R1 配套，deepseek 验收关键发现①）**：R1 保护掉的缺席（`base_served` 有、`base_submitted` 无、本次提交缺）**既不删除也不记录** ⇒ "手机上删掉从电脑同步过来、自己还没重新上传过的歌单"永久静默无效（云端和澜音侧还在、手机侧没了、无人提示、不自愈）。修复：此类缺席记 `never_owned` 并出**待确认删除卡**（`reason=never_owned`，复用 §5.3.5 确认通道 + PendingCard.vue），默认不删、确认后才写墓碑（墓碑可压制另一端推回，S10/S11 语义保留）；**I2′ 并发轮次只并入 suspects 不出卡**（防噪音）。详见《多设备同步改造方案.md》§7 P0.5 实施记录。

## 5.2 不变量

| # | 不变量 | 违反后果 |
|---|---|---|
| I1 | 基线只在**真正送达后**推进：`base_served` **只在 GET 成功交付（200）后**推进，`base_submitted` 只在提交成功后推进。PUT 的响应体**不算交付**（栖弦拿到响应即丢弃，评审 F3） | 客户端没收到却推进基线 ⇒ 下次把别端新增/本地新增误判成删除（静默丢数据） |
| I2 | "消失"必须有墓碑才能判删；无法判定时**保留** | 误删 |
| **I2′** | **凡是"该客户端从未被交付过"的元素，它的缺席一律不构成删除**；且当 `space.revision ≠ base_served.served_revision`（期间有别的客户端写过）时，**本次提交禁止产生删除**，只取并集并把删除候选写入 `journal` 待确认 | 拿旧视图回写时误删别端新增（评审 S1） |
| I3 | 同一元素"一加一删"同轮出现 ⇒ **删除优先**（D7） | 删除反复复活 |
| I4 | 合并是纯函数：同 `(canonical, base_served, base_submitted, C_new)` 必得同结果（幂等） | 重试导致漂移 |
| I5 | 任何单次操作删除量超过阈值 ⇒ **挂起该批删除、其余照常应用**（不整批拒绝） | 客户端 bug 或误操作血洗歌单；同时避免"整批 409 ⇒ 客户端永久卡死"（评审 S2/UX S1） |
| **I6** | 适配器无法表达的元素（本地文件曲目、无平台 id 的兜底曲目、未知扩展）**必须原样携带**（`ext.<client>.opaque`），**不参与**合并判定与去重、**不参与跨设备交付**：按 `client_key` 分桶存储与渲染（2026-10-06，D23） | 栖弦 `applyFromSync`"缺席即删除"⇒ 用户本地音乐被间接删掉（评审 S2） |
| **I7** | **墓碑压制（不以时间为判据）**：只有**身份不可信**的提交者（无基线 / 未验证 / 已判退休）碰到**仍存活**的墓碑 key 时才**不得复活**，改为生成"待确认恢复"卡；**已越过删除点的已知身份**重新添加同一 key = 显式恢复，直接生效并清墓碑。墓碑存活期由**确认水位**决定（删除发生时已注册的客户端都已在成功交付中见过它 ⇒ 可 GC）；**例外：无删除能力的提交者（`can_delete=false`，澜音插件）"收到视图"不算确认**，必须等它的**提交内容里不再携带该条目**（否则它下一次 GET 就把墓碑 GC 掉，重加时失去压制 ⇒ 删除被推回，复检 S11/S15）；**时间只用于判定身份是否退休（>180 天无活动）**，不能用"满 N 天即可复活" | 换手机/重装/清数据后，用户已删的歌自己冒回来（D20，用户 2026-10-05 选择"不要自己回来"）；同时避免"2 年后必然复活"这个假窗口（评审 F1/C） |

## 5.3 算法

```text
merge(space, client, payload):
    C_new = dialect[client].parse(payload)          # 结构坏 → 抛错，不猜
    bsub  = base_submitted[client]                  # 可能为 None（首次）
    bsrv  = base_served[client]                     # 可能为 None（从未交付过）

    if bsub is None:                                # 首次接入（D8）
        return adopt_initial(space, client, C_new)  # 只增不删

    # 差分一律相对 base_served（I2′），绝不相对 base_submitted
    added_pl   = keys(C_new.playlists) - keys(bsrv.playlists)
    removed_pl = keys(bsrv.playlists) - keys(C_new.playlists)
    for pl in keys(bsrv.playlists) ∪ keys(C_new.playlists):
        added_t[pl]   = keys(C_new[pl].tracks) - keys(bsrv[pl].tracks)
        removed_t[pl] = keys(bsrv[pl].tracks) - keys(C_new[pl].tracks)

    delta = {added: …, removed: …}
    if space.revision != bsrv.served_revision:       # 期间别端写过：禁止删除
        delta.suspect_removals = delta.removed
        delta.removed = {}                           # 只并集（I2′）
    if deletion_ratio(delta.removed) > SAFETY_LIMIT: # 阈值以 §5.3.5 为权威（I5）
        deferred = delta.removed                     # 挂起，不整批拒绝
        delta.removed = {}

    trusted = client.identity_verified              # 有基线且身份未判退休（I7 的判据）
    with transaction(space):                        # 单写者串行
        # I7：只有"身份不可信"的提交才被墓碑拦下；已知身份重加 = 显式恢复
        suppressed = {k for k in delta.added if not trusted and live_tombstone(k)}
        restore_candidates = suppressed
        apply_additions(space, delta.added - suppressed)      # 并集；`(source,songId)` 去重
        clear_tombstones(keys(delta.added) - suppressed)      # 显式恢复 ⇒ 解除墓碑
        apply_removals(space, delta.removed)         # 写墓碑；删除优先（I3）
        gc_tombstones(ack_watermark)                 # T3：删除时已注册的客户端都已见过 ⇒ 可 GC
                                                     # 例外：can_delete=false 的端点（澜音）确认只能来自
                                                     # "提交内容里不再携带该条目"（复检 S11/S15）
        if canonical_mutated: space.revision += 1    # 只在真变化时推进（评审 E1）
        base_submitted[client] = C_new               # I1：仅提交成功后
        journal.append(delta, deferred, suspects, restore_candidates)  # 审计/回滚/待确认
    rendered, served_rev = render_for(client, space)
    return 200 rendered                              # 不因挂起而整批拒绝
    # 注意：base_served 不在此处推进 —— PUT 的响应体不算交付（I1 / 评审 F3）
```

### 5.3.1 首次接入（`adopt_initial`）

- 该客户端的所有内容作为**新增**并入；**不产生任何删除**；因首次接入者身份不可信，仍受 **I7 墓碑压制**：命中存活墓碑的条目**不加回**，转为"待确认恢复"卡（判据是身份可信度，不是时长）；
- 同名/同身份歌单按 **id → 名字别名 → 新建** 顺序匹配，避免因为改名复制出歌单；
- 建立基线为该客户端当前视图；
- 若空间已有数据，则返回的渲染结果已包含"空间的其它内容"，客户端下一轮即可看到。
- **新增的曲目置顶**（与 `merge()` 同规则；2026-10-08 补，真机报告）：新并入的曲目按提交顺序放到歌单最前，已有曲目相对顺序不变。漏掉这条会让"换机/新设备首次接入时新加的第一批歌"全部沉到歌单末尾（详见 `docs/notes/第八轮修复记录.md` 事故三）。
  - 第十轮（2026-10-08，用户 m04142「无论什么平台，新增的歌曲都要在最顶部」）：置顶**与方言无关**，三方言（`cyshine-v1`/`ceru-plugin`/`lx-x`）与两条路径（`merge()` 常规 / `_adopt_initial()` 首次接入）一视同仁，回归 `tests/engine/test_multidevice.py::test_new_tracks_go_to_head_from_every_dialect`；同用例固定了配套边界——**集合不全的提交（该设备还看不到别人新加的歌）不得整体重排**，只有"交付过完整集合后"的纯重排才整体采用提交顺序。

### 5.3.2 删除优先（I3）

```text
keep(key) = (本地有 && 远端有) || (!base 有 && (本地有 || 远端有))
```
删除优先意味着：`base` 有、任一侧没有 ⇒ 删除。防止"一端删除后另一端又把它写回来"造成无限复活。

> **第九轮（2026-10-08，D28，真机事故）——"整份歌单消失"只删歌单，不派生曲目删除**：
> 客户端不再提交某张歌单时（R1 成立：`owned_pl = base_served ∩ base_submitted` 里有它、本次 `cur_keys` 没有；
> **第十三轮 D32 起，可信客户端的歌单级判据为 `owned_pl = base_served`**），
> 只走 `_delete_playlist`（歌单墓碑 + 从 `playlist_order` 摘除），**不再把该歌单的全部 owned 曲目算成删除**
> （原 `removed_t[pl] = owned_t[pl] - cur`，`cur=∅` ⇒ 全量）。原因：曲目墓碑是**曲目池级**的
> （`Track.deleted_at`，`_remove_track_global`），而派生/合并歌单里的曲目往往同时躺在来源歌单里
> ——真机现场「合并歌单」235 首与「Yes」253 首重复 232 首，旧规则一次性把 232 首从 Yes 里抹掉
> （Yes 253 → 21）。网页端删歌单（`delete_playlist`）本来就只删歌单不墓碑曲目，这里与之对齐；
> 只属于该歌单的曲目会变成"无歌单引用的活曲目"（不渲染、不删），用户重新建同名歌单即可拿回。
> 详见 `docs/notes/第九轮修复记录.md`。

> **第十一轮（2026-10-08，D30，用户真机）——对"整份替换"客户端放松 R1（洛雪拉取后删歌必须能同步上去）**：
> 洛雪（`lx-x`）拉到远端后是 `overwriteListFull` **整份覆盖**（`src/core/sync/webdavSync.ts:438-489`），
> 之后的 PUT 内容 = 远端视图 + 本地操作重放 ⇒ 它"我们交付过、这次提交缺席"的条目就是用户在洛雪里删掉了。
> 但旧口径要求 `owned = base_served ∩ base_submitted`，而洛雪**纯拉取时不上报**（`uploadLists` 只在
> `hasLocalChanges` 时调）⇒ 这首歌它从未提交过，缺席被归入 `never_owned`、永不判删，用户在洛雪里怎么删
> 都同步不上去。现按方言能力 `capabilities.full_view_submit` 放松：为真时 `owned = base_served` 即可
> （歌单级同样成立：缺席的歌单就是删掉的歌单）。三道约束不变：
> ① 只对该方言能**原样往返回来的音源**生效（`capabilities.round_trip_sources`，洛雪 = `wy/tx/kw/kg/mg`；
> 解析会把白名单外的曲目丢进 `opaque["tracks"]`，那些缺席不能当删除）、
> ② **I2′ 并发闸门**（交付之后别端写过 ⇒ 只记 `suspects`、不判删）、③ 安全阀照旧。
> **栖弦 `full_view_submit=False`**：它是 section 级 LWW，可能保留自己的旧段（M1），放松会误删别人加的歌；
> **澜音插件 `False`**：本地删不掉，缺席可能只是导入失败。详见 `docs/notes/第十一轮修复记录.md`。
>
> **第十三轮补（2026-10-08，D32，用户真机）——歌单级再放松一档给"可信客户端"**：
> 用户报告「lx-x 加入了一个歌单，然后用栖弦删除后却没有同步上去」。真因是**歌单级** R1：栖弦的歌单**新增**
> 永远进不了 `base_submitted`——远端胜过它的那轮 `applyFromSync` 整份替换本地歌单
> （`playlist_store.dart:227-280`），而那一轮 `_syncOnce` 见 `merged == remote.snapshot` 直接 `return`、
> **根本不上传**（`webdav_sync_controller.dart:286`）⇒ 交付过、却永远"没提交过"，缺席落进 `never_owned`、
> 永不判删。而栖弦的 `sections.playlists` 恰恰是**整份**导出（`exportForSync` 遍历本地全部歌单、无过滤，
> `playlist_store.dart:214-225`）。故歌单级改为：**可信客户端**（`identity_verified ∧ can_delete ∧ ¬retired`，
> 与安全阀 `trusted` 同判据）`owned_pl = base_served`，缺席即删（写歌单墓碑；按 D28 不派生曲目墓碑）。
> **曲目级 `owned_t` 一字未动**（真机数据损失都发生在曲目层）；I2′、安全阀、墓碑 + 冷静期显式恢复三道约束不变；
> 从未交付过的条目（不在 `base_served`）仍不算删除。澜音 `can_delete=False` 天然排除。
> 代价：栖弦若真的"保留自己的旧段"（M1），它整份提交缺的歌单现在会被删——用户拍板"删歌单必须同步得上去"，
> 且删歌单不丢曲目、误删可由别端重新提交在冷静期后恢复。详见 `docs/notes/第十三轮修复记录.md`。

### 5.3.3 时钟

- **服务端时钟是唯一权威**；客户端提交的时间戳只作展示与启发式参考；
- 渲染给客户端时，section 级 `modifiedAt` 取**随空间 `revision` 单调推进的确定性值**（`f(served_revision)`），**且仅当"相对该客户端上次交付的渲染内容确有变化"时才推进**；内容不变时输出**完全相同**的时间戳与字节（评审 S3 修正）。理由：填 `now` 会让每次 GET 都被客户端判成"远端更新"，触发整表替换 + 必然回写（写放大），并让"本地已新增但先 GET"的未同步新增被远端覆盖；
- **第十二轮补（2026-10-08，D31，真机事故）**：上一条的"内容不变"必须是**双条件**——① 相对该客户端上次**交付**的内容未变 **且** ② 该客户端**手上那份**（它上次提交声明的视图）与我们本次要交付的一致。只看 ① 会漏掉这一路：客户端本地加过一条并 PUT 上来（PUT 不更新交付基线），别端把它删了，此时交付视图恰好**退回**它上次拿到的那份 ⇒ 短路返回**旧戳**，而栖弦按 section 级 LWW「远端时间更大才采纳」判定远端没更新 ⇒ 它永远不应用这次删除、本地副本一直在、每轮回推（详见 `docs/notes/第十二轮修复记录.md`）。实现：`_submission_matches()`；只比对客户端**声明过**的歌单（它没提交过的歌单不影响判据，避免写放大）。
- **不使用 `304`**：栖弦只接受 2xx（`webdav_client.dart:69/91`），304 会被它当成"WebDAV 请求失败（HTTP 304）"。内容未变时返回 `200` + 相同正文 + 相同 `ETag`（流量靠 gzip，不靠 304）；
- 歌单级 `createdAt` = canonical 首次入库时间（稳定）；歌单级 `updatedAt` = canonical 的更新时间（**不填渲染时间**）；
- 客户端时钟明显错乱（偏差 > 24 h）时记警告，不影响合并；
- **弃用决策（评审 S3）**：`modifiedAt = now` 原设计已废弃，见 `docs/10-评审记录与整改.md`。

### 5.3.4 字段冲突（用户验收只要求增删，故按简单规则）

| 冲突 | 策略 |
|---|---|
| 歌单名 | 最后写入者胜（服务端记录 `updated_at`） |
| 封面/描述 | 同上；空值不覆盖非空值 |
| 曲目可播放信息（品质等） | 取"更优品质"（用规范排序比较），不可用时保留可用版本 |
| 未知扩展字段 | **双方都保留**，按命名空间合并；冲突时保留服务端现值 |
| 删除 vs 修改 | 删除优先 |

> **第十轮（2026-10-08，D29，真机事故）——"曲目可播放信息"对洛雪必须双份齐备**：
> 洛雪客户端**无守卫**读 `meta._qualitys`（`src/core/music/utils.ts:246-271 getPlayQuality()`，`online.ts:86` 在任何 try 之前就调用）
> ⇒ 交付条目缺 `_qualitys` 时，在列表里点歌会在"解析音质"一步抛异常（URL 根本不请求），表现为"点了没反应、进播放页才能播"。
> 因此 `lx` 方言渲染必须**同时**给出 `qualitys`（数组，带 `size` 人类可读字符串）与 `_qualitys`（档位→`{size}` 映射）：
> 优先原样回写用户自己洛雪数据的九个原生 meta 键（`_LX_META_KEYS`），缺料时用"历史最高档 + `128k` 下限"兜底。
> 详见 `docs/notes/第十轮修复记录.md`。

### 5.3.5 安全阀

> **第八轮（2026-10-08，D27）起默认行为已变**：`policy.confirm_delete=False`（默认）下安全阀**不再产生"待确认删除"卡**。三分支：① 可信端（`identity_verified ∧ can_delete ∧ !retired` 且 `trusted_direct_delete`）→ 直删生效，`meta.safety_valve.applied` 留痕；② 不可信端点 → **既不生效也不出卡**（它可能只是"没拿到这批曲目"），`meta.safety_valve.withheld` 留痕；③ 把 `confirm_delete` 设为 `True` 才回到下表"挂起 + 确认卡"的旧通道。下表与 §5.3.5 正文描述的是 ③ 打开时的语义。

| 触发 | 阈值（可配、对用户可见） | 行为 |
|---|---|---|
| 单次删除歌单数 | ≥ 3 或 ≥ 空间的 50% | **不可信端**：挂起（新增照常应用；该批删除本轮**不生效、也不写墓碑**；渲染**仍含这些条目**；响应 `200`；差异摘要只进状态页与日志）。**可信端**（`identity_verified ∧ can_delete ∧ !retired`，空间策略 `trusted_direct_delete=True` 默认）：**直删生效、不挂起**（D25 P1-2） |
| 单次删除曲目比例（单歌单） | ≥ 50% 且 ≥ 10 首 | 同上 |
| 单次提交替换全部客户端身份 | 全部 `client_key` 变化 | 记警告 + 保留旧基线 30 天（防"清数据后血洗"）+ 状态页确认卡 |
| 文档超限 | > 单客户端上限 | `413`，不落库；**绝不裁剪曲目**（裁剪对客户端等于静默丢歌） |

**确认通道（必须有落点，评审 S2）**：待确认删除进入状态页"需要我决定的事"卡片，可用按钮确认/放弃；同时提供 CLI `hub confirm-delete --space X --pending <id>`。**队列必须持久化且可重放（评审 A2）**：用户点"确认"时由枢纽写墓碑并推进 `revision`（各端下次 GET 学习）；未确认则**永不自动生效**，且**不能因为客户端后续 PUT 里不再带这次删除就把卡片丢掉**（栖弦会在拿到渲染后把条目重新加回本地，删除信号从此消失）；状态页每 24 h 提醒一次，**30 天未处理自动按"保留"结案并清卡**（删除放弃，条目保留）。差异摘要**只写日志与状态页，不放进响应体**（栖弦对非预期结构会抛 `PlaylistStoreException`，`playlist_store.dart:228/234`）。

## 5.4 收敛性

| 场景 | 收敛轮数 | 依据 |
|---|---|---|
| 单端增删（该端写成功） | 1 轮（该端写 → 其它端下次读） | 其它端 GET 拿到渲染结果 |
| 两端各自增删 | 1–2 轮 | 第二次读即使客户端自身 LWW 判"本地更新"，其本地内容也已是合并结果 |
| 客户端拿旧视图回写 | ≤ 2 轮，**不丢数据** | I2′：`base_served` 之外的缺席不构成删除 |
| **客户端只 GET 不 PUT**（栖弦 `_sameSnapshotData` 相等时不写，`webdav_sync_controller.dart:286`） | 对"获取"1 轮即可；对"它自己的删除"则**永不传播** | 删除只能在它 PUT 时学习 ⇒ 已在 §5.6 记为已知限制：**读取路径可推进 `base_served`，但不能代替提交**；缓解=切前台/手动同步会带上本地删除 |
| 服务重启/事务失败 | 0 额外轮 | 基线未推进，重放同一请求结果相同（I4） |
| **换机 / 重装 / 清数据（新身份）** | 1 轮 | 墓碑压制（I7）：已墓碑化的条目不复活，转"待确认恢复"卡；未墓碑化的本地残留按只增并入（D8/D20，用例 26）。**判据是"提交者身份不可信"，不是时间**（D21） |
| 三客户端交错 GET/PUT | ≤ 2 轮 | 用例 20 专门覆盖 |

> 客户端侧三态（写前是否读过 / 写成功·失败·被挂起 / 本地胜·远端胜）的完整状态机在 M1 PoC 中用用例 20–22 固化，不在此处展开（评审 I1）。

## 5.5 边界用例（M1 PoC 必测）

| # | 用例 | 期望 |
|---|---|---|
| 1 | 单端加歌 | 对端可见 |
| 2 | 单端删歌 | 对端消失，且不复活 |
| 3 | 两端各加不同歌 | 并集，两首都在 |
| 4 | 一端加、一端删同一首 | 删除优先，最终不存在 |
| 5 | 两端各删不同歌 | 两首都不存在 |
| 6 | 新增歌单 | 对端出现 |
| 7 | 删除歌单 | 对端消失，且不复活 |
| 8 | 首轮接入（空间已有数据） | 只增不删，对端数据不丢 |
| 9 | 客户端清数据重装 | 只增不删；已删的风控提示但不血洗 |
| 10 | 歌单改名 | 不复制歌单（靠 id/别名） |
| 11 | 同名歌单来自两个平台 | 按 id/别名合并，不产生重复 |
| 12 | 跨源同 songId（`wy:123` vs `kw:123`） | 视为两首，不撞车 |
| 13 | 坏 JSON / 截断文件 | 拒绝并回滚，基线不动 |
| 14 | 删除比例 80% | 触发安全阀：**新增照常应用**，该批删除**挂起且不写墓碑**，渲染仍含这些条目（D4），响应 200 且数据无损；状态页出"待确认删除"卡；**用户确认后才真正删除**，30 天未处理自动按"保留"结案（评审 S2/A2 修正原"整批 409"） |
| 15 | 未知方言 | 隔离保存，其它客户端不受影响 |
| 16 | 重复提交同一请求 | 幂等，无额外变化 |
| 17 | 两端同时写 | 串行化，结果一致 |
| 18 | **含本地文件曲目（`file:` / 无 songId 兜底）的歌单 round-trip** | 该曲目**原样带回**，不被删除也不参与合并（I6；评审 S2） |
| 19 | 设备身份（由 URL 路径段确定，D10 修订/评审 B/F5） | ① **同一路径、同一台设备**（含重装后仍填同一地址）⇒ 身份稳定，两侧互不丢数据；② **同地址后面有两台设备 / 重装后恢复了旧数据** ⇒ 大比例删除被安全阀挂起并要求确认、`revision` 闸门拒绝并发生删除；**小比例纯删除可能被自动执行**（已承认残差，D10），状态页给出"同一地址可能被多台设备使用"的提示 |
| 20 | **三客户端交错 GET/PUT**（A 写 X → B 写 Y（未 GET）→ C 首接 → A GET 后回写 → B GET 后回写） | 无删除、无重复并入、`revision` 不无限增长（评审 S1 的反例场景） |
| 21 | **客户端只 GET 不 PUT** | 枢纽不产生删除；`base_served` 正常推进；该端本地删除**不被误判**（已知限制按 §5.6 记录） |
| 22 | **客户端清数据重装后回写空视图** | 不血洗：走 I2′ 的"禁止删除"路径或安全阀挂起，并在状态页出确认卡 |
| 23 | **离线 90 天后回归** | 以 `base_served` + 墓碑水位判定，不复活、不误删（评审 I2） |
| 24 | **未适配方言客户端写入** | 隔离保存，**不污染**任何其它客户端的渲染结果（评审 I3） |
| 25 | **首次接入时两端同时 PUT**（`If-None-Match: *` 语义） | 后到者收到 `412`/明确失败，不静默覆盖（移动端评审 P2） |
| 26 | **新身份设备提交含"已墓碑条目"的视图**（换手机/重装/清数据） | **不复活**：该条目被压制，其余本地残留只增并入；状态页出现"待确认恢复"卡；用户确认"恢复"后才加回（I7/D20）。**判据是身份不可信，与离线时长无关**（D21） |

## 5.6 错误与回滚

| 失败 | 处理 |
|---|---|
| 解析失败/结构损坏 | `400`，落库前拒绝；**基线不动**；记录样例供排查 |
| 合并中崩溃 | SQLite 事务回滚；重放请求结果相同（I4） |
| 渲染失败（客户端硬要求不满足） | 记错误并向该端返回 `500` + 可读原因（正文不含自定义结构）；**其它端不受影响** |
| 安全阀触发 | 挂起删除 + `200` 正常交付（§5.3.5）；差异摘要进状态页与日志，**不进响应体** |
| 需要回退 | 状态页/CLI：用 `journal` 重放到指定 `revision`；或导出 canonical JSON 后人工编辑再导入 |
| **已知限制**：客户端"相等则不写回" | 该端**自己的删除**在"下一步不写"时不会传播（它写回才会学习）；缓解=切前台/手动同步会带上本地删除；M0.5 真机取证后决定是否需要在 GET 路径上补"墓碑确认" |
| **已知限制**：同地址被多台设备/重装复用 | 用户只填一个 URL（D10），枢纽无法区分同一地址后面的设备 ⇒ **小比例纯删除可能被当成用户的删除直接执行**（大比例被安全阀挂起）。缓解：`revision` 闸门 + 正向归因 + 状态页提示（**可选**：给第二台设备一个带设备段的地址） |

## 5.7 性能

| 项 | 设计 |
|---|---|
| 复杂度 | 并集/差集均 `O(n+m)`；曲目池按 `(source,songId)` 哈希索引 |
| 存储 | 只存增量（`journal`）；canonical 物化在 `playlists/tracks` 表 |
| 渲染缓存 | 按 `(client, canonical_revision, content_hash, dialect_version)` 缓存渲染结果与 ETag（**加入内容哈希**，否则"缓存命中"与"时间戳推进"互相矛盾，评审 S3） |
| 大文档 | **绝不裁剪曲目**（裁剪=对客户端静默丢歌，违反 V7）。超上限时：先按目标 ≤100 KB 瘦身（曲目池去重、字段自净、`ext` 限额）→ 仍超则拒绝该次写入并返回可读错误 + 状态页提示导出；分片（每歌单一个文件）作为 M2 真机量出上限后再定的策略（评审 I4/I6、移动端 S13） |
| 容量估算 | 单客户端 `base_served` **只持久化"元素键清单 + 内容哈希"**（足以做差分），完整视图按 `canonical_revision` 共享物化、按需重建；否则 ≤20 客户端 × 整份视图会撑爆 32 MiB 空间配额（评审 I4） |
