# 02 · 现状调研（客户端、服务端与根因）

## 2.1 结论先行

1. **点对点同步的天花板**：WebDAV 单文件里只有"最终状态"，任何一端都无法区分"对端删了这首歌"与"对端还没同步这首歌"。没有第三方记账，就必然在"误删"和"复活"之间二选一。
2. **客户端各自的合并语义是丢数据的直接原因**：栖弦按 section 比较 `modifiedAt` 后**整段采用胜者**，并把结果**先落盘再写回**；两端各自增删时，落败一侧的新增被整体覆盖。
3. **服务端翻译 + 合并是唯一解**，且客户端不需要改代码。
4. AList 能提供**账号、权限、存储、HTTPS**，但**不提供合并**（PUT 即覆盖）；所以它是"底座"，不是方案本身。

## 2.3 根因分析

```text
【现状：点对点单文件】
栖弦本地 ──┐                        ┌── 澜音本地
           ├─ 同一个 sync 文件 ─────┤
           ┘  只有"最终状态"        ┘
问题1 无法区分"对端删了" / "对端还没同步"   → 删除必然误判（丢歌）
问题2 双方各自增删时，按 modifiedAt 整段采用胜者 → 落败方新增被覆盖（丢歌）
问题3 匿名文件里没有"谁写的、上次看到什么"   → 无法做三路合并
问题4 各家格式互不相同                  → 跨平台互通不可行
问题5 单文件随歌单增长，写截断风险上升     → 静默损坏
```

**解法方向**：文件里没有的信息，放到服务端去记——服务端知道"每个客户端上一次看到/写的是什么"（基线），于是"少了什么"可以判定为**这个客户端删了**，而"对端还没有的东西"不再被误判为删除。这就是三路合并（three-way merge）。
