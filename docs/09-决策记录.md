# 09 · 决策记录（ADR）

格式：`编号 · 决策 · 背景 · 理由 · 代价 · 状态`。状态取值：`已定` / `待定` / `已废弃`。

---

### D1 · 手机端"分钟级" = 打开 App / 切回前台即同步
- **背景**：栖弦全库无同步定时器（只有启动、切前台、本地变更 2 s 防抖、手动）。
- **理由**：用户确认接受；避免后台常驻耗电与被系统杀掉。
- **代价**：手机不在前台时不会主动拉取；"分钟级"实际是"你打开时同步"。
- **状态**：已定。

### D2 · 与 AList 并存，不替换
- **背景**：AList 已在本机运行并服务其它用途（`https://yechoy.cn/dav/music`）。
- **理由**：风险隔离；`/dav` 只是 AList 的路由前缀，不是协议要求。
- **代价**：需要路径规划（枢纽用 `/sync/` 或子域名）。
- **状态**：已定。

### D3 · 第一阶段客户端零代码改动
- **背景**：改客户端（栖弦/LX）成本高且不可控；用户曾考虑 fork。
- **理由**：合并搬到服务端后，客户端"笨"也能正确收敛。
- **代价**：服务端要容忍客户端整节替换/LWW/拿旧视图回写。
- **状态**：已定。

### D4 · 每客户端一份基线做差分，不升级客户端文件格式
- **背景**：客户端文件里没有"谁写的/上次看到什么"。
- **理由**：不动客户端即可获得三路合并能力。
- **代价**：换机/清数据 = 新身份 ⇒ 只能"只增不删"。
- **状态**：已定。

### D5 · 统一格式（canonical-v1）只存在于服务端内部
- **背景**：各家格式不同。
- **理由**：合并算法只写一次；对外仍按各客户端格式收发。
- **代价**：需要适配器层。
- **状态**：已定。

### D6 · 曲目身份 = `source + songId`；歌单身份用映射表
- **背景**：歌单会改名；不同音源可能同 `songId`（`wy:123` vs `kw:123`）。
- **理由**：跨源不撞车；改名不复制歌单。
- **代价**：服务端要维护歌单别名表。
- **状态**：已定。

### D7 · 删除用墓碑；同一元素"一加一删"删除优先
- **背景**：靠"缺席"表达删除会和"尚未同步"混淆。
- **理由**：避免删除反复复活。
- **代价**：墓碑需要清理策略（用**确认水位**，不用时间 TTL，见 D21）。
- **状态**：已定。

### D8 · 任何客户端首次接入只增不删
- **背景**：首次没有基线，任何删除判定都不可靠。
- **理由**：这是防"血洗歌单"的第一道闸。
- **代价**：首次接入后，空间里原有的"垃圾"需要人工清理一次。
- **修订（D20，2026-10-05；机制再修订见 D21）**：新身份设备带来的内容仍受**墓碑压制**——已墓碑化的条目不因新设备再次提交而复活，而是转成状态页的"待确认恢复"卡。**压制不以时间为判据**，只作用于**身份不可信**的提交者。
- **状态**：已定。

### D9 · 目标是通用 WebDAV 枢纽，插件不是前提
- **背景**：用户要"任何支持 WebDAV 的客户端填 URL 就能同步"。
- **理由**：解耦；多平台可扩展。
- **代价**：必须实现完整 WebDAV 兼容层与方言识别。
- **状态**：已定。

### D10 · 接入 = 一个 URL + 一组账号密码（Basic over HTTPS），账号即空间
- **背景**：用户明确要求"一个 url 链接，而且要有账户密码来表示身份"；2026-10-05 再次强调"**就简单些啊，通过 url+账户+密码认证**"。
- **理由**：与 AList 习惯一致；天然多用户隔离与吊销；客户端普遍原生支持。
- **决定**：**用户侧只填三项**（URL、账号、密码），**不要求为每台设备配置不同地址**。枢纽按 `(账号/空间, 方言, 设备标识)` 识别设备。
- **多设备改造（2026-10-06 已实现）**：设备标识 = `X-Hub-Device` 头 ＞ URL 设备段 `/d/{device}/` ＞ `default`（老空间无标识请求沿用 `账号:方言` 旧 key，行为与升级前完全一致，M8）。电脑端（澜音插件）可零配置用头；手机端（栖弦不发头）在地址里加设备段即可分开。**不额外配置的两台设备仍共享 `default` 身份**，残差由 **R1 删除判据（base_served ∩ base_submitted）** + `revision` 闸门 + 安全阀兜住——R1 之后"别人加的内容被误判成这台设备的删除"这条唯一丢数据路径已封死（M1 复现脚本：修复前丢、修复后不丢）。
- **代价**：必须 HTTPS；需防"密码错误锁定 IP"。
- **状态**：已定（2026-10-05）；多设备维度 2026-10-06 落地。

### D11 · 未识别方言隔离存储、不跨格式合并
- **背景**：无法为每个客户端预置适配器。
- **理由**：宁可先不同步，也绝不猜错格式把数据合并坏；补适配器后**先通知用户、经其确认**再并入（评审 M3 修订：若自动并入，用户只会看到"配置对了却什么都没发生"）。
- **代价**：新客户端上线到"真正参与同步"之间有一个空窗期。
- **状态**：已定。

### D20 · "删除永不复活"用墓碑压制实现，而不是"接受换机复活一次"
- **背景**：用户提问（2026-10-05）："已经删除的歌不是都同步上去了吗，那换设备怎么还会有已删的歌会复活呢"。
- **机制澄清**：① **同一台设备**（身份不变，哪怕离线很久）本来就不会复活——枢纽持有它的基线 + 墓碑，同步时直接告诉它"这首已删"；② 只有**设备身份变化**（重装 App / 清数据 / 换新机）才会被当成新客户端，而"首次接入只增不删"（D8）会把它的本地残留重新加回来。
- **决定（用户 2026-10-05 选择"不要自己回来"）**：墓碑**压制**复活——**身份不可信**的提交者（无基线 / 未验证 / 已判退休）提交一个已墓碑化的条目时，枢纽拒绝加回，并在状态页出确认卡「恢复 / 保持删除」；墓碑只存 key + 时间戳（约 50 B/条）。**压制不以时间为判据**（机制修订见 D21）：已越过删除点的已知身份重新添加同一 key = 显式恢复，直接生效并清墓碑。
- **与 D8 的关系**：D8"首次接入只增不删"仍然成立（绝不因为陌生设备"没有"而删数据），但它的**新增**要再过一道 I7 墓碑压制。
- **代价**：**换设备/重装带来的旧副本**里含用户删过的歌时，需要点一次确认（状态页写出原因「你于 X 删过它」）；同身份设备与已确认过的身份不会被拦（D21）。
- **落地**：`docs/05` 新增不变量 **I7** 与用例 **26**；引擎边界用例 25 → **26 条**。
- **状态**：**已定**（2026-10-05）。

### D21 · 墓碑不以时间为判据：抑制看身份，GC 看确认水位
- **背景**：用户质疑 D20 的"2 年"（2026-10-05："两年太长了吧……都已经是通过 url+账户+密码，这已经能表面身份了吧"）；两轮独立复审（`docs/11-对抗性评审-合并引擎.md`、`docs/10` §10.8）证明"时间为判据"双向出错：既拦下**同设备合法重加**（栖弦按"缺席即删"重建本地 ⇒ 用户看到的是"我加的歌被删了"），又制造"满 N 天后旧设备回来即可复活"的新窗口，并与 `spec` T3"全员确认后才可 GC"直接矛盾。
- **决定**：① **抑制的判据 = 提交者身份是否可信**（无基线 / 未验证 / 已判退休），不是时间；② **GC 的判据 = 确认水位**——删除发生时已注册的所有客户端都已在成功交付中见过该墓碑（`docs/03` §3.7 `tombstones` 增 `created_at_revision` 与 `ack_mask`）；**例外（复检 S11/S15）：无删除能力的客户端（`can_delete=false`，澜音插件）不能靠 GET 确认**——它删不掉本地副本，收到不含该条目的视图也会在下一轮提交里带回来；它必须靠**提交内容里不再出现该条目**才算确认。代码落点：`deliver` 只对 `can_delete` 端 ack、`merge` 对无删除能力端按提交内容 ack、`_gc_tombstones` 对它要求 ack；③ **时间只用于判定身份是否退休**（>180 天未出现 ⇒ `retired`，从 GC 条件中排除，并在状态页列出）；④ **兜底 TTL 若一定要设，语义是"完全没有确认时的最长保留"，取无限（永不按时间 GC）**，绝不接受 30 天这类短值（与用例 23"离线 90 天"、6 个月场景冲突）；⑤ 离线 6 个月的活跃设备仍被压制 ⇒ 不复活（符合 D20/V10）；退休设备回来后走确认卡，**同样不自动复活**。
- **代价**：墓碑无界增长（约 50 B/条，可忽略——在文档里承认为**有意权衡**）；`docs/08` R16 的缓解措施"必要时手动缩短 TTL"**作废**。
- **落地**：`docs/05` I7/§5.3/§5.4/§5.5 用例 26、`docs/01` V7/V10、`docs/03` §3.5.3/§3.7、`docs/08` R16/Q9、`spec/canonical-v1.md` T3、`spec/README.md`。
- **状态**：已定（2026-10-05）。**2026-10-07 由 D25 修订**："显式恢复仅限删除发起者本人"→ 看过删除结果 + 冷静期后的任何可信端回推即显式恢复；"压制不以时间为判据"保留（冷静期只是防止同一轮竞态抖动，不是复活依据）。

### D22 · 第一版范围 = **原案：删除自动生效**（不采用"并集+删除转确认"）
- **背景**：产品复审建议砍到 `Cut A`（删除不自动生效、转确认），以省掉一半机制；2026-10-05 用户裁决："**就简单些啊，通过 url+账户+密码认证，并且同步，一方删了就删了呗**"。
- **决定**：**删除自动生效**（一端删了，另一端分钟级跟着删），不做 `Cut A`。因此 A1 正向归因、A2 持久待确认队列、D4 挂起渲染语义、E1 `canonical_mutated`、安全阀（挂起而非 409）**全部保留**。
- **"简单"的落点**：简单体现在**用户侧只有三项配置**（URL + 账号 + 密码，D10）和**没有额外确认流程**（正常删除不问用户、直接生效）；不体现在砍掉服务端的归因与安全阀——那些是"删了不会删错"的代价。
- **代价**：确认卡只出现在两种异常情形（大比例删除触发安全阀；提交无法归因）。25→26 条用例一条不减。
- **状态**：**已定**（2026-10-05）。

### D23 · 多账户共用歌单（空间即共享单位）
- **背景**：用户（2026-10-06）"我要实现多设备多账户之间共享歌单"（反转 D19）。
- **决定**：① 多个账号 `space` 填同一值 = 共用同一份 canonical（歌单真合并、双向、删除自动生效）；② **opaque（主题/音源/本地音乐）按 `client_key` 分桶存储与渲染，不跨设备交付**；③ 待确认卡带 `account` 归属，只有本人或管理员能确认/拒绝；④ 删除账号时孤儿空间**默认保留数据**，`?purge=true` 才清理。
- **代价**：同空间成员互相可写（无只读角色）；删除归因只到"账号"级；栖弦需手工把地址加一段才能分成两台手机（澜音插件尚不发设备号）。
- **落地**：`src/hub/store.py:97`、`src/hub/api.py:298-360/650/661/708/742`、`src/engine/engine.py:442-485`；用例 `tests/hub/test_api_http.py:389/421/452/484/511/536`。
- **状态**：已定（2026-10-06）。**2026-10-06 扩展为多对多成员表 + 空间角色 + 邀请码（v3），见 D24**；D23 的"同空间成员互相可写（无只读角色）"代价由 viewer 角色补齐。

### D24 · 空间与成员体系（角色 + 邀请码 + 自助建空间，config v3）
- **背景**：D23 下账号与空间仍是一对一指针，"共用"靠管理员把多个账号的 `space` 改成同一值；用户要求普通账号能**自助**与家人共享、能设**只读**成员、且**不能凭猜测擅入**他人空间。
- **决定**：
  1. config 升级 **v3**，在 accounts/spaces 之外新增 **members（多对多）/ invites（邀请码）/ policy（策略）** 三段；账号保留"**当前空间指针**"，**一个账号同一时刻只生效一个空间**。
  2. **为什么只生效一个空间**：同步协议（canonical-v1）的 GET/PUT 以"账号当前所在空间"为唯一作用域，客户端一次只与一份歌单双向同步；若同时挂多个空间，会产生"这次提交代表哪份歌单"的歧义，也会让删除归因与基线差分失效。需要别的空间时显式"切换空间"即可，成员关系（可进哪些空间）是多对多、长期保留的。
  3. **角色管"进了能做什么"**：owner / editor / viewer 三级，全局 admin 对任何空间视同 owner；viewer 只读，同步 GET 走引擎新增的纯只读 `peek_view`（不注册客户端、不推进基线、不 ack 墓碑）。
  4. **邀请码管"怎么进来"**：加入他人空间必须持有效邀请码（editor/viewer，不能造 owner），失效四态可区分（不存在/已撤销/已过期/已用完）；可凭码自助注册新账号（`allow_self_register` 开关）。
  5. 普通账号可**自助创建属于自己的空间**（纯增量，受 `max_owned_spaces=3` 配额限制，admin 不限）；首个创建/归属账号即 owner；不搞"admin 兜底进所有空间"。
  6. 成员变动、邀请、注册、切换/退出、代管全部写 **`_audit.jsonl` 审计日志**；配置原子写盘 + `.bak1/.bak2`，密码仍 pbkdf2 不存明文。
  7. **空间重命名＝展示名可变、id 不变**（第三轮）：`spaces[id].name` 字段已存在、零迁移；WebDAV 地址不含空间名故客户端零影响；API 路径参数由 `_find_space` 同时接受 id 或唯一展示名；`account.space` 仍存 id，不得改 name。
- **代价**：展示名与 space_id 允许不一致（同名/重名冲突由 API 校验）；viewer 首登无需 PUT 即可读（引擎唯一只读例外）；邀请码/注册上公网前必须配限流并关自助注册（见 docs/06、docs/08 Q18）。
- **落地**：`src/hub/api.py`（v3 数据层/权限层/13 条新接口 + 第三轮 rename/policy 路由）、`src/hub/run_fastapi.py`（迁移/策略日志）、`src/engine/engine.py`（`peek_view`）、`webui/src/components/SpacePanel.vue`、`LoginView.vue`；用例 `tests/hub/test_spaces_http.py`（26 条，含第三轮 test_22~26 重命名）。

### D25 · 同空间删除免二次确认（互信直删 + 交付即确认 + 冷静期压制）
- **背景**：用户（2026-10-07）以两台栖弦实测：A 设备新增歌单同步、B 设备删除后回推仍需确认卡，且 A 的陈旧残留会在下一轮把已删歌单重新同步上去——"既然都归属于同一个空间那么就应该是信任的设备，这个就不用再确认了"。dsh 审查文档《第四轮修改文档-删除免二次确认与前端整改.md》立项。
- **决定**：
  1. **时间戳根因（A）**：枢纽交付时间戳 `%Y-%m-%dT%H:%M:%S.%fZ`（毫秒固定宽、单调 `+1ms`），压过客户端本地值（`modifiedAt` 透传并入比较），消除"交付值 == 提交值 → 客户端 LWW 误判自己最新"（根因 A）；内容无真变不推进。
  2. **墓碑确认（P0-B）**：恢复"交付即确认"——`deliver` 交付删除后视图即 `acked.add`；`merge` 确认段 split：回推（带键）→ `carried` 记入并**撤销** ack；提交不带键 → ack。**无删除能力端（澜音 `can_delete=false`）**：GET 看过不算数（删不掉本地、必带回），但**提交不再带该键 = 真采纳**（D21 提交内容确认语义）；`deliver` 对澜音关掉 ack。墓碑 GC 为简单"全部 acked"版。
  3. **恢复判据（P0-C）**：去掉"仅删除发起者本人"限制——**身份已验证 ∧ 未退休 ∧ 可删除 ∧ 看过删除结果（served_revision ≥ 删除 revision）∧ 距删除 ≥ 冷静期（`restore_grace_seconds`，默认 120s）**的回推 = 显式恢复、直接生效、无卡；冷静期内的重加仍按残留压制（防同一轮竞态抖动）。
  4. **安全阀分流（P1-2）**：`trusted = identity_verified ∧ can_delete ∧ !retired` 时可信端大比例删除**不再挂起**（空间策略 `trusted_direct_delete=True` 默认，可关）；不可信端仍走挂起确认卡。
  5. **澜音缺席（P1-3）**：`never_owned` 并入删除时加 `if client.can_delete:` 闸门——澜音缺席只记 `meta.never_owned`、不写墓碑不删数据。
  6. **恢复确认卡（P1-1）**：`_note_restore` 全局短路（`confirm_restore=False`），同空间不再产生"待确认恢复"卡；抑制信息由 `meta.suppressed_playlists/suppressed_tracks` 承载；`/api/state` 的 pendingRestores 字段与确认端点保留（策略可开回）。
- **代价**：互信直删下"只提交部分视图"会被解释为删除空间内未提交歌单（首接 `_adopt_initial` 仍只增不删）；冷静期内的同端"删了立刻加回"需要等 120s（策略可调 0）。
- **落地**：`src/engine/engine.py`（`_next_stamp` 重写 / `Tombstone.carried` / `_crossed_deletion_point` / `_note_restore` 短路 / 安全阀分流 / `_gc_tombstones` / `_mark_retired`）、`src/engine/canonical.py`、`src/hub/api.py`（策略三键 / `modifiedAt` 透传 / C2–C4、C6）、`src/hub/store.py`（merge 透传 + hasattr 兜底）；测试见 §4.1 名单（引擎 +3、多设备 +7、故障注入 +1、hub +4，共 118 条全绿）。
- **状态**：已定（2026-10-07），详见 [`docs/05-合并引擎.md`](05-合并引擎.md) §5.3.5 与第四轮修改文档。

### D26 · 澜音按"可删"处理（收口，2026-10-07）
- **背景**：D25/P1-3 之前，`CAPABILITIES["ceru-plugin"].delete_track=false` ⇒ 枢纽对澜音走三条特殊路径：缺席不并入删除、不计入墓碑确认水位（`deliver` 关掉 ack）、安全阀仍挂起。用户 2026-10-07 拍板：澜音删不掉本地副本是**客户端**要解决的问题（其开发者正在处理，用户手动删掉即可），枢纽不再替它兜底。
- **决定**：`adapters.CAPABILITIES["ceru-plugin"]` 的 `delete_track`/`delete_playlist` 置 **True**（能力表是单一来源，`src/hub/store.py:121-124` 注入 `Client.can_delete`）；`GET` 的 viewer 分支 `api.py` 也从能力表取 `can_delete`，不再写死 `dialect != "ceru-plugin"`。
- **保留**：`engine.py` 仍支持 `can_delete=false` 的通用语义（`tests/engine/test_multidevice.py:318` 等仍在用），但当前没有方言映射到 false；澜音"无基线 GET → 200 空视图"这条**探测兼容**改为按方言判断（与删除能力解耦），否则澜音首次保存配置会因 404 误报端点不存在。
- **影响**：澜音提交里"少了"的曲目/歌单按删除处理并写墓碑；它 GET 看过删除后即 ack，若随后回推残留，`merge` 的 `carried` 会撤销确认（`Tombstone.carried` → `t.acked.discard`），墓碑不会被提前 GC。
- **状态**：已定（2026-10-07）。
