## 10.2 因为评审而**废弃**的既有决策（重要）

| 废弃项 | 原设计 | 现在 | 原因 |
|---|---|---|---|
| `modifiedAt` 渲染时填"当前时间" | 让客户端 LWW 总判"远端更新"，从而采用合并结果 | 随空间 `revision` 单调推进，**内容不变则不推进** | 原方案导致"每轮必写回"的写放大，且会覆盖客户端本地尚未同步的新增（A3/M1） |
| 条件读 `If-None-Match` → `304` | 省流量 | **不使用 304**（永不对客户端发 304），内容未变返回 `200` + 相同正文与 ETag | 栖弦把非 2xx 判为失败（`webdav_client.dart:69/91`）；省流量改由 gzip 承担 |
| 安全阀"整批 `409` + 等确认" | 更安全 | **挂起删除 + 新增照常 + `200`**，确认通道落在状态页/CLI | 栖弦写回前已落盘、只对 412 重试一次 ⇒ 409 会让它永久卡死并反复推含删除的视图（A2/P1） |
| 接入凭据以"路径令牌"为主 | 让"只填一个 URL"成立 | **一个公共 URL + 账号密码（Basic over HTTPS）**；令牌降级为极少数客户端的兜底 | 用户明确要求（m01714）；与 AList 习惯一致、天然多用户隔离与吊销 |
| 共享空间（多账号同一空间） | 家人共享 | **不做**（用户 2026-10-05 最终定：**不做共享歌单，每人一个账号**）——**已于 2026-10-06 反转（D23）**：现为空间级共用歌单 + opaque 按客户端分桶 + 确认卡归属 | 与 V6 互斥、删除归因无解（P4/U6）；曾一度改为"歌单级共享 + 权限"（D19），用户随后决定整体不做 |
| 单文档超限"分页/裁剪并标 `truncated`" | 保住响应 | **绝不裁剪**：瘦身 → 仍超则拒绝写入 + 提示导出；分片留待量出上限后再定 | 裁剪对客户端等于静默丢歌（违反 V7） |
| `baselines` 存整份视图 | 实现简单 | 只存**元素键清单 + 哈希**；整份视图按 `canonical_revision` 共享物化、按需重建 | ≤20 客户端 × 整份视图会撑爆 32 MiB 空间配额（A6） |

## 10.4 不采纳 / 判定为误读的发现

**A4「曲目池身份冲突」——部分误读，改为澄清而不改结构。**
架构师认为：`I3`（`tracks[]` 内身份键唯一）与 `P5`（同一首歌只存一份、歌单只持 `trackIds`）冲突——"同一首歌进多个歌单会被校验器判非法"。
我的核实：两条规则并不冲突——池中每个身份只有**一条记录**，多个歌单的 `trackIds` **引用同一条**，`I3` 的唯一性约束作用在 `tracks[]` 上，不作用在引用计数上。示例之所以看起来"每首只属于一个歌单"，只是样例小，不是规则限制。
**处置**：不改池结构，但补充三处澄清（`spec/canonical-v1.md` §4.2/§6、`docs/04` §4.2）：① `id`（`tr_<ULID>`）是**记录键**、`(source,songId)` 是**身份键**；② 多歌单引用同一条记录**不构成**身份重复；③ `track` 墓碑按**身份键**记录，不按 `tr_<ULID>`。

**A6 部分数字**：架构师给出的"每客户端 ≥5 s + ≤20 客户端 ⇒ 预算不成立"在**单写者串行**前提下成立，但结论应是"重写预算并给出容量模型"，而非"架构不可行"——已按此处置（`docs/05` §5.7、`docs/03` §3.9）。

**其它**：无。四位评审的其余发现均被采纳或部分采纳。

### 10.8.2 I7 / TTL 的裁决（复审要求明确表态）

- **删掉"2 年"在抑制上的角色**：抑制的判据是**提交者身份是否可信**（无基线 / 未验证 / 已判退休），不是时间。否则会拦下**同设备合法重加**，而栖弦按"缺席即删"重建本地 ⇒ 用户看到的是"我加的歌被删了"（违反 T2 精神与 V8）。
- **删掉"2 年"在 GC 上的角色**：GC 由**确认水位**决定（删除发生时已注册的所有客户端都已在成功交付中见过该墓碑）；>180 天未出现的身份标记 `retired`，排除在 GC 条件外。
- **时间只用于判定身份是否还活着**，绝不用于判定"删除是否还算数"。
- **兜底 TTL**（若运营上一定要设）：语义 = "完全没有确认时的最长保留"，取**无限（永不按时间 GC）**；**30 天不安全**（与用例 23"离线 90 天"、6 个月场景直接冲突）。
- 容量理由不成立：墓碑约 50 B/条，无界增长可忽略（承认为**有意权衡**）。
- ⇒ 落地为 **D21**；`docs/08` R16 的"必要时手动缩短 TTL"作废。

### 10.8.3 产品/复杂度复审的结论（未改文档的部分）

- 架构方向成立（客户端零改动只能如此），但**第一版范围过大**：文档自估 1.5–2.5 周，实际 **4–6 周**；墓碑/TTL/I7/安全阀/状态页这一半机制**只在支撑"自动删歌"**。
- 建议 **Cut A = 并集 + 删除转确认**：删除不自动生效 ⇒ V10"删除不复活"**免费成立**；26 条用例中 2 条消失（14 安全阀 / 26 墓碑压制）、5 条改写（2/4/5/7/9）、19 条保留。⇒ 记为 **D22（待用户决定）**。
- 建议先做**种子化干跑**：用现有云端 `歌单样例\sync-v1.json`（237 KB / 245 首）+ 本地 `playlists.db` 导出做"往返无损"验证；并**先用现有云端文件播种枢纽** ⇒ 手机首次 GET 拿到的是自己内容的超集 ⇒ 首次接入风险（Q11）自动消失。
- 最可能死因：**静默分叉且没有调试回路**（栖弦把一切 HTTP 结果翻成四句固定文案、只接受 2xx），叠加当前处境"没在同步、设计冻结、0 行代码"。
- 一周版切分（若做）：D1 种子干跑 / D2 门面（OPTIONS·PROPFIND·HEAD·GET·PUT·MKCOL，永不 304）/ D3 并集 + opaque 透传 / D4 一台真机走隧道 / D5 第二个参与者 / D6 候选队列 + 备份 / D7 故障演练 + 回退。
- 另列文档体量问题：**当前文档量已超过被描述的系统本身**，需在下轮瘦身（本轮未动）。
