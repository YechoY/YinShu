# 客户端对接说明（可直接转发给客户端开发者）

> 背景：我们自建了一个**服务端合并枢纽**（`playlist-sync-hub`，FastAPI）。澜音插件、栖弦、洛雪三个客户端都连它，各自上传自己格式的整份歌单文件，枢纽做**三路合并**后按各自格式返回。客户端不需要懂别人的格式。
>
> 这份文档说明**客户端需要怎么连**，以及**希望客户端配合改的两件事**。除特别注明外，枢纽侧已实现或本轮正在实现，**客户端改动量很小**。

---

## 0. 通用接口契约（三个客户端都一样）

**认证**：HTTP Basic —— 用户名 = 枢纽账号，密码 = 账号密码。用户名决定"**空间**"（分享单位），客户端不需要知道空间名，地址里也不出现空间名。

**路径**：两种写法，二选一

| 写法 | 例子（栖弦） | 说明 |
|---|---|---|
| 在**地址**里带设备段 | `http://<枢纽>:8000/d/phone` | 客户端把自己固定的目录/文件名接在后面 → `/d/phone/CyShineMusic/sync-v1.json` |
| 在**请求头**里报设备 | `X-Hub-Device: phone` | 地址填枢纽根 `http://<枢纽>:8000` |

- 设备名规则：`[A-Za-z0-9_-]{1,32}`，非法会被拒（400）。**头优先于路径段**，所以**不要同时用**（否则设备会判成头里那个）。
- **同一账号 + 同一客户端 + 不报设备名 = 同一台设备**，两台机器会共用一份同步基线，A 机器还没同步到的新歌在 B 机器提交时会被判成"删除"。所以**多设备必须区分设备名**（或每台填不同地址）。

**响应约定**

- `GET` 成功返回 **200 + 该客户端格式的完整文件**；**枢纽永不返回 304**（请按内容比较判断是否需要回写，不要依赖 `If-None-Match` 的 304 分支）。
- `PUT` 成功返回 2xx；请求体就是客户端自己格式的整份文件。
- 枢纽会发 `ETag`，也接受 `If-Match` / `If-None-Match`，但**不会**用 304 回你。
- 没有远端数据时，枢纽可能返回 **404**、也可能返回 200 + 空视图 —— 两种都要按"远端为空"处理（栖弦现有 `read()` 已把 404 当 null，行为正确）。
- 可以 `MKCOL`（返回 2xx/405 都不会报错）、`HEAD`、`OPTIONS`；不需要创建目录。

## 1. 给栖弦（CyShineMusic / CyShineMusic-Y）开发者

### 1.1 现状

栖弦**今天就能连枢纽**：`lib/core/sync/webdav_client.dart:32-33` 的 `${baseUrl}/CyShineMusic/sync-v1.json` 正好对上枢纽的 `/CyShineMusic/sync-v1.json`。地址/账号可配，`sync-v1.json` 的外形不用改。

**问题只有一个：多设备**。同一个账号在两台设备上填同一个地址时，枢纽把它们当成同一台设备，会共用基线 → 可能出现"平板把手机上刚加的歌当删除"。

### 1.2 最小方案：**零代码**（推荐先这么用）

每台设备的**地址栏**填不同值即可：

```
设备 A：http://<枢纽>:8000/d/phone      → 枢纽收到 /d/phone/CyShineMusic/sync-v1.json
设备 B：http://<枢纽>:8000/d/pad        → 枢纽收到 /d/pad/CyShineMusic/sync-v1.json
```

枢纽把 `/d/<设备名>` 解释为设备身份，两台设备各自独立基线，互不误删。**栖弦不需要改任何代码**，只要在设置页/文档里提示"多设备请各填不同地址"。

### 1.3 建议的代码改动（可选，体验更好）

1. 新增设置项（如 `webdav_sync_device_v1`）：首次开启同步时自动生成稳定短名（如 `cyshine-<6 位>`），持久化，设置页可改；
2. 路径拼成 `directoryUri = <baseUrl>[/d/<deviceId>]/CyShineMusic`；
3. 设备名只允许 `[A-Za-z0-9_-]{1,32}`，非法就拒绝保存并中文提示；
4. 如果用户自己在地址里填了 `/d/xxx`，就不要再发 `X-Hub-Device`（二选一）。

### 1.4 删除传播：需要一处真正的行为改动

枢纽的删除结果**目前可能被栖弦丢掉**，根因两条：

1. **section 级 LWW 用本机墙钟**：`sync_models.dart:120-127 newerSyncSection()` 比 `modifiedAt`（本地是设备墙钟毫秒）。枢纽交付的 `modifiedAt` 只保证"比自己上次交付大"，打不过设备墙钟 → 栖弦认为"本地更新"，丢弃远端并把自己那份推回去，**删除被撤销**。
2. **纯拉取不 ack**：`webdav_sync_controller.dart:286` 在"合并结果与远端相同"时直接 `return`，不 PUT。枢纽的墓碑确认只发生在合并里 → 墓碑只增不减。

**建议**：新增同步模式开关 `mirror`（默认，现状，用于自建网盘）/ `hub`（连枢纽）。`hub` 模式下：

- 不跑 `newerSyncSection`，**直接把远端快照当权威**（`_applyRemoteSections(local, remote.snapshot)`）；
- 然后把本地视图**整份 PUT 一次**（即使 `_sameSnapshotData` 为真也要 PUT），用于 ack 墓碑。

`sync-v1.json` 的外形**不用改**（枢纽把 `appearance` / `musicSources` 按客户端分桶原样保管，不跨设备下发）。

**验收**：两台栖弦 + 一个澜音（同账号）—— A 删一首歌 → B 同步后本地也删掉；B 再同步不会把它推回来。

## 2. 给洛雪开发者

### 2.1 现状（我们读了你写在 Alist 上的真实文件）

`https://yechoy.cn/dav/music` → 本地 `D:\Alist\music\`，实际文件：

- `LX_Muisc/playlists.json`（866,956 B）：顶层 `version / lastModified / data / playHistory / downloadTasks`，`version` 是**字符串** `"2"`，`lastModified` 是 epoch 毫秒；
  - `data.defaultList` / `loveList` / `tempList` = **曲目数组**（722 / 232 / 301 首）
  - `data.userList` = **歌单数组**（2 个：`tx_32c57f1de8258842602240a7c3920333`(YHK,114 首)、`userlist_1782378881351`(纯音乐,17 首)）
  - 共 1386 首，音源 tx 1169 / wy 69 / kw 99 / kg 49
- `lx-x-playlists.json`（137,005 B）：同一 schema 的精简导出（没有 `playHistory/downloadTasks`）。

### 2.2 想请你确认/配合的三件事

1. **地址与目录能否配置**？我们希望 base 填 `http://<枢纽>:8000/d/<设备名>`、目录填 `lx-x`，即请求 `/d/<设备名>/lx-x/playlists.json`（或不带 `/d/` 段时由枢纽按文件名兜底）。若文件名/目录被写死，请告诉我们实际值，我们在枢纽侧注册即可（**不需要你改**）。
2. **是否支持自定义请求头**？支持的话可以发 `X-Hub-Device: <设备名>` 来代替地址里的 `/d/` 段（**二选一，别同时**）。
3. **同步语义**：是"手动/自动整份上传下载"，还是本地也会做合并？如果本地也做类似栖弦的"按 `lastModified` 取新"（**本机墙钟**），枢纽的删除结果会被本地判成"更旧"而丢弃 —— 那就需要像栖弦那样加一个"以远端为准"的模式。抓一次请求即可判断：PUT 的 body 是整份文件还是增量。

### 2.3 枢纽会怎么对待你的文件（承诺）

- **只有 `data.userList`（用户自建歌单）参与合并**，且回写仍是你的外形（`version:"2"` 字符串、epoch 毫秒 `lastModified`、`interval` 用 `mm:ss`）。
- `data.defaultList` / `loveList` / `tempList`、顶层 `playHistory` / `downloadTasks`：**按客户端分桶原样保管、原样返回**，不合并、不跨设备下发 ⇒ **不会被别人清空，也不会被发送给别人**。
- 曲目 `id` **原样回写你给的字符串**（含 49 首 kg 老格式 `545879713_E3426FF…` 这种没有 `kg_` 前缀的），不会重新推导成别的 id，避免你把自己的曲目当成新歌。只有"别的客户端带进来的新歌"我们才会合成 `"<source>_<id>"`。
- 歌单附加键（`origin` / `source` / `sourceListId` / `locationUpdateTime`）原样透传。
- 我们不写你不认识的键。

### 2.4 需要你侧确认的字段

`interval` 一律 `mm:ss`（≥1 小时 `h:mm:ss`）；`meta` 会被我们原样回填常用键（`songId/strMediaMid/albumName/albumId/picUrl/qualitys`），未知键不丢。若你有校验（如 `version` 必须是字符串、`data` 必须四键齐全），请提前告诉我们。

## 3. 联调验收（双方一起看）

1. 客户端 A 加一首歌 → 客户端 B（同账号、不同设备名）同步后能看到；
2. A 删一首歌 → B 同步后消失；**B 再同步不会把歌推回来**；
3. 两台同类设备各自增删 → **互不误删**（这是设备名存在的唯一理由）；
4. 换一个账号登录 → 看到的是那个账号自己空间的内容，看不到上面这些。
