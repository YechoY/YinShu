结论：**交付条目缺 `meta._qualitys` ⇒ 点播在解析音质时就抛异常，URL 根本没请求。**

### 2. 真因（枢纽侧）

旧 `render_lx` 每首只输出：

```python
"meta": {"id":…, "songId":…, "strMediaMid":…, "albumName":…, "picUrl":…,
         "qualitys": [{"type": <最高档>}]}     # 没有 _qualitys，size 也丢了
```

且 `_lx_tracks` 只把 `_best_quality()` 选出的**最高一档 type** 存进 canonical，用户洛雪原文里的
`qualitys`（4–6 档，带 `size`）、`_qualitys`、`albumId`、`albumMid` 全部无留档。

### 3. 修复（`src/hub/adapters/lx.py`）

- 新常量 `_LX_META_KEYS = ("_qualitys","albumId","albumMid","albumName","id","picUrl","qualitys","songId","strMediaMid")`
  —— 洛雪原生 meta 就这九个键。
- `_lx_tracks`：把九个键里非 None 的值留档为 `entry["lx_raw_meta"]`（走 `meta_delta` 汇总）。
- `render_lx`：按九个键**原样回写** → 用枢纽字段覆盖 `songId`/`strMediaMid`/`albumName`/`picUrl`/`albumId`
  （`meta.id == 0` 语义保持：枢纽没有洛雪数字主键）→ 调 `_ensure_lx_quality_meta()`。
- 新 `_ensure_lx_quality_meta(tr_meta, fallback_quality)`：保证 `qualitys` 与 `_qualitys` **同时非空**；
  只有映射时补数组（带 `size`）；两者都缺时用最高档猜测，并补 `128k` 下限，`size` 写 `""`。
- 未动：`_best_quality`（仍作 fallback）、opaque（三张个人列表/顶层键/非白名单曲目原样往返）、`DIALECT`。

### 6. 仍未定论

### 6. 让修复真的送到设备上（交付戳的坑）

改完适配器还不够：`_next_stamp()`（`src/engine/engine.py:311-342`）判断"内容有没有变"用的是**交付视图**
（歌单名 + 曲目身份键顺序 + opaque，`_view_hash`），**曲目级 meta 不在判据里**。我们这次是直接改 `meta_pool`，
于是 `lastModified` 保持 `2026-10-08T08:22:12.862Z` 不动 ⇒ 洛雪客户端 `hasRemoteUpdate = remoteTimestamp > localTimestamp`
为假 ⇒ 它**不会重新采纳**，修复到不了设备上（这正是"枢纽看起来对了、客户端还是坏的"的经典陷阱）。

处置：`tmp/touch_delivery_stamp.py`（先停枢纽，干跑/`--apply`）：

1. `engine.content_changed_at = engine._now()` —— 给下一次交付一个能压过客户端本地时间的候选值；
2. 对每个客户端**只清 `base_served.stamp`**（保留 `view` / `served_revision` / `view_hash`）——
   `_next_stamp` 的 `bsrv.stamp` 是"视图没变就复用旧戳"的短路条件，不清推不动；而 `view` 必须保留，
   R1（`owned = base_served ∩ base_submitted`）与 I2′ 闸门都靠它。下一次 `deliver()` 会用新戳重建完整基线（自愈）。

现场执行结果（2026-10-08 16:45）：`content_changed_at 08:22:12.862Z → 08:45:45.863Z`，清了 3 个客户端的交付戳，
`_next_stamp(Yecho:lx-x:default)` 回读 = `2026-10-08T08:45:45.863Z`，**revision 仍 16、歌单内容一字未动**。

> **未修的局限**：`_view_hash`/`_next_stamp` 不含曲目 meta ⇒ 任何"仅 meta"的变化都不会自动推进交付戳。
> 根治要动核心收敛逻辑（`ServedBaseline` 增"交付 meta 哈希" + `deliver()` 由 `SpaceRuntime` 包装注入，
> 因为 `meta_pool` 在 hub 层、引擎拿不到），留待后续轮次评估——好在现有 merge 规则是"缺失字段不覆盖已存在"，
> 既有曲目的 meta 本来也不会被客户端改写，触发面只有维护/回填。

## 事故二：新增曲目置顶要覆盖所有平台（m04142）

- 现状：置顶规则写在引擎里、**与方言无关**；第七轮补的 `merge()` 主路径、第八轮补的 `_adopt_initial()` 首次接入通道，
  两条路径都对三方言生效。
- 本轮补的是**跨方言回归**：`tests/engine/test_multidevice.py::test_new_tracks_go_to_head_from_every_dialect`
  （A=栖弦、B=`ceru-plugin`、C=`lx-x` 各加一首 ⇒ 依次置顶 `["kg:g1","wy:w1","kw:k1","tx:t1","tx:t2"]`）。
  ⚠️ 方言名是 `ceru-plugin` 不是 `ceru`（`from hub import adapters` 才会把方言注册进 `SyncSpace.KNOWN_DIALECTS`，
  否则 `merge()` 直接返回 `{"isolated": True}` 而不做任何合并）。
- 顺带固定的边界：**集合不全的提交不得整体重排**（该设备还看不到别人新加的歌时，提交顺序不等于空间状态）；
  只有交付过完整集合后的纯重排（集合相等、无新增）才整体采用提交顺序。
- 配套更新了 `tests/hub/test_api_http.py` 里两处"交付顺序"期望（`test_03_conditional_header_never_304`、
  `test_05_native_id_registered_across_dialects`）为置顶后的 `["kw_2","tx_1"]`。

## 教训

1. **"能播"不是枢纽自己的事**：交付合同的验收标准是"客户端拿到后能不能用"，不是"枢纽字段看起来对不对"。
   洛雪的音质字段是**两份并存**的结构（`qualitys` 数组 + `_qualitys` 映射），只给一份等于没给。
2. **客户端有无守卫的解引用时，枢纽要么给全、要么给兜底**：`meta._qualitys` 一缺就是 TypeError，
   所以 `_ensure_lx_quality_meta()` 选择"至少给一档 + 128k 下限"，而不是"缺就缺"。
3. **别在测试里直接改引擎开关**：`delete_cards_enabled` / `trusted_direct_delete` / `restore_cards_enabled`
   由 `api._apply_engine_policy_to()` 按 `_policy` 反复重设（`api.py:134-149`），直接改 `engine.xxx` 会被下一次
   `Hub.get()` 冲掉 —— 要改就改 `api._policy` 再 `api._apply_engine_policy()`
   （`tests/hub/test_api_http.py::test_13` 已按此修正）。
4. **`Hub.probe()` 不登记运行时**，`Hub.save()` 因此拒绝写盘（第九轮踩坑，现为显式 `KeyError`）——写盘前必须 `Hub.get()`。
5. 同一首歌在两份 lx 原文里音质档位数可能不同，回填要**取档位更多的那份**，否则会把 4 档覆盖成 2 档。
