# 多账户共用歌单 —— 一次性修改文档

> 交付对象：下一个接手的 AI（豆包）。
> 目标：把"多人共用一个空间共享歌单"从"能用但硌手"做到"能用且不互相覆盖"。
> 本文件只写"改什么、改哪里、怎么验收"，不含设计讨论。所有行号基于当前工作区代码。

---

## §0 一句话目标

两个账号把空间填成同一个值时，**歌单共享**（已实现且正确），但**主题外观 / 音源配置 / 本地音乐**会互相覆盖，**确认卡**会泛滥且能被别人点掉，**空间**只能在建账号时填一次且填错会静默建空空间。

本轮要修的就是这四件事，**核心是 §1**。§4/§5 可选、可单独一轮。

## §0.1 铁律（先读，违反任何一条都算失败）

1. **不许改** `src/engine/engine.py` 里的：R1 判据（`owned = base_served ∩ base_submitted`，`:491-508`）、I2′ 并发闸门（`:509-520`）、墓碑 GC 例外（`:739-759`，`can_delete=False` 必须 ack 才允许回收）、"永不回 304"（`src/hub/api.py:772-817`）。这些是修 bug 换来的，改回去会让 M1/S10/S11/S15 复发。
2. **不许改** 栖弦（CyShineMusic）与澜音插件仓库的任何代码；本轮**只动 `playlist-sync-hub`**。
3. **不许改** `webui/` 已有接口调用的契约（只能新增调用）；前端可以加界面，不能改已有请求的参数/路径。
4. **不许编造测试数字**。跑不通就写"未跑通 + 原始报错"，不许写"全绿/68 条通过"。
5. **不许用脚本批量改写测试文件**（历史上用"找函数末尾"的脚本替换 `rmtree_force` 时，把紧跟其后的整个测试类一起吞掉，14 条用例凭空消失）。要改测试就逐处手改。
6. opaque 迁移必须**保住老数据**：老的空间级主题不能因为升级而清空。

## §1（P0，核心）主题 / 音源 / 本地音乐：按客户端隔离，不再互相覆盖 —— ✅ 已完成（豆包，2026-10-06）

### 1.1 现状行为（先复现，再改）

A 账号（栖弦）提交一次主题/音源/本地曲目 → B 账号（另一个栖弦）下一个 GET 就拿到 A 的主题；B 再提交自己的主题 → 顶掉 A 的；A 的本地文件曲目（`opaque.tracks[pl_id]`）也会被回填进 B 的视图，B 侧出现打不开的本机路径。

### 1.2 根因（代码事实）

| 位置 | 事实 |
|---|---|
| `src/hub/store.py:96` | `self.opaque: dict = {}` —— **整个空间只存一份** |
| `src/hub/store.py:203` | 落盘写 `"opaque": rt.opaque` |
| `src/hub/store.py:282` | 载入读 `data.get("opaque", {})` |
| `src/hub/api.py:809-812` | 渲染栖弦时用 `rt.opaque`（空间那份）传给 `render_cyshine` |
| `src/hub/api.py:846-847` | 提交时 `if opaque and any(v is not None ...): rt.opaque = opaque`（整份覆盖空间那份） |
| `src/engine/engine.py:50` | `Client.opaque: dict` —— 引擎里**其实已经按客户端**存了一份 |
| `src/engine/engine.py:488` | `client.opaque = submission.get("opaque") or {}` |
| `src/engine/engine.py:245-246` / `:266-267` / `:297` | 该副本只用于变化检测（计入 view_hash / 抑制时间戳跳变 / 交付快照哈希） |
| `src/hub/adapters.py:57` | `parse_cyshine(payload)` 无状态、不接收客户端身份 |
| `src/hub/adapters.py:152-153` | `render_cyshine(view, meta_pool, ..., opaque, ...)` —— opaque 本来就是**参数传入** |

**结论：适配器不用改**（这就是本文件最容易被改错的地方）。要改的是"枢纽存几份、渲染取哪一份"。

### 1.3 改法（按客户端分桶，推荐）

1. `src/hub/store.py:96`：`self.opaque: dict = {}` → `self.opaque_by_client: Dict[str, dict] = {}`，键 = `cid`（即 `rt.client_for(user, dialect, device)` 的返回值）。
2. 落盘 `src/hub/store.py:203`：改存 `"opaque_by_client": rt.opaque_by_client`（**保留**写旧键 `"opaque"` 一份作为兼容快照也可以，但载入时以新键为准）。
3. 载入 `src/hub/store.py:282`：
   - 有新键 → `rt.opaque_by_client = data["opaque_by_client"]`；
   - 只有旧键 → `rt.opaque_legacy = data.get("opaque") or {}`（新增字段），**老设备读取时回退用它**，新设备从空开始；
   - 建议仿照同文件已有的自愈函数写法（`_repair_engine_fields` `:285`、`_repair_playlist_order` `:288`）新增 `_repair_opaque_fields(rt)`，把"旧键 → legacy 槽"和"缺字段补齐"集中在一处。
4. `src/hub/api.py:809-812`（GET 路径）：`cid` 已经在 `:780` 算好了，改成
   `client_opaque = rt.opaque_by_client.get(cid) or getattr(rt, "opaque_legacy", {})`，用它传给 `render_cyshine`。
5. `src/hub/api.py:846-847`（PUT 路径）：`cid` 已经在 `:839` 算好了，改成 `rt.opaque_by_client[cid] = opaque`。
   **保留**原来的 `if opaque and any(v is not None for v in opaque.values())` 判断——澜音的 `parse_ceru` 返回 `opaque=None`（`adapters.py:262`），不能让它把栖弦那份覆盖成空。
6. 语义结果：`appearance` / `musicSources` / `opaque.tracks` 全部按 `cid` 隔离 ⇒ 手机和电脑各用各的主题、各自只看到自己的本地文件。
   （如果以后想要"同一账号多设备共享主题"，只需把 `appearance`/`musicSources` 的键改成账号 `cid.split(":", 1)[0]`，`tracks` 仍按键 `cid`。**本轮不做**，用户明确选的是"各用各的"。）
7. `src/engine/engine.py` **不要动**：`client.opaque` 与 `opaque_by_client[cid]` 必须来自同一次提交、保持同值，否则会出现"变化检测认为变了、渲染却拿旧的"。

### 1.4 §1 的测试

- 兼容用例（可选但建议）：构造老格式 pkl（只有 `"opaque"` 键）→ 载入后老设备仍拿到那份主题，新客户端拿到空。

## §2（P0）确认卡：去重 + 自动关闭 + 只能点自己的 —— ✅ 已完成（豆包，2026-10-06）

### 2.1 现状（代码事实）

- 安全阀卡：`src/engine/engine.py:693-701`，`pid = new_ulid("del")`。
- never_owned 卡：`src/engine/engine.py:705-714`，同样 `pid = new_ulid("del")`。
- ⇒ **同一个现象每轮 stale echo 都会新开一张卡**（UI 里同一批删除反复出现）。
- 卡片结构：`{"space", "client", "playlists", "tracks", "created_at"[,"reason"]}` —— 只有 `client`（形如 `账号:方言[:设备]`），**没有账号字段**。
- `src/hub/api.py:617-634 _pending_delete_action`：只校验登录 + 用登录者的空间取 runtime（`:621-622`），**同一空间里任何账号都能确认/拒绝别人的卡**。
- 对照：`pending_restores` 已经按 key 合并（`src/engine/engine.py:416-431 _note_restore`，注释"同 key 合并上下文"）——照这个模式做删除卡的去重。其记录里同样**没有 client 字段**（`:421-425`）。

### 2.2 改法

1. **去重/合并**：在 `merge()` 生成卡之前，先找同一 `client` 且同一 `reason` 的未处理卡：
   - 找到 → **复用旧 `pid`**，把新的 `playlists`/`tracks` 并入（并集），只更新 `created_at`；
   - 找不到 → 新建。
2. **自动关闭**：本次提交**又带回了**卡里的条目时（歌单出现在 `sub_view`、曲目 key 重新出现），`eng.pending_deletions.pop(pid, None)` —— 用户不删了，卡应该消失。
3. **归属字段**：卡里加 `"account": cid.split(":", 1)[0]`；`_note_restore` 也补 `"client"`/`"account"`（该调用点拿得到 client）。
4. **权限**：`_pending_delete_action`（`api.py:617-634`）与 `_pending_restore_action`（`:647-655`）加校验：
   `if card.get("account") and card["account"] != user and not _is_admin(user): return JSONResponse({"error": "只能处理自己设备发起的确认卡"}, status_code=403)`。
   （`_is_admin` 已存在，`api.py:107`。）
5. 前端 `webui/src/components/PendingCard.vue` 已有 `reason` 文案分支（含 `never_owned`）；如卡片新增"发起设备/账号"字段，可在卡上多显示一行"来自：<账号>"。

## §3（P0）空间管理：能看到、能加入、不再静默新建、不再删数据 —— ✅ 已完成（豆包，2026-10-06）

### 3.1 现状（代码事实）

- 建账号时才能定空间：`src/hub/api.py:224-257`（`space = body.get("space") or name`，重名 409）；**没有任何"改已有账号空间"的路由**（当前全部路由：`/`、`/api/users` GET/POST、`/api/users/{name}` DELETE、password/rename/enabled/role PUT、`/api/playlists/*`、`/api/state`、`/api/pending-deletions|pending-restores` 的 confirm/reject、`/d/{device}/...` 与精确路径的 GET/PUT、OPTIONS/HEAD 兜底 ⇒ **没有 `/api/spaces`**）。
- 删账号时若空间没有别的账号指向它 → `src/hub/store.py:231-247 delete_space()` 把该空间的 pkl **一起删掉**（由 `api.py:260-284` 调用）。⇒ 共用空间里"最后一个人退出"会清空歌单。
- 空间索引存在于 store 内部（`_known`：`store.py:228/241/289` + `_save_index()`）。
- 前端入口已具备：`webui/src/components/AccountCenter.vue:57,64-67,151`（新增账号对话框有"空间"输入，默认跟随账号名，手改后不再跟随）、`:254`、`:285`；`webui/src/lib/api.js:22-26 createUser(token,name,password,space,role)`。

### 3.2 改法

1. 新增 `GET /api/spaces`（只读）：
   - admin → `[{space, members, playlists, revision, exists}]`；
   - 普通账号 → 只返回自己那一个空间；
   - **不返回任何歌单内容**。
2. 新增 `PUT /api/users/{name}/space`（admin 可改任何人，普通账号只能改自己；body `{"space": "..."}`）：
   - 目标空间**必须已存在**（校验 `_hub` 的空间索引），否则 404/409 + 明确文案"空间不存在；如需新建请用 /api/users 建号时指定"；
   - 换空间后若**旧空间变成没人指向**，按第 3 条处理（不要直接删）。
3. 把"孤儿空间"从"立即删除"改成"**保留 + 标记**"：
   - `api.py:260-284` 删账号流程里不再无条件 `delete_space`；默认保留数据，只在显式 `?purge=true`（或 admin 二次确认接口）时才删；
   - `delete_space` 保留但只由显式清理调用；日志里说明"空间 X 已无成员，数据保留在 `data/spaces/`"。
4. 建账号体验：`POST /api/users` 允许 `space` 指向已存在空间（行为不变），前端把"空间"输入改成"已有空间下拉 + 可输入新名字"，输入新名字时显示"将新建空间 <name>"。
5. **禁止静默新建**：`space` 为空时仍按 `name` 兜底（保持兼容），但任何"用户明确填了名字却不存在"的场景都不许悄悄建空间——走第 2 条的报错路径。
