# playlist-sync-hub 实现审查意见（FastAPI + Vue3 同步服务）

> 审查对象：`playlist-sync-hub`（`src/engine`、`src/hub`、`webui`、`plugins/ceru-webdav-sync`）
> 审查基准：本仓库 `docs/01`–`docs/11` + `docs/spec/canonical-v1.md`（**冻结设计**）与栖弦真实源码（`CyShineMusic-main/…/lib/core/sync/*`）
> 审查方式：**只读**（未改动任何实现代码）+ 真实进程内端到端复验（起 uvicorn 后走 HTTP 打 GET/PUT/MKCOL/OPTIONS/HEAD/401）
> 结论时效：2026-10-06

---

## 0. 一句话结论

**骨架是对的，主链路能跑（两端并集、删除传播、空间隔离、Basic 认证都实测通过），但 hub 门面离冻结设计还差关键一半：对栖弦的生命线语义（无基线 GET → 404）、`modifiedAt` 的确定性、本地文件曲目的 opaque 透传三条全是致命偏离，会真实丢数据；正向归因、安全阀确认通道、DAV 方法集、限流、gzip、原子落盘基本缺失或未接线。**

按当前版本直接上真机（栖弦 + 澜音插件），**大概率结果**：新设备第一次连上就把本机歌单清一次；只要手机里有一首「本地文件」歌，同步整轮失败（HTTP 400）；只要 GET 与本地编辑的时序不巧，本机未上传的新增会被远端覆盖。**建议先修 P0 七条（§3 六条 + §11.1 一条）再进 M2 真机联调。**

### 简单版：第一版只做这 5 条（其余全部延后）

下面 5 条是"能同步 + 不丢数据 + 不自毁"的下限，每条改动都不大；做完就能上真机。后面的 §4–§6、§11 全部是"以后遇到再加"。

| # | 做什么 | 为什么非做不可 | 改动量 |
|---|---|---|---|
| 1 | 无基线客户端 GET 返回 **404**（`api.py:581-608` + `engine.py:210-226`） | 否则新设备第一次连上就按"远端为空"把本机歌单清一次 | 一个分支 |
| 2 | `modifiedAt` **内容不变就不变**（`api.py:598` → `adapters.py:152,153,169`） | 否则每轮 GET 都被栖弦判成"远端更新"，覆盖本机未上传的新增 | 小（记住上次交付的渲染） |
| 3 | 本地文件曲目走 `ext.*.opaque` 透传（`adapters.py:107-135`） | 否则手机里有一首本地歌，整轮 PUT 400，同步直接断 | 约 40 行 |
| 4 | 落盘改**原子写** + 载入失败**别静默建空空间**（`store.py:132-146`、`:163-182`） | 一次崩溃就毁掉唯一数据副本，还被空空间覆盖 | 小 |
| 5 | PUT **先全量校验再落库**（`engine.py:147-171`） | 否则一个坏歌单会让 canonical 留下半截数据 | 小 |

安全侧：Basic + pbkdf2 落盘已够局域网自用；**对外必须放在 HTTPS/隧道后面**，别裸奔；**不要**加 412/304（栖弦会把非 2xx 当失败）——现在不解析条件头就是对的。

第二版再做（双端真机跑起来才会撞上）：跨方言歌单墓碑抑制（`engine.py:122-145`，否则删掉的歌单会被另一端推回来）、跨端 native id 登记（`engine.py:122-145`）、待确认队列的确认入口（`engine.py:619-681` 有逻辑、HTTP 层没路由）。

明确**第一版不做**（不是错，是过度设计）：PROPFIND、gzip、限流、ETag 当交付句柄、渲染缓存、日志/事务重放、墓碑 180 天退休与 30 天结案、正向归因、未知方言通配、413/507 配额、待确认卡 UI（队列在、日志能看就够）。

## 1. 我对这个设计的评价（架构层面，先谈方案再谈代码）

### 1.1 设计立得住的地方（我认为这是对的方向）

1. **「翻译 + 合并」收进服务端**是唯一正确解。栖弦是 section 级 LWW + `applyFromSync` 按远端整体重建、缺席即删（`docs/02:20-21`），澜音插件方只有 `list/getTracks/import`。点对点无论怎么排最终只能决定"让哪一端丢"。枢纽把双方方言翻译成 `canonical-v1` 再合并，客户端零改动——这个判断在源码层面是站得住的。
2. **每个客户端一份「交付基线」**（`base_served`）做三路合并，而不是靠文件里的时间戳猜——这是把"对端删了"和"对端还没同步"分开的唯一办法。文档 `docs/05` 的 I1/I2′ 与实现 `engine.py:391-413` 一致。
3. **删除用墓碑表达 + 删除优先 + 首次接入只增不删**（D7/D8）是"宁可少同步，不可错删除"的正确取舍；实现里有 `Tombstone`/`_crossed_deletion_point`/安全阀/挂起队列的完整形状（虽然接线不全）。
4. **一个 URL + 账号密码、账号即空间**对用户是零心智负担；`config.json` 里密码落盘用 pbkdf2（`api.py:66-84`）而不是明文，比一般自建服务讲究。
5. **未识别方言隔离、不猜**（D11）是对的谨慎。

### 1.2 设计里最脆的三处（这三点决定了"能不能真的不丢")

1. **整条链路的胜负判断仍然由栖弦客户端的 LWW 决定**。枢纽再怎么合并，只要渲染出的 `modifiedAt` 比手机本地修订新，栖弦就会 `applyFromSync` 按**远端整体重建、缺席即删**。因此 `modifiedAt` **不是展示字段，而是数据安全字段**：必须是"相对该客户端上次交付确有变化才推进"的确定性值（`docs/03:119-120`、`docs/05:97-101`）。实现里它取的是**本次墙钟**，等于把设计刻意拆掉的雷又装回去了。
2. **"无基线客户端 GET"的语义是这条链路的生死开关**。栖弦先 GET 后 PUT（`webdav_client.dart:45-48`、`webdav_sync_controller.dart:259-296`），GET 到 200 就按"云端有数据"走 LWW，GET 404 才走"以本地为准并建文件"。`docs/03:86` 已把结论写成"无基线必须 404"，实现里**根本没有 404 分支**。
3. **"删除 vs 从未同步"在栖弦文件里天然不可区分**（无 per-song 时间戳、无墓碑、采纳动作对外不可观测）。所以新设备、重装、同一路径两台设备这些场景的服务端归因（正向归因 + 安全阀 + 挂起确认）**必须实现**，不能只写在文档里。当前实现只有 revision 闸门 + 安全阀，缺正向归因（`C_new ⊂ base_served` 严格子集 + 往返无损自检）。

> 补充一个设计层的诚实评价：**协议选 WebDAV 单文件是对的妥协**（客户端零改动换来的），代价是"权威真相"不得不寄生在一个客户端能整体覆盖的文件里，所以枢纽必须精确伺候栖弦的那几条行为。这也是为什么本审查里"HTTP 语义正确性"权重很高——它不是工程洁癖，是数据安全。

## 3. P0 致命（会真丢数据 / 直接断同步，必须改）

### P0-1 无基线 GET 返回 200 + 空间全量视图 ⇒ 新设备第一次连上就清本机歌单

- **文档要求**：`docs/03:86`「对**无基线客户端**的 GET **必须返回 404**，逼它走'远端不存在 ⇒ 以本地为准 ⇒ PUT'这条路；返回空间全量视图会让它先把这台设备自己的歌单清一次」。`docs/08` R14/Q11 同。
- **现状**：`api.py:581-608` `_sync_get` 无 404 分支；`engine.py:210-226` `deliver()` 无条件推进 `base_served` 并返回 200。
- **实测**：空空间首次 GET（无 `base_served`/`base_submitted`）→ `HTTP 200`、`sections.playlists.data = []`；换一个未接入账号同样 `HTTP 200` 空文档。
- **后果**：栖弦拿到 200 后按"云端有数据"做 LWW；其 `applyFromSync` 缺席即删 ⇒ 本机歌单先被清一次，再回写一个空/子集视图 ⇒ **丢失用户歌单**。
- **修改要点**：
  1. `SyncSpace.deliver()` 增加"首次交付"判定：当该客户端**既无 `base_served` 也无 `base_submitted`**（= 从未交付也从未提交）时返回 `404`，且**不写 journal、不推进基线**；`MergeResult.status=404`。
  2. `_sync_get` 原样透传 404（响应体可为空 JSON `{"error":"not found"}`）。
  3. 触发条件要**按客户端**判定而不是"空间是否为空"——否则（a）第一台设备 PUT 之后永远拿不到 200（死循环），（b）第二台设备仍会走 200 清本地。
- **验收**：新客户端 `GET → 404`；`PUT（If-None-Match: *）→ 200`；随后 `GET → 200` 且含自己刚提交的内容；已交付过的客户端重复 GET 仍 200。

### P0-2 `modifiedAt`/`generatedAt`/歌单 `updatedAt` 取本次墙钟 ⇒ 每轮都被判"远端更新"，覆盖本机未上传新增

- **文档要求**：`docs/05:97-101`「渲染给客户端时 section 级 `modifiedAt` 取随空间 revision 单调推进的确定性值，**且仅当相对该客户端上次交付内容确有变化时才推进**；内容不变时输出**完全相同**的时间戳与字节」；`docs/03:119-120` 给出公式 `max(空间内容最后一次真变时刻, 该客户端上次交付的 modifiedAt + 1s)`；`docs/04:65`、`docs/09:158` 同。
- **现状**：`api.py:598` `generated_at = rt.engine._now()` 每次 GET 现取；`adapters.py:169` `modifiedAt = generated_at`；`:152-153` 歌单 `createdAt/updatedAt` 也填它。
- **实测**：内容完全未变，间隔 1.3 s 两次 GET → `modifiedAt 07:09:37Z → 07:09:38Z`、`generatedAt` 同步递增、**正文不同**（ETag 随整包哈希一起变）。
- **后果**：栖弦每次 GET 都判"远端更新" ⇒ 整表替换 + 必然回写（写放大）；更要命的是"本地已新增但先 GET"的未同步新增被远端覆盖（正是评审 S3 记的那条）。
- **修改要点**：
  1. 空间维护 `content_changed_at`（内容真变时更新）与每个客户端 `last_delivered_stamp`；渲染时 `modifiedAt = max(content_changed_at, last_delivered_stamp + 1s)`，**仅当相对该客户端上次交付内容有变化时才推进**；无变化 ⇒ 返回上次交付的**同一字节**（可缓存渲染结果）。
  2. `generatedAt` 同理（或干脆与 `modifiedAt` 同值）；歌单级 `createdAt/updatedAt` 用 canonical 的创建/更新时刻，**不得**用渲染时刻。
  3. ETag 语义跟着定：内容不变 ⇒ 相同正文 + 相同 ETag（同时为 Q17 的"ETag 当交付句柄"留出改造位）。
- **验收**：内容不变时连续两次 GET（间隔 >1s）→ 字节与 ETag 完全一致；内容变化后第一次 GET → `modifiedAt` 严格大于该客户端上次交付值。

### P0-3 本地文件曲目（无平台 id）导致整轮 400 ⇒ 手机里有本地音乐就永远同步不了

- **文档要求**：`spec I6`（`docs/spec/canonical-v1.md:221`）「本地音乐/文件曲目**禁止**作为一等元素进入规范文档，**但必须原样携带**：适配器放进 `ext.<client>.opaque.tracks`，渲染时原样回填」。理由写明：栖弦 `applyFromSync` 对"缺席"按删除处理，渲染时丢掉这些曲目 = 服务端**间接删除**用户的本地音乐。
- **现状**：`adapters.py:107-135` `_cyshine_track_identity` 在推不出 `(source,songId)` 时 `raise ParseError` ⇒ `_sync_put` 返回 400（`api.py:626-627`）。
- **实测**：提交 `{"musicId":"D:\\Music\\a.flac","source":"local","musicInfo":{"id":"D:\\Music\\a.flac",…}}` → **`HTTP 400 parse failed: 曲目无法确定身份 (source,songId)`**。（注：`{"source":"local","musicId":"local_9f3"}` 这种能凑出 `local:9f3` 的样本会被接受并当成 `local:9f3` 一等元素，同样不符合 I6。）
- **后果**：整轮 PUT 失败 ⇒ 栖弦看到"WebDAV 请求失败"，同步完全停摆；且这些曲目从未被携带 ⇒ 与 I6 的"原样回填"要求相悖。
- **修改要点**：
  1. `parse_cyshine` 把无法确定身份的 track 收集进 `ext.cyshine-v1.opaque.tracks`（连同 `musicId/name/singer/albumName/source/quality/picUrl/musicInfo` 原样），**不进入** `playlists[].tracks`；`source=local` 之类非平台曲目同样按 opaque 处理。
  2. `render_cyshine` 按歌单把 opaque track 回填到**原歌单**的 `tracks` 中（保序位置建议：先按上次交付位置回填，再追加新增平台曲目）。
  3. `view_hash` 计入 `ext.*.opaque`（I6/E5），但**不参与**身份与冲突判定。
- **验收**：含 1 首本地文件的栖弦文档 PUT → 200；GET 回来的该歌单里同时有平台曲目与那首本地文件（字段逐项一致）；引擎 canonical 里不出现该本地文件的 identity。

### P0-4 持久化非原子 + 载入失败静默重建空空间 ⇒ 一次崩溃/半写就是整空间数据蒸发

- **现状**：`store.py:132-146` `save()` 直接 `pickle.dump` 覆盖目标文件（无 temp+`os.replace`、无备份、无锁）；`store.py:163-182` `_load()` 捕获**所有**异常后 `return None`，`Hub.get()` 随即 `SpaceRuntime(space_id)` 建一个**空空间**并继续服务；一旦随后有 PUT，空空间会被 `save()` 覆盖回磁盘 ⇒ 旧数据不可恢复。
- **实测/旁证**：`data/spaces/space__main.pkl`（126 KB）、`space__wife.pkl`（110 KB）是唯一副本；项目**不是 git 仓库**（`git status` → `fatal: not a git repository`），没有版本或备份兜底。
- **修改要点**：
  1. 落盘改 `写 tmp 文件 → fsync → os.replace`（原子）；保留最近 N 份 `.bak`（滚动）。
  2. `_load` 失败**必须显式报错**（启动即失败 / 该空间进入只读故障态并在状态页红字提示），**禁止**静默新建空空间；把损坏文件重命名为 `space__<id>.corrupt-<ts>.pkl` 保留取证。
  3. 每空间一把 `threading.RLock`（`merge`/`save`/UI 写操作同一把），并明确"**只允许单 worker**"（`uvicorn.run(app, …)` 已是单进程，但 README 与代码要写明）。
  4. pickle 加 `{"schema_version": 1, …}` 包装，便于以后迁移。

### P0-6 跨端 native id 未登记 ⇒ 第二端拿到别人的歌单 id（可能造成重复歌单/导入错位）

- **验收**：新增用例"栖弦建单 → 澜音以同名单提交 → 澜音 GET 的 id 必须是它提交的 id；再换任一端改名不影响配对"。

## 4. P1 高（契约/功能缺失，会导致"设计里承诺的能力不存在")

### P1-1 安全阀挂起的删除**没有任何确认通道**（挂起的删除永不生效）

- 引擎 `engine.py:619-643`（`confirm_delete` / `reject_delete`）、`:645-681`（`confirm_restore` / `reject_restore`）已实现，但 `api.py` **没有任何对应路由**，`/api/state`（`api.py:480-557`）不返回 `pending_deletions/pending_restores`，webui 也没有卡片。
- 后果：`docs/05 §5.3.5`（挂起 → 状态页确认）在实现里等于不存在；用户遇到"删除量异常被暂缓"后**永远没有入口**把它执行掉。
- 修：`/api/state` 增 `pendingDeletions`/`pendingRestores`（含 kind/name/数量/创建时间/来源客户端）；新增 `POST /api/pending-deletions/{id}/confirm|reject`、`POST /api/pending-restores/{key}/confirm|reject`（`origin="ui:<user>"`，随后 `_hub.save`）；webui 加卡片 + 一键确认。

### P1-2 正向归因缺失：只有 revision 闸门 + 安全阀，就可能把"重装设备"当用户主动删除

- `docs/03 §3.5.2`/`docs/05 §5.3` 要求 removed 生效前满足：**适配器往返无损自检**（`parse(render(doc))` 与提交视图一致）+ **`C_new ⊂ base_served` 严格子集** + **提交者身份可信**。实现（`engine.py:391-423`）只有 `revision != served_revision` 闸门与阈值安全阀。

- 修：removed 生效前加三道判定，任一不满足则整批进 `pending_deletions`（不写墓碑、`revision` 不动），并在状态页标"无法归因"。
- 验收：用例"重装设备提交 7/10 首子集（低于阈值）必须进 `pending_deletions`，不得直接删"。

### P1-3 墓碑 GC 无法退休旧身份 ⇒ 墓碑堆永不回收；且新注册客户端会一直"卡住" GC

4. **`identity_verified` 的判定依据**：现在 `store.py:64` 恒 True。是否改成"该 `(账号, 路径)` 已成功交付过至少一次 ⇒ 可信"？这直接决定 D20/D21 的"墓碑压制"在真机上是否生效（若恒 True，新装的同身份客户端会被当成已越过删除点，删过的歌可能被它的旧副本复活）。
5. **同路径多设备（D10 残差）**：是否落地"每台设备在 URL 加设备段"的**可选**建议？或者先实现 Q17（ETag 当交付句柄）来自动区分？在此之前，同一账号 + 同一路径的两台栖弦 = 一个身份，小比例纯删除可能被自动执行。
6. **`ext.<client>.opaque.tracks` 的渲染位置**：本地文件曲目回填时放在歌单的什么位置？（我建议"记录上次交付位置，按位置回填；新出现的追加到末尾"，避免每次渲染顺序抖动导致无谓回写。）
7. **待清理清单要不要 ack**：澜音端只展示、无法删除。是否给"已看过的清理项"做已读标记（否则清单会长期显示它从未见过的条目）？
8. **是否需要实现 PROPFIND/HEAD 的完整语义**：栖弦不用；将来接别的客户端（AList 兼容生态）才需要。现在只给明确 405/501 是否可接受？

### 多设备改造裁决（2026-10-06，见《多设备同步改造方案.md》）

- **P1-2 正向归因**被 R1 取代为更强判据：删除只在"这台设备自己提交过（`base_served ∩ base_submitted`）而本次缺席"时成立——封死"别人加的内容被误判删除"（M1）。

### 12.2 唯一剩下的真问题：删除被"删不掉的那一端"推回（致命，必修）

复现（两端同一账号/空间，实测）：
1. 栖弦有歌单 P（含 `tx2`），澜音插件也导入过 P（它本地同样有 `tx2`）。
2. 栖弦删掉 `tx2` → 澜音 GET 后确实看不到了（待清理清单出现 `tx2`）✅
3. 澜音下一轮 PUT **仍把 `tx2` 带上**（插件无法删除本地副本，只能原样提交）→ 栖弦 GET：**`tx2` 又回来了** ❌

歌单同理：栖弦删掉「澜音单」→ 澜音再提交本地仍保留的同名歌单 → 栖弦侧歌单复活（实测新 canonical id，`pendingRestores=0`）。

原因：`engine.py` 的 `_crossed_deletion_point()` 判定"身份可信 + 已越过删除点 ⇒ 视为**显式恢复**、清墓碑"；但澜音在这个场景里是**被迫重加**（它删不掉），并不是用户想恢复。

最小修法（改动很小，且 UI 已就绪）：
- `_crossed_deletion_point()` 对**无删除能力**的客户端（`client.can_delete is False`，澜音即此类）直接返回 `False` ⇒ 它的重加走"墓碑压制"，保持删除，并写入 `pending_restores` 出"待确认恢复"卡（`POST /api/pending-restores/{key}/confirm|reject` 与 `webui/src/components/PendingCard.vue` 都已存在，不用新写）。
- 验收：上述 1–3 步后，栖弦 GET **仍不含** `tx2`，且 `/api/state` 的 `pendingRestores` 有该条；点"确认恢复"后才回来。
