# 第十二轮修复记录 · 删除被复活（洛雪删掉的歌又回到栖弦）

- 日期：2026-10-08
- 报告人：用户（m04824）「这个网页端发现 lx 删除是成功了的，但是栖弦拉取时好像又拉去回来了，
  但是只是在日志里面有显示合并提交，实际好像并没有合并上去，而且栖弦里同步后这首歌还在」
- 影响：洛雪里删除的歌在栖弦里删不掉；越过冷静期后枢纽还把这次回推当成"显式恢复"，
  把已删的歌重新入列置顶（rev 21），等于**撤销了用户的删除**。
- 结论：**一处根因**（交付时间戳被"视图未变"短路，客户端因此判定远端没更新），
  配套一处 D21 确认水位的漏项（还在回推残留的客户端被算成"看过即采纳"）。已在 `docs/09` 记为 **D31**。

用户看到的"日志里有合并提交却没生效"，就是 09:12:15 / 09:12:32 那两次被压制的提交。

## 2. 真因

`src/engine/engine.py` 的 `_next_stamp()`：只在"本次交付视图 == 该客户端上次交付视图"时短路，
原样返回上次的戳（为了内容不变时字节全同、避免写放大）。

栖弦**加歌走的是 PUT，不更新交付基线**——它的 `base_served` 还是"加歌之前"那次 GET 的内容。
于是这首歌被别端删掉之后，它拿到的交付视图**恰好回到了**它上次拿到的那份 ⇒ 短路生效，
返回旧戳 `2026-10-08T09:03:19.522Z`。

栖弦的同步语义是 section 级 LWW：**远端 modifiedAt 更大才采纳**（`sync_models.dart`）。
它本地声明 `09:11:08.398Z` > 旧戳 ⇒ 判定"远端没更新" ⇒ **从不应用这次删除**，
本地副本一直在，每轮同步把这条推回来（每轮都被墓碑压制，看起来"合并不生效"）。

压制期间 `acked` 每轮被撤销；但 `_crossed_deletion_point()`（显式恢复）只看
"交付水位 ≥ 墓碑创建 revision ∧ 越过 120s 冷静期"。09:15:58 那次拉取把交付水位推到 20，
09:16:01 已越过冷静期 ⇒ 这次回推被判定为**用户"删了又加"** ⇒ 清墓碑 + 重新入列置顶。

## 3. 修复（两处，同一判据）

1. **交付戳**：新增 `_submission_matches(client, view)`；`_next_stamp()` 短路条件改为
   `same_view and same_opaque and self._submission_matches(client, view)`。
   即"内容没变"必须同时满足：相对上次**交付**没变 **且** 客户端**手上那份**（它上次提交声明的视图）
   与本次交付一致。只比对客户端**声明过**的歌单（没提交过的不影响判据，避免每轮推戳的写放大）。
2. **确认水位（D21 原文的后半句）**：`deliver()` 记 ack 时跳过 `key ∈ t.carried` 的客户端；
   `_gc_tombstones()` 跳过 `carried` 非空的墓碑。"还在回推残留"≠"看过即采纳"，
   否则它一被记 ack 就可能凑齐全员确认 → 墓碑被 GC 收走 → 下一次回推成了**无墓碑的普通重加**（同样是复活）。

顺带：`merge()` / `_adopt_initial()` 的 `added_tracks` 不再把被墓碑压制的键算成"新增"
（真机日志里那句"合并提交 +N 曲"就是这么来的，排查时会误导）。

## 5. 教训

1. **"内容没变"必须两面都看**：只看"我们交付的没变"，漏掉"客户端手上那份和我们不一样"。
   后者的典型来源：PUT 不更新交付基线、墓碑压制、R1 的 `never_owned`、安全阀 `withheld`、I2′ `suspects`。
2. **"看过即采纳"是错的**：整段覆盖客户端 GET 之后本地可能仍然保留副本，下一轮照样推回来；
   ack 必须是"看过删除后视图 ∧ 未再回推"（D21 原文如此，实现漏了后半句）。
3. **日志文案要可信**：被压制的键记成"新增"会让人以为合并成功只是没下发。
4. **冷静期不是安全网**：120s 之后，残留回推会被当成用户意图——它只能挡住"刚删完就回推"，
   挡不住"设备一直没采纳"。
5. **测试基建也会骗人**：HTTP 测试端口是 `18xxx + PID%100`，本机 18787 上常驻 DSH 的
   billion-context 代理 ⇒ 整卷跑必挂一批用例、单跑却全绿，连续几轮被误判成"端口抖动"。
   改成向系统要空闲端口后整卷一次全绿（147 passed）。
6. **先复算再改代码**：现场 pkl 只读复算（`same_view` / `_submission_matches` / 新旧戳）
   直接指认了根因，也直接证明了修复后栖弦会采纳——比再加一层机制划算。
