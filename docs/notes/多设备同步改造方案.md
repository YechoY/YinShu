# 多设备同步改造方案

> 目标读者：负责改代码的下游 AI + 用户本人。
> 本文只回答一个问题：**要让"几个手机、手机＋电脑、电脑＋电脑"都能同步，枢纽（playlist-sync-hub）还要改什么。**
> 文中所有代码锚点都指向 `playlist-sync-hub/` 下真实文件与行号（改动前请先 `read` 复核，行号可能因其它改动位移）。

---

## 0. 结论速览

| 场景 | 今天的实际状态 | 要不要改 |
|---|---|---|
| 手机（栖弦）↔ 电脑（澜音插件） | **能用**。方言不同 ⇒ 天然是两个客户端 | 不改 |
| 几个手机（都是栖弦） | **有真丢数据的路径**（见 §2 M1）。共享一个客户端身份，一台手机"没采纳"的内容会被另一台判成"被删除" | **必须改（P0）** |
| 电脑 ↔ 电脑（都跑澜音插件） | 同上（同方言共享身份），另外插件侧可以零配置给每台电脑一个设备名 | **必须改（P0 + 插件小改）** |
| 换机 / 重装 / 恢复旧配置 | 设备身份若不区分，会被当"老设备回来了"⇒ 旧基线还在 ⇒ 一次全量缺席=大批删除（安全阀会拦住大的） | 改（P1，设备页退休旧设备） |
| 手机 ↔ 电脑 ↔ 手机 混合 | 上线的组合，P0 做完即可 | —— |

**一句话结论**：多设备的第一障碍是**客户端身份**（`账号:方言`），第二障碍是**"缺席即删除"这个判据本身对栖弦这种"整段覆盖"客户端不成立**。第二点比第一点更危险，而且**只把身份拆开并不能修好它**（原因见 §2 M1 的时间线）。真正要落的是：① 每台设备一个身份；② 删除声明的资格水位改成"这台设备自己提交过的东西"，而不是"枢纽交给过它的东西"；③ 保留/补强保护闸门。

### 先澄清一个常见误解：接入 ≠ 分得清

"同账号的任何设备不都接入了这个枢纽吗？"——**是的，接入从来不是问题**：

| 能力 | 今天 | 说明 |
|---|---|---|
| 同账号设备接入同一空间、看同一份 canonical | ✅ 已具备 | `api.py:691-693` 从 `_users[user]["space"]` 取空间，所有同账号设备共享 |
| 内容（新增歌曲/歌单、改名、顺序）双向同步 | ✅ 已具备 | 并集合并，不依赖设备身份 |
| 删除判定、删除确认、`opaque` 按设备区分 | ❌ **做不到** | 身份是 `账号:方言`（§1.1），同方言设备被当成**一台**设备 |

枢纽看到的是"**栖弦手机来了一次**"，而不是"**手机 A 来了一次**"；同一个账号下的三台手机在前台只有一个名字。于是"交付基线 / 墓碑确认 / appearance·本地文件"这三样本来属于单台设备的东西全被叠在一起（§2 M1/M2/M4）。所以本方案改的不是"怎么接入"，而是"**接入之后怎么分得清**"。

## 1. 现状：身份、基线、删除是怎么判的

### 1.1 客户端身份 = `账号:方言`（同方言多设备直接撞车）

```python
# src/hub/store.py:62-74
def client_for(self, account: str, dialect: str) -> str:
    """同一账号+同一方言 = 一个客户端（D10 残差：无 Client-Id 无法区分多台设备）。"""
    cid = f"{account}:{dialect}"
```

调用点只有两处，都不带任何设备信息：

- `src/hub/api.py:693`（GET）`cid = rt.client_for(user, dialect)`
- `src/hub/api.py:749`（PUT）`cid = rt.client_for(user, dialect)`

所以：两个手机都是 `cyshine-v1` ⇒ 同 `cid` ⇒ **共用同一个 `Client` 对象**（同一个 `base_served` 交付基线、同一个 `base_submitted`、同一个墓碑 ack 集合）。两台澜音电脑同理（`ceru-plugin`）。

路由本身也是写死的两条精确路径，没有设备段的位置：

```python
# src/hub/api.py:664-683
@app.get("/CyShineMusic/sync-v1.json")   # 栖弦固定路径
@app.get("/ceru/sync-v1.json")           # 澜音插件固定路径
```

### 1.3 墓碑确认与 GC 是按 `client_id` 记的

```python

```

身份合并以后，**一台设备的确认等于替所有同方言设备确认**（M2）。

## 2. 多设备下的具体失效（每个都有可复现时间线）

### M1（严重·会真丢数据）一台手机"没采纳"的新增，被另一台手机判成"已删除"

前提：两台手机 A、B，都是栖弦，同一个账号。**栖弦的一轮同步是"先 GET、再按 section 级 LWW 决定写不写回"**（`docs/03 §3.5.1`；栖弦侧 `lib/core/sync/webdav_sync_controller.dart:271-288`），而且栖弦**任何歌单改动都会把自己的 playlists 段 `modifiedAt` 顶到 now，并在 2 秒后自动跑一轮同步**（`webdav_sync_controller.dart:13` `_uploadDebounce = 2s`、`:361-373`）：

1. B 在手机上加了歌 `s`，PUT ⇒ 枢纽 canonical 有 `s`，`revision = R+1`。
2. A 在手机上改了任意歌单（哪怕只是换个顺序/加一首别的）⇒ A 本地 playlists 段 `modifiedAt = T_A = now`（比枢纽交付给它的 stamp 新）。
3. A 的自动同步开始：**先 GET**。这一步就地把共享的 `base_served` 推进成"包含 `s`"的视图（`engine.py:280-299`），并令 `bsrv.served_revision = R+1`。
4. A 拿 `T_A` 与云端 stamp 比，自己更新 ⇒ 栖弦选择**保留自己的整段**（里面没有 `s`），PUT 回来。
5. 枢纽做差集：`base_view`（刚交付给 A 的、含 `s`）− A 的提交（不含 `s`）⇒ **`s` 被当成 A 的删除**。
6. 闸门为什么没拦住：`self.revision (R+1) == bsrv.served_revision (R+1)` ⇒ **I2′ 不触发**（是 A 自己刚 GET 过）；单曲删除又达不到安全阀阈值 ⇒ 直接写墓碑、全局删除。
7. 结果：B 的 `s` 从云端消失；B 下轮拉取发现线上没有 ⇒ 栖弦按 `playlist_store.dart:227 applyFromSync` 整单重建，`s` 在 B 的手机上也没了。**两台手机都丢，且没有任何确认卡。**

歌单级同理：A 的整段里缺了 B 新建的歌单 ⇒ 整张歌单被全局删除（安全阀要求"≥2 张且≥50%"才拦，单张溜过去）。

> **关键提醒：这个 M1 不是"身份没拆开"造成的，拆开身份也修不好。**
> 因为第 3 步的 GET 是 A 自己发的，枢纽在 A 提交前**已经把 `s` 交付给 A 了**——"交付过"≠"采纳了"。所以除了身份，还必须改判据本身（见 §3.2 规则 R1）。

**已复现（2026-10-05，只读脚本，未改任何代码）**：`tmp/repro_multi_device.py`（用**两个不同身份** `acct:cyshine-v1:d-a` / `:d-b` 模拟两台手机）：

```
1) A 首次接入 : 201    2) B 首次接入 : 201
3) B 加歌 s   : {'pl_…': ['tx:s','tx:t1']}      云端有 s : True
4) A 先 GET   : 200    A.base_served  = {…: ['tx:s','tx:t1']}
                       A.base_submitted= {…: ['tx:t1']}
5) A stale PUT: status=200 removed_tracks={'pl_…': ['tx:s']}
6) 云端还有 s : False ⇒ *** 丢了（M1 复现）***    墓碑: {'tx:s': 'track'}
R1 owned(A)   : ['tx:t1']    ⇒ s 不在 owned ⇒ 不判删除（修复方向成立）
```

⇒ **结论坐实**：把身份拆开**仍然会丢**（第 5 步照旧写墓碑），必须同时改判据；R1 的 `owned = base_served ∩ base_submitted` 在这一轨迹上正好把 `s` 排除。把这个脚本扩成 `tests/engine/` 的正式用例（含 M1-a/b/c）是 P0 的一部分。

### M2（严重·删除被推回/被提前回收）一台设备的确认替另一台确认

墓碑确认按 `client_id` 记（§1.3）。身份共享时：

- 栖弦 A、B 共享身份。一处删除产生墓碑后，A 的 GET 就把它 ack 了 ⇒ `_gc_tombstones()`（`engine.py:739-759`）认为"所有活着的客户端都见过了" ⇒ 墓碑被回收。
- 而 B 本地可能还没采纳（它上轮同步失败/还没跑），下一轮 B 提交时又带着这首歌 ⇒ 此时**墓碑已经没了**，压制失效 ⇒ 删除被推回。这正是单机场景 S15 的教训（`修改意见.md §12.2`），多设备下会以"另一台手机"的形式复发。

### M3（重要）换机/重装/恢复旧配置 ⇒ 一次"全量缺席"

设备身份区分后，如果用户**沿用同一个身份**（恢复了旧配置/迁移了插件存储），旧 `base_served`/`base_submitted` 还在，而新机器上是空库或旧库 ⇒ 一次性大批缺席 ⇒ 变成大批删除。安全阀能拦住"≥2 张歌单且≥50%"或"单歌单≥50% 且≥N 首"，但小改动仍可能落地。需要设备页支持"退休旧设备/换新身份"。

### M4（重要·串味）`opaque` 是空间级

两台手机的 appearance/musicSources/本地文件曲目互相覆盖（§1.4）。表现为：B 的栖弦界面主题被 A 改掉；更糟的是 A 的**本地文件曲目**会被渲染进 B 的视图，B 可能把 `D:\...\x.flac` 这类只存在于 A 的条目导入自己的库。

### M5（轻）顺序抖动

`engine.py:586-609` 的排序传播规则是"集合一致且顺序不同就按提交方重排，并 `sort_tag += 1`、推进 stamp"。多设备各自持有不同顺序时，可能来回重排、反复触发对端拉取。目前只有"集合完全一致才整体重排"这一条约束，多设备下要补一条"只有提交方集合相对它自己上次提交发生了变化（即真的动过顺序）才传播"。

### 已经不需要改的（避免重复劳动）

- **手机删歌 → 电脑跟着删**：链路已通（手机删 ⇒ 墓碑 ⇒ 澜音端渲染成"待清理"，因为澜音 SDK 没有删歌 API，`docs/09 D22`/`m00234` 约束）。
- **电脑删歌 → 手机跟着删**：澜音用户在澜音 App 里删掉歌 ⇒ 插件下次提交缺它 ⇒ 枢纽写墓碑 ⇒ 手机拉取时栖弦把它删掉。**自动、无需确认**，符合 D22。
- **手机 ↔ 电脑内容同步**：不同方言、不同身份，今天就能用。

## 3. 目标设计（三层）

```
第 1 层  设备身份    每台设备一个 client_id ← 账号 + 方言 + 设备标识（路径段 / Client-Id 头 / ETag 句柄）
第 2 层  基线语义    base_served（交付水位，用于并发闸门与 GC）
                     base_submitted（拥有水位，用于判"这是不是删除"）★ 本方案的核心改动
第 3 层  保护闸门    I2′ 并发闸门 + 安全阀 + 他端新交付保护窗 + 待确认卡（D22 例外通道）
```

### 3.1 第 1 层：设备身份

规范早已写好，只是没实现：

- `docs/03:143`：`client_key = (账号/空间, 请求路径, User-Agent 家族)`，并承认为 D10 残差。
- `docs/04:50`：`clientIdentity(path, ua, headers) → {path_part, device_part, ua_family}`，"**必须能区分同一 App 的两台设备**（优先 `Client-Id` 头；缺失则枢纽签发并在路径中固定）"。
- `docs/08 Q17`：**用 ETag 当"交付句柄"**——栖弦写回时必带 `If-Match: <上次 GET 的 ETag>`（`webdav_client.dart:83`、`webdav_sync_controller.dart:288`），若枢纽每次交付发唯一 ETag，则该 ETag 即"哪一次交付"= 基线句柄，**客户端零改动、用户零配置**。代价：与"内容不变 ⇒ ETag 不变"（PF4）冲突；首次接入走 `If-None-Match: *`（`createOnly`）时无句柄；AList 忽略 `If-Match`，所以必须由我们的门面自己签发校验。
- `docs/10 M5`：URL 规范化会**丢弃 query** ⇒ 不能用 `?cid=`，设备身份只能走**路径段 + `Client-Id` 头**。

三种落地手段对比：

| 手段 | 谁需要配合 | 用户操作 | 评价 |
|---|---|---|---|
| **A. 路径设备段** `http://host:8000/d/phone-b` | 只改枢纽（新增路由） | 每台设备在 WebDAV 地址里加一段 | **P0 推荐**。栖弦的路径是 `{用户填的 baseUrl}/CyShineMusic/sync-v1.json`（`docs/03:143`），加一段天然可用；MKCOL 已被 `api.py:802-808` 通配 201 接管，不会挡 |
| **B. `Client-Id`/`X-Hub-Device` 头** | 我们的澜音插件改一行（生成 UUID 存插件存储，随请求头发送） | 零配置（电脑） | **P0 推荐给电脑**；栖弦不发头，救不了手机 |
| **C. Q17 ETag 交付句柄** | 只改枢纽 | 零配置（所有端） | **P2**。最优雅但牵扯 ETag 语义与 `createOnly` 特例，先做 A+B，再单独验证 C |

实现要点（A+B 并存，优先级：头 > 路径段 > 兜底）：

```python
# src/hub/store.py:62  改为
def client_for(self, account: str, dialect: str, device: str | None = None) -> str:
    did = device or "default"                 # 兜底：无设备标识时退化为今天的行为
    cid = f"{account}:{dialect}:{did}"
```

```python
# src/hub/api.py:664-683  保留原两条精确路由（向后兼容），新增带设备段的等价路由
@app.get("/d/{device}/CyShineMusic/sync-v1.json")
@app.put("/d/{device}/CyShineMusic/sync-v1.json")
@app.get("/d/{device}/ceru/sync-v1.json")
@app.put("/d/{device}/ceru/sync-v1.json")
# device 交给 clientIdentity(path, ua, headers) 归一化（限 [A-Za-z0-9_-]{1,32}），
# 头 X-Hub-Device 优先于路径段。
```

**不要**顺手把 `identity_verified` 改成"没有设备段就不受信"（`docs/11:75` 的建议）——`identity_verified` 参与了"显式恢复 vs 墓碑压制"的判定（`engine.py:396-413`），一改就会让**默认单设备用户**"删了又想加回来"从直接生效变成弹恢复卡。这是行为变更，要么维持 `identity_verified=True`（`store.py:71` 现状：密码认证过的空间成员即受信），要么单独立项并写清取舍。

### 3.2 第 2 层：删除判据（本方案的核心）

**规则 R1（必须）**：删除只在"**这台设备自己曾经提交过**该条目，而这次提交里没有"时成立。

```python
# src/engine/engine.py:492-504 改为（等价伪代码）
owned = base_served.view ∩ base_submitted      # 该设备"真的拥有过"的内容 = 交付过 且 自己提交过
removed_pl = set(owned.keys()) - set(view.keys())
removed_t[pl] = set(owned.get(pl, {}).get("tracks", ())) - set(view[pl]["tracks"])
```

为什么这条规则能同时修掉 M1 又保住单设备语义：

- M1 里 A 从没提交过 `s`（`s` 是 B 加的）⇒ `s ∉ owned` ⇒ **不判删除**，只做并集 ⇒ 不丢。
- 单设备/真删除：A 自己上次提交里有 `s`（`base_submitted` 有），这次没有 ⇒ **照常判删除** ⇒ D22"删了就删了"不退化。
- 澜音端同理：用户在澜音 App 里删歌 ⇒ 上次提交里有、这次没有 ⇒ 正常删。
- 唯一的"更保守"边界：某设备**采纳过但从没提交过**就删掉了 ⇒ 不再直接判删除，落进 suspects/待确认（D22 允许的"无法归因"例外）。这比丢数据好。

> 这一条把 `engine.py:8/48/631` 的注释（"base_submitted 仅审计，不用于判删除"）**反转**。改的时候必须同步改这三处注释与 `docs/05` 里对应的描述，否则下一个人会按旧注释把它改回去。

**规则 R2（必须，与 R1 配套）**：`base_served` 继续只干两件事——I2′ 并发闸门（`engine.py:509`）和墓碑 GC 水位（`engine.py:754`），**不再作为删除判据的单独来源**。

## 5. 迁移与兼容（别让老空间"删除功能停摆"）

现有 `data/spaces/space__*.pkl` 里 client key 是 `账号:方言`。新代码给每个 `cid` 加一段设备名，会产生一批**全新 client**；新 client 走 `_adopt_initial`（`engine.py:668`）＝**只增不删**。若不处理，老用户升级后"删除不再生效"，会被当成新 bug。

做法（二选一，推荐第 1 种）：

1. **别名继承**：老 key `acct:dialect` 落成一个特殊设备 `default`。若请求没带设备标识 ⇒ 仍然映射到 `default` ⇒ 老客户端行为与今天完全一致（零变化）；带设备标识的新设备才新建 client。首次接入的新设备走"只增不删"建基线（正确语义）。
2. 状态页给出一次性提示："检测到旧基线属于 `未命名设备`，若这是手机 A，请把它的地址改为 `.../d/phone-a`"并支持**设备合并/改名**（把 `default` 的 `base_served`/`base_submitted`/`acked` 迁移到目标设备）。

另外：`Hub._repair_engine_fields`（`store.py:241`）这类"老 pkl 补字段"的钩子要顺手给新字段（设备标识、交付时间）补默认值，避免读到老 pkl 抛属性错。
