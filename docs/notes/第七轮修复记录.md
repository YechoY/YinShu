## 事故 1：澜音 2.2.1 被误报"澜音版本过低"

**现象**：插件日志 `澜音版本过低：自动删除需要 2.2.1 及以上，请升级澜音后再同步（已跳过删除）`，状态栏 `2 首跳过删除`；同时在枢纽侧表现为把远端已删曲目回写、要求手动确认。

**根因（能力探测写法与宿主上报格式不一致）**
- 宿主 `CeruMusic/src/main/services/plugin/manager/PluginHost.ts:72-84` 的 `SERVICE_CAPABILITIES.library.methods` 是
  `['playlists.list','playlists.getTracks','playlists.import','playlists.removeTracks','playlists.clearPlaylist']`
  —— **不带 `library.` 服务前缀**；`:917-924` 的 `services.capabilities.*` 把它**原样**返回。
- 插件旧写法用 `m.endsWith('.playlists.removeTracks')` / `m.endsWith('.import')` 判定：`.import`（末段无点）碰巧为真，
  只有删除路径恒 false ⇒ 2.2.1 被错判成"宿主太老"。宿主只在**插件调用**时用 `library.playlists.removeTracks` 这种带前缀的名字。

**修法（插件 0.3.2）** `plugins/ceru-webdav-sync/src/index.js`
```js
function hasHostMethod(methods, name) {
  if (!Array.isArray(methods)) return false
  return methods.some((m) => typeof m === 'string' && (m === name || m.endsWith('.' + name)))
}
```
`ensureLibraryAccess`（`playlists.import`）与 `hardDeleteCapable`（`playlists.removeTracks`）都改用它；
能力确实缺失时日志会打印宿主实际上报的 `methods` 列表，便于下次一眼看出是不是探测问题。

## 事故 2：栖弦往「Yes」加的 5 首，被澜音设备的整段 PUT 带走

**取证**（只读，脚本在 `tmp/inspect_engine3.py` / `tmp/inspect_del.py` / `tmp/trace_del.py`）
- `data/spaces/space__test.pkl`：墓碑 `[13]` 由 `test:ceru-plugin:ceru-3eccdu` 在 `2026-10-08T07:14:19.692Z` 删除 5 首：
  `tx:001J8wR61ayNXI`、`tx:001iJcCp1q0kej`、`tx:001wl0By0P1oYH`、`tx:001xBIY10BKWLP`、`tx:003dttLk4gGkv1`。
- 这 5 首是栖弦先加、「Yes」歌单交付给澜音设备后，澜音本地没有它们（没导入成功）⇒ 该设备整段提交时自然缺席。

**根因** `src/engine/engine.py:732-743`（第三轮"同空间成员设备互信"引入）
```python
no_pl = set(never_owned_pl)          # base_served - base_submitted - cur 的缺席
if client.can_delete:                # ← 罪魁：能删本地 ≠ 缺席就是删除意图
    removed_pl |= never_owned_pl
    removed_t[pl] |= keys
```
`never_owned` = "枢纽交付过、这台设备**从未提交过**"的键。把它当删除，等于"我这台设备看不到/放不进它 ⇒ 全世界都删掉"。

**修法（引擎）**：`never_owned` 缺席**永不写墓碑**，只保留在 `meta["never_owned"]` 供排查；
I2′ 并发轮次仍并入 `suspects`（不误删，也不静默丢弃信息）。`meta["never_owned_applied"]` 恒为 `False`（字段仅为兼容保留）。
只有 **owned**（`base_served ∩ base_submitted`）的缺席才表达删除意图——即"我自己提交过、这次没有"。

**行为影响**：澜音删掉**自己导入并提交过**的歌（插件流程 `GET#1 → 导入 → PUT` 会把导入的歌提交上去，所以是 owned）依旧自动传播；
"从没提交过的歌"不再被删 —— 这正是这次数据丢失的根因。

## 附带修复：新增曲目置顶（用户拍板 m02307）

`engine.py:850-864`：把"本轮新增的曲目整体挪到歌单最顶部"从**新增循环之后**移到**排序同步段之后**
（`if set(cur_live) == set(desired) and desired and desired != cur_live: pl_.track_ids = desired`）。
原因：集合相等时排序同步会把整单改写成提交顺序，放在它前面会被覆盖（第一次改动无效的原因）。
