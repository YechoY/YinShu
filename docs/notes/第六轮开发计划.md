### 1.3 注册表字段（骨架）

```python
@dataclass(frozen=True)
class RenderContext:
    view: dict
    meta_pool: dict
    native_ids: dict
    pending_cleanup: Optional[list]
    opaque: dict
    opaque_tracks: Optional[dict]
    revision: int
    generated_at: str
    playlist_times: dict          # {pl_id: {"created_at":…, "updated_at":…}}

@dataclass(frozen=True)
class Dialect:
    name: str                     # "cyshine-v1" —— 引擎/存储里用的稳定 id，不许改
    roots: tuple                  # 路径第一段白名单，如 ("CyShineMusic",)
    files: tuple                  # 文件名，如 ("sync-v1.json",)
    parse: Callable               # (payload) -> (submission, meta_delta, opaque, warnings)
    render: Callable              # (ctx: RenderContext) -> dict
    capabilities: dict            # 见 §2.6
    empty_view_on_no_baseline: bool = False
    file_fallback: bool = False   # 见 §1.4
```

## §2 任务包 B：洛雪（lx-x）客户端适配器

### 2.1 客户端与样例文件事实（实测，别猜）

样例：`D:\Alist\music\lx-x-playlists.json`（洛雪经 WebDAV 同步上来的真实文件）

- 137,005 字节、**单行** JSON；顶层键 `version / lastModified / data`；`version = "2"`（字符串）、`lastModified = 1791284114614`（epoch 毫秒）。
- `data` 是 4 个数组：`defaultList`、`loveList`、`userList`、`tempList`（样例里分别是 0 / 0 / 1 / 0 个）。
- `userList[0]` = `{name, id, origin, locationUpdateTime, list}`：`name="合并歌单"`、`id="userlist_1789448083655"`、`origin="created"`、`locationUpdateTime=null`、`list` 235 首。
- 曲目：`{id, name, singer, source, interval, meta:{...}}`；`interval` 形如 `"03:55"`；顶层 `id` 形如 `tx_002xEHdK35q6Qp`（`source_平台ID`）；`meta` 常见键 `songId / strMediaMid / albumName / albumId / picUrl / qualitys / _qualitys`（**必须容忍未知键**，样例里出现过 `types/_types/_full/songmid/vid`）。
- 音源分布：tx 200 / wy 15 / kg 10 / kw 10；**不要用纯数字 id 做身份**（跨音源会撞车，见工作区 `LX澜音歌单对比工具\README.md:34-40`）。
- 身份校验（我在真文件上统计过）：顶层 `id` 去掉 `source_` 前缀的字符串，**234/235** 等于 `meta.strMediaMid`、**1/235** 等于 `meta.songmid`；该文件里没有 `hash/copyrightId`。

### 2.2 身份映射规则（`parse_lx`）

```
platform_id = 顶层 id 以 "<source>_" 开头时 → 去掉该前缀
             否则 → meta.strMediaMid || meta.songId || meta.songmid || meta.hash || meta.copyrightId
source      = song.source || meta.source        # source 也可能只在 meta 里
```
理由：顶层 `id` 就是**洛雪自己的身份**（`source_平台ID`），用它当 canonical `(source, songId)`，235/235 可还原、渲染回写也最省事；与官方洛雪导入插件 `CeruMusic-Plugin-Template-fork\plugins\ceru.lx-playlist-import\plugin.js:2480-2488` 的字段优先序（hash→songmid→copyrightId→songId）在**那 1 首 tx 曲目**上会取到不同 id —— 记为已知差异（§2.8），联调时确认。

- 无法确定 `source` 或 id 的曲目：**不许丢**，按 I6 原样进 `opaque["tracks"][native_id]`（照 `src/hub/adapters.py:111-117` cyshine 的做法），渲染时回填。
- 非白名单音源（`wy/tx/kw/kg/mg` 之外，例如本地文件 / 其它插件）：同上走 opaque，只计数 + `warnings`。
- `meta_delta[identity_key(source, songId)]` 写：`title`（`name || title`）、`singer`、`album`（`meta.albumName`）、`duration_ms`（`interval` → 毫秒）、`quality`（`qualitys/_qualitys` 里最高一档）、`pic_url`（`meta.picUrl`），另存两个**洛雪专用**字段供回写：`lx_num_id`（`meta.id`，为 0 时不写）、`lx_str_media_mid`、`lx_song_id`。缺失字段不覆盖已有值（沿用 cyshine 的 `if v is not None and k not in merged` 写法）。
- `interval` 解析：照官方 `plugin.js:2471-2479`，`split(":")` 最多 3 段、每段数字 → `total*60+秒` ×1000。

### 2.3 线格式（提交 / 交付都由我们定，洛雪不用改）

- **提交（PUT）**：就是洛雪原文件的外形 —— `{"version":"2","lastModified":<int>,"data":{defaultList,loveList,tempList,userList}}`。
- **交付（GET）**：同外形，`data.userList` = 枢纽合并结果；歌单对象写 `{name, id, origin, locationUpdateTime, list}`。
  - `id` = 该歌单在本客户端的 `native_id`（首次提交时写入 `store.native_ids("lx-x")`；枢纽新建的歌单没有 native_id → 用枢纽 id，并允许洛雪下次提交时换回它自己的 id）。
  - 只写洛雪认识的键；**不加额外的顶层/曲目键**（避免它校验失败）。
  - `lastModified`：写"引擎 stamp 的 epoch 毫秒"（`generated_at` 是 ISO8601，需转换）；**内容不变则同值**（保持既有的"确定性交付"约定）。
- 曲目回写：`{"id": f"{source}_{pid}", "name": title, "singer": "、".join(artists), "source": source, "interval": "mm:ss"（≥1 小时写 h:mm:ss）, "meta": {"songId": <lx_song_id 或 pid>, "strMediaMid": <lx_str_media_mid 或 pid>, "albumName":…, "albumId":…, "picUrl":…, "id": <lx_num_id 或 0>, "qualitys":[{"type": <最高档>}]}}`。

### 2.4 三张"非歌单"列表：走 opaque，不进合并（**关键**）

`defaultList`（默认列表）、`loveList`（我喜欢）、`tempList`（试听/临时）**不参与歌单合并**：按客户端分桶存进 `opaque_by_client[cid]`（D23），渲染时原样还给**同一台客户端**。

- 提交侧：`parse_lx` 的第 3 个返回值 `opaque = {"lx_lists": {"defaultList":…, "loveList":…, "tempList":…}}`；
  `src/hub/api.py:2009-2012` 已经会把非空 `opaque` 落到 `rt.opaque_by_client[cid]`。
- 交付侧：`src/hub/api.py:1962-1969` 已实现"按客户端取桶"，`render_lx` 读 `ctx.opaque` 原样输出；空/缺失时输出 `[]`。
- 理由：这三张表是"本机个人数据"，一旦进合并会被别人的空值清空（和澜音主题/音源同一类问题）。

### 2.5 歌单身份与顺序

- `native_id = str(userList[i].id)`（如 `userlist_1789448083655`）；`name` 参与同步，允许重名（枢纽侧已支持）。
- 曲目顺序按 `list` 原样（枢纽保留顺序）。
- `origin`/`locationUpdateTime`：原样透传；枢纽新建的歌单给 `origin="created"`、`locationUpdateTime=null`（这两个字段不参与合并，见 `AGENTS.md` 里栖弦的同类结论）。

### 2.6 能力表

```python
CAPABILITIES["lx-x"] = {"delete_track": True, "delete_playlist": True,
                        "create_playlist": True, "reorder": False}
```

理由与前提：洛雪提交的是**整份**歌单文件（每个歌单都带完整 `list`），"缺席即删除"在语义上成立，与 D26（澜音按可删处理）同一逻辑。**若联调发现洛雪只上报增量/局部歌单，回退方式是一行**：`delete_track/delete_playlist` 改回 `False`（此时被删内容只会进交付里的 `cleanup` 提示，不会自动删本地）。
`reorder=False`：洛雪文件里没有可用的顺序变更信号，保守。

### 2.7 路由

- 注册 `roots=("lx-x",)`、`files=("lx-x-playlists.json",)`、`file_fallback=True`（§1.4）。
- 于是三种地址都可用：`<枢纽>/lx-x/lx-x-playlists.json`、`<枢纽>/<任意目录>/lx-x-playlists.json`（兜底）、以及带设备段的 `<枢纽>/d/<设备名>/…`。

### 2.8 已知有损点（写进 `docs/`，别偷偷丢）

1. `qualitys` 只保留最高一档，`size`/`sizeBytes` 丢弃（澜音侧同一取舍）。
2. `meta.id` 为 0 的 35 首歌单曲目（真实文件里存在）回写仍是 0。
3. `_qualitys`/`types`/`_types`/`_full`/`vid` 等杂键不回写。
4. 与官方洛雪导入插件的字段优先序在那 1 首 tx 曲目上不一致（§2.2），可能导致"同一首歌在澜音/洛雪两个客户端里算两条"。
5. 若 `userList[].list` 里同一 `(source, songId)` 出现多次：保留首次出现的顺序位置（照 cyshine 的既有做法）。

### 2.9 测试（`tests/hub/test_adapters_lx.py`，或用例并入 `test_adapters.py`）

## §3 任务包 C：设备身份（多设备 / 多端同账号）

### 3.1 为什么必须做（会真丢数据）

枢纽的删除判据 R1 是"这台设备自己提交过、这次却没有"（`owned = base_served ∩ base_submitted`）。两台同类设备若**不报设备名**，在枢纽看来是同一个客户端、共用一份基线：平板没同步过"手机刚加的歌"时，那首歌在平板这次的提交里缺席 → 被判成删除。

### 3.2 枢纽侧已经支持（不要重复实现）

- `src/hub/api.py:1793-1805 client_identity(path_device, x_hub_device)`：**头 `X-Hub-Device` 优先，其次 URL 里的 `/d/{设备名}/`**；非法名抛"设备标识非法（限 `[A-Za-z0-9_-]{1,32}`）"，路由层 400。
- `src/hub/api.py:1808-1813 _resolve_device`、`src/hub/store.py:105-126 client_for(account, dialect, device)` → cid `{account}:{dialect}:{device}`（不报设备名退化为 `default`，老空间沿用旧 key）。
- 同一账号、不同方言本来就是两个 client；**所以本轮客户端侧只需"报设备名"这一件事**。

### 3.3 澜音插件 B：两件事（**去回落** + **加设备头**）

#### 3.3.0 去掉"待清理清单"的三类回落（用户 m01476 拍板：客户端该升级，不是我们适配）

现状（0.3.1）：`hardDeleteCapable` 返回 false / 宿主太旧 / 未授权 / `notFound` → 被删内容进 `deletions.view` 待清理清单（`plugins\ceru-webdav-sync\src\index.js:930-990`），让用户手动删。**这三类全部去掉**，改成"说清原因，让用户去升级/授权"：

| 情况 | 新行为（不再列手动清理清单） |
|---|---|
| 宿主没有 `playlists.removeTracks`（老澜音） | 状态栏 + 日志：**"澜音版本过低：自动删除需要 2.2.1 及以上，请升级澜音后再同步"**；同步其余部分照常 |
| 未授权 `library.delete` | 首次仍弹一次授权；拒绝后状态栏：**"未授权删除，已跳过删除（可在插件设置里重新授权）"** |
| 调用了但 `notFound` / 抛错 | 视为**异常**（说明 `(providerId,id)` 与本地行对不上，属真 bug）：日志 + 状态栏报"删除未匹配到本地曲目，请上报"；不做手动清理 |

实现要求：

- `hardDeleteCapable` 的返回值从 `bool` 改成带原因的枚举，如 `{ok:true}` / `{ok:false, reason:'host-too-old' | 'not-granted'}`；同步主流程按 `reason` 出中文提示。
- 单曲类条目**不再写入** `deletions`（待清理清单只保留"整歌单删除"这一种，原因见下）。清单为空时沿用既有的"无待清理"分支。
- **数据后果（写进 README「关键不变量」）**：删不掉的歌会**留在澜音本地**，插件**绝不写回云端**（沿用既有"不复活"语义）⇒ 不会撤销云端删除；下次同步会重试删除。
- **保留不动**：整歌单删除时宿主没有"删歌单本体"的 API（`PluginHost.ts:75-84` 只有 `clearPlaylist`），这不属于本次要移除的三类，仍按现状提示。若以后要去掉，单独一轮。
- 测试：现有 3 条回落用例（老宿主 / 未授权 / `notFound` → 进待清理）**按新语义改写**为"不进清理清单 + 状态栏/日志给出明确原因"。**原断言锁的是"老宿主可用性"兼容，新语义是用户拍板不要该兼容** —— 这属于需求变更，不是放宽断言；改的时候在汇报里写明这一点。
- 跑 `npm test`（改动后必须全绿，条数不允许减少）。

#### 3.3.1 加 `X-Hub-Device` 设备头

## §4 任务包 D：栖弦 Y "听枢纽裁决"（枢纽模式）—— 需用户拍板

### 4.1 要解决的两个问题

1. **栖弦的 section 级 LWW 会丢掉枢纽的删除结果**：`sync_models.dart:120-127 newerSyncSection` 比 `modifiedAt`（本地=设备墙钟毫秒）；枢纽交付的 `modifiedAt` 只保证"比自己上次交付大 1 秒"，打不过设备墙钟 → 栖弦认为本地更新，整段丢弃远端并回推残留。
2. **纯 GET 的设备永远不 ack 墓碑**：`webdav_sync_controller.dart:286` 在"合并结果与远端相同"时直接 return，不 PUT；而枢纽的墓碑确认（ack）只发生在 merge 里 → 墓碑只增不减，被删的歌可能被永久压制/反复回推。

### 4.2 改动点（都在 `CyShineMusic-Y\lib\core\sync\`）

- 新增设置 `webdav_sync_mode_v1`：`mirror`（默认，现状，用于自建云盘）/ `hub`（连枢纽）。
- `webdav_sync_controller.dart:273-286`：`hub` 模式下**不再跑 `newerSyncSection`**，直接把远端快照当权威（`_applyRemoteSections(local, remote.snapshot)`），再把本地视图整份 PUT 一次（即使 `_sameSnapshotData` 为真也 PUT，用于 ack 墓碑）。
- `sync_models.dart` **不改**（保留 `sync-v1.json` 外形）。理由：栖弦的 `appearance`/`musicSources` 两节在枢纽里是按客户端分桶的 opaque（D23），canonical 格式没有对应位置，换成枢纽格式只会重写模型、收益为零。
- 不做（明确划界）：不改加密、不改目录结构、不动 `appearance/musicSources` 的内容语义。

### 4.3 验收

- `flutter analyze` 干净；有测试就 `flutter test`。
- 三端联调（两组栖弦 + 一个澜音，同账号）：A 删歌 → B 拉到后本地也删；B 再同步不会把歌推回来；枢纽 `scripts/hub/inspect_space.py` 显示墓碑最终被 GC 收走。

> **拍板项**：D 会改用户自己的栖弦 fork（Flutter 工程）。若用户想先只做 A/B/C，D 留到下一轮 —— 此时"多设备不误删"已经成立，只是"栖弦删歌传播"仍受限。
