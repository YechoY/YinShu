# 第八轮修复记录（两个真机事故）

日期：2026-10-08 · 触发人：真机自测 · 影响面：澜音插件 0.3.2 → 0.3.3、枢纽合并引擎

用户在网页端手动删掉 4 首曲子，再用澜音插件同步，结果是：

1. 插件日志报 `ctx.library.playlists.removeTracks is not a function`，4 首**没有**从澜音本地歌单删掉；
2. 插件每轮把整份本地视图（含那 4 首）重新 PUT 上来，枢纽把"试图复活墓碑条目"逐条挂成**「待确认恢复」卡**，网页端反复要求人工裁决。

两个事故是独立的，各修一处。

---

## 事故一 · 澜音插件调用了一个不存在的 API

### 事实（有源码依据）

| 位置 | 结论 |
|---|---|
| `@shiqianjiang/ceru-plugin-sdk` 0.3.12 `dist/library.d.ts` LibraryAPI | 插件只能 `ctx.library.playlists.list / getTracks / import` —— **没有删除** |
| 同包 `dist/services.d.ts` `HOST_SERVICE_METHODS` | 服务白名单里**根本没有 library 条目**，删除类只有 `queue.remove`、`favorites.remove` |
| `CeruMusic/src/main/services/plugin/manager/PluginHost.ts:80` | 能力表里**有** `playlists.removeTracks`，`:885-900` 也确实会分派 |
| `CeruMusic/src/renderer/src/components/PluginHostBridge.vue:292…385` | 那个分派是**渲染层/应用自身 UI 桥**用的，没有暴露给插件 |

也就是说：**宿主能力表声明 ≠ 插件能用**。`ctx.capabilities.get('library')` 说 `playlists.removeTracks` 存在，但插件 `ctx` 上没有这个函数，照它调用只会抛异常。

### 改动（`plugins/ceru-webdav-sync/src/index.js`）

- `hardDeleteCapable()` 改为**以函数是否存在为准**：
  `typeof ctx?.library?.playlists?.removeTracks !== 'function'` → 直接跳过删除，并按能力表声明区分原因：
  - 能力表说没有 → `host-too-old`（旧宿主文案）；
  - 能力表说有但函数没有 → 新原因 **`no-api`**（当前澜音未向插件开放删除接口），日志同时打印"宿主能力表声明：有"。
  授权判定（`ctx.permissions.query`）保持不变，只在函数确实存在后才问。
- 状态栏新增一条口径：`当前澜音未开放删除接口/未授权，已不再回写`。
- 顺带把 `hasHostMethod()` 的 `.endsWith('.' + name)` 兼容逻辑保留下来（能力名带不带 `library.` 前缀都能识别）。

### 但"删不掉"本身不能靠插件解决

澜音 2.2.1 就是没有给插件删除能力，插件**无法**从本地歌单里移除一首歌。能做的只有：**不把枢纽已经删掉的曲目再写回去**。

## 事故二 · "本地删不掉就别回写"（插件侧）

### 机理

本地删不掉 → 插件每轮提交仍带着这 4 首 → 引擎看到"墓碑条目的键重新出现" → 走墓碑压制 + 待确认恢复卡 → 网页端永远弹卡。

### 改动（`plugins/ceru-webdav-sync/src/index.js`）

新增存储键 **`hub-deleted.v1`**：`{ endpoint, marks: { 歌单名: { 曲目键: 标记时间 } } }`

- `refreshHubDeleted()`：只有同时满足下面四条才**新建**标记 —— ① 上次交付（`last-view.v2`）里有这个键 ② 上次提交（`prev-submit.v1`）带过这个键 ③ 本轮交付里没有它 ④ 本地歌单里还有它。
  ⇒ 这正好等价于"枢纽侧已接受删除、而本地删不掉"。
- 键一旦在本轮交付里重新出现，或本地已经没有了 → **自动清除标记**（一旦以后澜音开放删除接口，不会留下永久黑洞）。
- 标记按 `serverUrl + \u0001 + username` 绑定 endpoint：**换地址或换账号即整体作废**，不会把 A 账号的删除意图套到 B 账号上。
- `buildLocalSubmission(operation, excluded)` 按标记把曲目从 PUT 里剔除，计数进 `summary.withheld`；状态栏显示 `${withheld} 首已在其他设备删除（本地删不掉，已不再回写）`。
- 只有 `canHardDelete.ok === false` 时才计算这套标记（真能删的宿主不受影响）。

### 效果

- 网页端不再因为澜音回写而弹「待确认恢复」；
- 澜音本地那几首仍在（这是宿主限制，插件无解），但**不会再把删除复活**；
- 状态栏明确告诉用户还有几首"本地删不掉、已停止回写"。

## 事故三 · 枢纽侧恢复卡开关根本没生效（撞名）

### 机理

第四轮把恢复卡开关做成引擎实例字段 `confirm_restore`，而 `SyncSpace` 上**有个同名方法** `confirm_restore(key)`（确认恢复通道）。于是：

- 旧 pkl 里没有这个实例属性 → `store._repair_engine_fields` 的 `hasattr(engine, "confirm_restore")` 摸到的是**绑定方法，恒为真** → 默认值 `False` 永远补不上 → `_note_restore` 里 `if not self.confirm_restore: return` 拿到真值、**不 return** → 恢复卡照旧产生；
- 反过来，如果实例真写入了 bool，又会**遮住方法** → `POST /api/pending-restores/{key}/confirm` 调 `eng.confirm_restore(key)` 会报 `'bool' object is not callable`；
- 另外 `_apply_engine_policy()` 只在 `configure()` 时对**已加载**的空间生效，`test` 这种按需加载的空间永远吃不到 policy。

### 改动

- `src/engine/engine.py`：字段改名 **`restore_cards_enabled`**（`_note_restore` 守卫同步改），方法名 `confirm_restore` 不动（对外契约）。
- `src/hub/store.py`：`_repair_engine_fields` 先清掉遗留的同名 bool，再补 `restore_cards_enabled = False`；`Hub` 新增 `policy_hook`，`Hub.get()` / `Hub.probe()` 拿到运行时后立刻 `_apply_policy(rt)`。
- `src/hub/api.py`：新增 `_apply_engine_policy_to(eng)`（清遗留同名 bool → 套 `restore_cards_enabled` / `trusted_direct_delete` / `restore_grace_seconds`），`configure()` 里把 `_hub.policy_hook` 指过去。
- 配置键仍叫 `policy.confirm_restore`（`config.json` 里没有这个键 ⇒ 默认 `False`）；前端与确认端点契约不变。

### 只读验证（`tmp/check_restore_policy.py`，不写盘）

对 `data/spaces/space__test.pkl`：实例里**根本没有** `confirm_restore` 属性（`hasattr` 只能摸到绑定方法 ⇒ 旧逻辑必然补不上默认值），`pending_restores` 落盘 0 条；修复后无遗留 bool、`restore_cards_enabled = False`、`callable(eng.confirm_restore) = True`、`trusted_direct_delete = True` ⇒ PASS。

## 生效条件（必须做，否则改动不生效）

1. **重启枢纽**：引擎/存储的改动要重新加载模块，`127.0.0.1:8000` 上那个进程（`.venv\Scripts\python.exe -m src.hub.run_fastapi`）必须重启。
2. **重装插件**：把 `plugins/ceru-webdav-sync/release/plugin.js`（0.3.3）装回澜音；澜音的插件缓存不会自动用新制品。

## 自测口径（见 `plugins/ceru-webdav-sync/TESTING.md` T4/T5）

1. 网页端删掉几首歌 → 网页端**不再**出现「待确认恢复」卡（revision 变化、日志显示"缺席仅记录"）。
2. 澜音插件同步 → 状态栏出现 `N 首已在其他设备删除（本地删不掉，已不再回写）`；日志**不应**再出现 `removeTracks is not a function`；`storage` 里出现 `hub-deleted.v1`。
3. 网页端再同步：那几首不会被澜音写回来。

## 已知限制（不可绕）

- 澜音 2.2.1（含 SDK 0.3.12）**没有给插件任何删除 API** → 插件无法自动删掉澜音本地歌单里的歌，只能"标记 + 不回写"。
- **整个歌单**的删除仍只能手动在澜音里删。
- 需要澜音官方把 `playlists.removeTracks` 真正接进插件 SDK（`SUBMISSION.md` 已作为反馈项记录）。

## 事故三 · 栖弦首次提交时，新加的歌被放到歌单最底下（当天下午真机）

用户报告（原文）：**「我刚刚用栖弦合并了一次，怎么栖弦新增的歌曲反而在最底下呢」**。

### 事实（有落盘依据）

- 栖弦客户端 `Yecho:cyshine-v1:default` 在 `2026-10-08T08:03:34Z` 做了**它自己的第一次 PUT**（此前只有 GET/deliver，`base_submitted is None`）⇒ 引擎走 `SyncSpace._adopt_initial()`，journal 里 `"adopted": true`。
- `space__main.pkl`（revision 14）里歌单 `pl_5W5224YFNAK62ND5JVYW0PNSSN`（「Yes」）共 253 首，用户新加的 5 首落在 **#249–#253**：`千年 - 云汐`、`轮回之境 - 封茗囧菌`、`轮回之境 - CRITTY`、`雨落江南巷 - 风华音纪、叶里`、`沦陷 - 白允y`。
- 原因：第七轮"新增曲目置顶"（`docs/notes/第七轮修复记录.md:50`，用户拍板 m02307）只写在 `merge()` 主路径；`_adopt_initial()` 这条**首次接入**通道漏了，新曲目按 `_append_to_playlist` 追加到末尾。
- 栖弦侧按 section 级 LWW（`newerSyncSection(local, remote)`）整段 PUT；枢纽随后用 `_next_stamp`（`engine.py:311-342`，取 `max(content_changed_at, order_changed_at)`、打不过提交声明就 +1ms）把顺序推回各端 ⇒ 用户在所有端都看到"新歌在最底下"。

### 改动

- `src/engine/engine.py` `_adopt_initial()`：与 `merge()` 同款置顶段——记录本次新增的 `tr_id`（`added_head`），循环后 `pl_.track_ids = head + [tid for tid in pl_.track_ids if tid not in head_set]`；仍然**只增不删**（不写墓碑、不误删他人曲目）。
- `tests/engine/test_merge_engine.py` 新增 `test_08b_first_adoption_new_tracks_to_head`。
- 一次性验证 `tmp/verify_adopt_order.py`：15 项全过（真机场景复刻、空空间、正常合并回归、纯重排、首次接入仍不删）。

### 现场数据处置（用户同意后执行）

`tmp/reorder_five_to_head.py` 把上述 5 首按**原提交顺序**挪到顶部（调用引擎自己的 `reorder_tracks`，与网页端上移同一条路径）：`revision` 保持 14、`sort_tag` 5→6、无墓碑变化、总量仍 253；落盘后回读磁盘 + 栖弦方言渲染双重复核，交付视图 `#1–#5` 即这 5 首，`modifiedAt = 2026-10-08T08:09:20.667Z`（压过客户端提交声明，各端下次同步即拉取）。

### 顺带修掉的坑

- `Hub.save()` 原先在"运行时未加载到内存"时**静默 return**：维护脚本用 `Hub.probe()`（只读、**不登记** `_runtimes`）拿到空间再 `save()`，会"打印成功但一个字节都没写"。现改为显式 `KeyError`；`api` 层所有调用点都是 `Hub.get()` + `save()`，行为不变（`tmp/verify_no_confirm_http.py` 12/12 复验）。
- 重启前发现 `:8000` 上**同时有两个枢纽进程在监听**（两个内存副本会互相覆盖 pkl）——已全部杀掉，现只保留一个。

### 生效条件

重启枢纽（引擎改动）+ 各端同步一次（拉取新顺序）。
