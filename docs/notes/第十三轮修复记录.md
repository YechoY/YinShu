  枢纽既不出墓碑、也不出确认卡，歌单一直挂在云端；栖弦每轮拉取又把它带回来，看起来"删不掉"。

  已在 `docs/09` 记为 **D32**；改动=歌单级对可信客户端放松为 `owned_pl = base_served`（3 行），客户端零改动。

## 2. 真因

`src/engine/engine.py:747-752`（改动前）：

```python
if full_view:                      # full_view_submit：整份替换方言（洛雪的 D30 放松）
    owned_pl = set(base_keys)
else:
    owned_pl = base_keys & set(sub_view.keys())    # ← 栖弦走这里
```

加上 `:815-822` 的"never_owned 缺席永不判删"，得到：**交付过、但从未提交过的歌单永远删不掉**。

而栖弦的歌单**新增**为什么永远进不了 `base_submitted`：

1. `CyShineMusic-Y/lib/features/playlists/playlist_store.dart:227-280 applyFromSync()`：
   远端 section 胜出时 `state = List.unmodifiable(restored)`——**整份替换本地歌单**（歌单集合变成远端集合）；
2. `CyShineMusic-Y/lib/core/sync/webdav_sync_controller.dart:259-296 _syncOnce()`：
   该轮结束前 `:286 if (_sameSnapshotData(merged, remote.snapshot)) return;`——远端全胜、本地没别的变化时
   **直接返回、根本不上传**（只 `_saveSnapshotRevisions` 记下远端戳）；
3. 于是栖弦"看到了这张歌单、本地也有、但一次都没提交过它"；
4. 用户在栖弦里删掉它 → 下一轮本地节 `modifiedAt = now` → 整份 PUT（缺这张歌单）→ 缺席落进 never_owned。

栖弦的 `sections.playlists` 本身是**整份**导出：`playlist_store.dart:214-225 exportForSync()`
`for (final playlist in state)`，无任何过滤 ⇒ "交付过、这次没提交"对歌单就等价于"这台设备上它没了"。

## 6. 教训

1. **"交付过"和"提交过"之间的差，在整份替换型客户端上是常态，不是异常**——远端胜出那轮它压根不上传。
   凡是用 `∩ base_submitted` 做判据的地方，都要问一句"这个水位对这种客户端会不会永远是空的"。
2. **放松要分层看**：歌单级放松 ≠ 曲目级放松。曲目级误删会全局清歌（D28 的事故），歌单级误删只丢一张歌单、
   曲目仍在库里、可由别端重新提交 + 冷静期显式恢复 ⇒ 两者的风险差一个量级，判据不必相同。
3. **边界必须有用例钉住**：放松的适用面（可信 vs 不可信、交付过 vs 没交付过）各写一条，"没交付过不算删除"这条尤其容易被顺手改坏。
4. **现场数据和原始 PUT 落盘是最硬的证据**：`base_served` 里"有"不代表客户端本地"有"，
   8 份原始 PUT 全是 2 张歌单，才把"它从未上报过"钉死。
5. **修完要问"下一次上报何时发生"**：客户端的提交是事件驱动的（本地变化才写），
   所以有些现场不一致只能补登一次，不能只等自然收敛。
6. **被 policy 管的引擎字段，测试里只能改 policy**：`Hub.get()` 每次都通过 `policy_hook`
   按 `_policy` 重设 `restore_grace_seconds`/`confirm_delete`/`trusted_direct_delete` 等，
   直接写 engine 属性会在下一次请求被冲掉——第十轮踩过一次（`test_api_http.py:486-490` 有注释），
   第十三轮发现 `test_12` 里那行同样失效了，**一个设置静默失效，测试会"空跑通过"很久**，
   要等行为真的改变时才以"回归"的形式暴露出来。
