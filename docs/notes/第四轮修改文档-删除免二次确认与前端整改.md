## §2 删除语义改造（用户拍板：同空间编辑者删除**不需要**二次验证）

### 2.1 用户的原话与场景

> 「已经用两台栖弦两个账户一个空间测试过了，就是删除有问题，但是豆包也修了，新增没问题，我觉得既然是归属于一个空间，且都有编辑权利，那么就没必要再做二次验证了，麻烦的很」

场景：**一个空间、两个账号、两台栖弦，双方都是 editor**。期望：谁删都直接生效；谁想加回来也直接生效；**不要弹"待确认删除/待确认恢复"**。对应产品的语义是"同一空间内的编辑操作互相完全信任"。

但"完全信任"直接实现会退回到第一轮的故障：**A 删掉一首歌，B 的陈旧副本又把它推回来（删了又回来）**。所以本轮的真正任务不是"删掉确认按钮"，而是**找到一个既能免确认、又不会自我翻转的判据**。

### 2.2 现状为什么会出问题（两处根因，都必须修）

**根因 A：枢纽交付的 `modifiedAt` 打不过客户端本地值 ⇒ 删除在设备侧不生效，被反复回推。**
- 栖弦的合并是 section 级时间比较（`CyShineMusic-main/CyShineMusic-main/lib/core/sync/sync_models.dart:120-127`）：
  `if (local.modifiedAt.isAfter(remote.modifiedAt)) return local;` —— 本地时间戳更大就**整段丢弃枢纽版本**。
- 客户端本地 `modifiedAt = DateTime.now()`（设备墙钟，**毫秒**精度）：`webdav_sync_controller.dart:367`、`:397`。
- 枢纽交付的 `modifiedAt` 来自引擎 `stamp`（`src/engine/engine.py:259-279 _next_stamp`），只保证"比**上次交付给这个客户端**的值大 1 秒"，而且 `_now()` 是**秒级截断**（`%Y-%m-%dT%H:%M:%SZ`）。
- 于是：只要设备时钟快一点，或客户端的本地改动与枢纽的内容变更落在**同一秒**（客户端的 `.500Z` > 枢纽的 `.000Z`），栖弦就判定"本地更新"⇒ **枢纽的删除视图被丢弃**，歌还在本地 ⇒ 下一轮 PUT 又把它带回来。
- 而且枢纽**根本看不到**客户端声明的 `modifiedAt`：`src/hub/adapters.py:57 parse_cyshine` 只返回 `(submission, meta_delta, opaque, warnings)`，时间戳被丢掉；`_sync_put` 调 `rt.merge(cid, dialect, submission, meta_delta, now=None)`（`api.py:1969`）也没有它。
- **这就是"删除有问题"的头号嫌疑**，也是第三轮之后必须弹恢复卡的直接原因。

**根因 B：墓碑确认只认"提交"，而栖弦"无变化时不 PUT" ⇒ 墓碑在正常场景下永远收不走。**
- 第三轮把 `deliver()` 的 ack 去掉了（`engine.py:300-309`），确认只能来自 merge 的"提交视图不再携带该键"（`engine.py:734-742`）。
- 但栖弦在"合并结果 == 远端"时**根本不写回**：`webdav_sync_controller.dart:286 if (_sameSnapshotData(merged, remote.snapshot)) return;`。即：一台**已经同步好、从不本地改动**的设备，拉取到删除后的视图、本地也应用了删除，却**永远不会 PUT** ⇒ 永远无法 ack。
- 叠加"纯 GET 设备（`retired=False`）"和 D21 的"墓碑不按时间判据"，结果是**墓碑只增不减**：内存/每次 merge 的遍历开销持续上涨，而所有"加回来"的操作都被永久压制。
- 引擎里那条自述注释（`engine.py:736-737`）说"栖弦 GET 后本地可能仍保留副本"——**归因不准**：栖弦是整段覆盖（缺席即删除），它保留副本的真实原因就是**根因 A**（时间戳比不过）。修掉 A，B 就不成立；B 不修，A 修好也会被"永不 ack"卡住。

### 2.3 目标语义（一句话）

> **"已经看过这次删除结果"的客户端，再把它提交回来 = 用户主动恢复，直接生效；没看过的（陈旧残留）一律压制。**
> 全程无人工确认卡。

这个判据同时满足两件事：
- 不翻转：陈旧副本（`served_revision < 墓碑创建时的 revision`）永远压制 ⇒ 不会"删了又回来"；
- 不阻塞：任何真实设备只要同步过一次（看过删除结果），用户再加回来就直接生效 ⇒ 不需要卡片。

#### 2.4.2 【P0-B】墓碑确认 = "已交付删除后视图" ∧ "当前没有回推"

改 `Tombstone`（`src/engine/canonical.py:84-98`）的语义：`acked` 含义保持"已交付/已确认该删除"，但**加一个反向集合**：

1. `deliver()`（`engine.py:281-309`）：对**每个存活墓碑**，若其键**不在**本次交付的视图里，则 `t.acked.add(client_id)`（**恢复**第三轮删掉的行为；注释要改成"看过删除后视图"）。
2. merge 的确认段（`engine.py:734-742`）：
   ```python
   for key, t in self.tombstones.items():
       carried = (key in view) if t.element == "playlist" else (key in submitted_keys)
       if carried:
           t.carried.add(client_id); t.acked.discard(client_id)   # 还在回推 → 不算确认
   ```

3. `_gc_tombstones()`（`engine.py:869-887`）：把条件恢复成**简单版**（`now_clients` 全部 `cid in t.acked`），但因为有第 2 步，**回推者会把自己从 acked 移除**，粘性不变：

#### 2.4.3 【P0-C】恢复判据：去掉"只有删除发起者本人能恢复"

`_crossed_deletion_point`（`engine.py:411-434`）改为：
```python
def _crossed_deletion_point(self, client: Client, t: Optional[Tombstone]) -> bool:
    if t is None:
        return False
    if not client.identity_verified or client.retired:
        return False
    if not client.can_delete:          # 澜音（deleteTrack=False）不具备可信删除/恢复表达
        return False
    bsrv = client.base_served
    if bsrv is None:
        return False
    # ① 必须"看过这次删除的结果"（交付水位越过墓碑创建时的 revision）
    if bsrv.served_revision < t.created_at_revision:
        return False
    # ② 冷静期：删除刚发生后的一小段时间内的回推仍按残留压制（防同一轮竞态抖动）
    if self._age_seconds(t.deleted_at) < type(self).RESTORE_GRACE_SECONDS:
        return False
    return True                        # ③ 删除 origin-only 限制（engine.py:432-433）
```
