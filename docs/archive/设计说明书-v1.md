## 1. 一句话与验收口径

**一句话**：在两端之间放一个自己写的同步服务，它伪装成 WebDAV 网盘（客户端只改地址、不改代码），内部用统一格式 `canonical-v1` + 每平台适配器 + 服务端合并，维护唯一事实。

**验收口径**（来自 Yecho）：

| # | 要求 |
|---|---|
| V1 | 任一端**新增/删除歌曲或歌单**，另一端在分钟级内跟随 |
| V2 | 两端**各自都有增删**时自动合并，**不丢数据** |
| V3 | 顺序冲突、属性冲突、新设备"不复活"**不在**验收范围内（但设计上顺手解决了一部分） |
| V4 | 手机端"分钟级"= **打开栖弦 / 切回前台即同步**（决策 D1，零额外耗电） |
| V5 | **通用接入**：任何支持 WebDAV 的音乐客户端，填 **一个 URL + 一组账号密码** 即可与同一账号下的其它客户端双向同步——**不依赖任何插件、不改客户端代码**（决策 D9–D11，见 §17） |

## 2. 现状与问题根因

现在两端共用云端一份 `sync-v1.json`：

| 现状 | 结果 |
|---|---|
| 云端只有"最终状态"，没有历史、没有基线 | **"对端没有这首歌"无法区分"他删了"还是"他还没同步"** ⇒ 整段覆盖型丢数据 |
| 栖弦的合并是 section 级 LWW（`newerSyncSection`）+ 按歌单 id 整条重建（`applyFromSync`） | 它写回时会把对端新增**整段覆盖掉** |
| 澜音插件替栖弦签 `playlists.modifiedAt = now` | 让桌面端"永远更新"，把胜负交给两个设备的墙上时钟 |
| AList 忽略 `If-Match` | 栖弦的 412 重试是**死代码**，并发保护实际不存在 |
| AList 实测在 ~108 KB 处把 PUT 写截断 | 文件越大越危险 |

**结论**：靠"让两端互相兼容"永远做不成——每加一个平台，就要改所有已有平台。必须把合并搬到一个中立的中间件里。

## 3. 架构

```
┌─ 客户端层（栖弦 / 澜音插件 / 将来 LX）── 只认 WebDAV，只改地址 ─┐
└───────────────┬──────────────────────────────┬────────────────┘
                │ WebDAV 请求                   │
┌───────────────▼──────────────────────────────▼────────────────┐
│ ① 门面层 WebDAV Facade                                          │
│   OPTIONS HEAD GET PUT PROPFIND MKCOL DELETE MOVE               │
│   Basic 认证 · ETag · If-Match / If-None-Match（真生效）· gzip  │
│   路由：URL 路径 → 适配器（路径即"方言开关"）                    │
├────────────────────────────────────────────────────────────────┤
│ ② 适配器层（每平台一个，互不感知）                               │
│   parse(原生 payload) → 客户端视图 → 规范模型                    │
│   render(规范模型) → 原生 payload（带回该端的 native id）        │
│   能力声明：删歌 / 建歌单 / PROPFIND / 多文件 / 体积上限          │
├────────────────────────────────────────────────────────────────┤
│ ③ 核心层                                                        │
│   合并引擎（每客户端基线差分）· 身份映射 · 墓碑与 GC ·           │
│   冲突策略 · 安全阀 · 审计日志                                   │
├────────────────────────────────────────────────────────────────┤
│ ④ 存储层 SQLite                                                 │
│   规范状态 · 平台身份映射 · 每客户端基线 · 客户端自有 section ·   │
│   审计日志                                                       │
└────────────────────────────────────────────────────────────────┘
```

**职责边界（不可越界）**

| 组件 | 可以做 | 禁止做 |
|---|---|---|
| 门面 | 协议、认证、缓存、条件写、压缩 | 理解业务语义 |
| 适配器 | 翻译、字段归一、身份解析、能力声明 | **实现合并逻辑**、直接改规范状态 |
| 合并引擎 | 判定增删改、落墓碑、记日志 | 理解任何客户端格式 |
| 客户端 | 继续用自己的格式与自己的 LWW | 不需要、也不被要求改代码 |

## 4. 部署形态：新服务与 AList 怎么共处

### 4.1 先澄清 `/dav` 的疑问

> "AList 启动的是 WebDAV 网盘就必须以 /dav 路径开头啊"

**不是协议要求，是 AList 自己的路由前缀。** AList 默认把 WebDAV 挂在 `/dav`，仅此而已。两个事实：

1. **WebDAV 客户端填的是完整 URL**（`https://主机[:端口]/任意路径`）。栖弦和澜音插件都允许填任意 URL（含路径与端口）——现在填 `https://yechoy.cn/dav/music`，只是因为 AList 在那。
2. **新服务是另一个程序、另一个端口**，它的 WebDAV 根路径由我们自己定（`/`、`/sync/`、`/music/` 都行）。所以"新服务必须在 `/dav` 下"这个前提不成立。

### 4.2 两种共处方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **并存**（推荐，D2） | 隧道把 `/dav/*` 继续给 AList，把 `/sync/*` 给新服务（或新服务用另一端口 / 子域名） | 互不影响；随时把两端地址切回 AList 回退 | 两端的同步地址要各改一次 |
| **替代** | 让 AList 让出 `/dav/music`（改它的路由或停掉它的 WebDAV），新服务接管这个前缀 | 两端地址完全不用动 | 没有平滑回退路径 |

**首轮建议**：AList 一行不动；新服务先跑在 `http://127.0.0.1:8787`，真机阶段通过现有隧道暴露 `/sync/*`（或临时用 `http://<局域网IP>:8787`，连同一 WiFi 就能测）。确认稳定后再决定是否替代。

### 4.3 部署组件

| 组件 | 说明 |
|---|---|
| 服务进程 | 单进程；建议注册为开机自启（Windows 服务/计划任务） |
| 数据 | SQLite 单文件（WAL 模式）+ 每日备份 |
| 入口 | 现有内网穿透 → `https://yechoy.cn/sync/…`；HTTP Basic 认证（独立账号，不复用 AList 凭据） |
| 监听 | 默认只绑定 `127.0.0.1:8787`，由隧道转发，不直接暴露 |
| 回退开关 | 两端把地址改回 AList URL 即可；服务端无需改动 |

## 5. 一次同步的完整时序

### 5.1 栖弦（零改动）

```
① GET /sync/cyshine/sync-v1.json
   服务端：读规范状态 → 用 cyshine 适配器渲染
           playlists.modifiedAt = 「栖弦自己上次上报的值」（绝不用 now）
   栖弦：section LWW
        · 它没有新改动 → 平局比内容哈希 → 远端胜 → 采纳我们的合并结果
        · 它刚改过     → 本地胜 → 随后把本地视图 PUT 上来
② PUT 同一路径（body = 它本地全量视图）
   服务端：parse → 与「它上次上报的视图 P_prev」差分 → 增量落到规范状态
           → 保存 P 为新基线 → 返回 200 + 新 ETag
```

### 5.2 澜音插件（M1 零改动；M2 可选改 hub 模式）

```
① GET → 拿到服务端渲染的同格式 payload → 导入缺失歌曲（宿主 import）
② PUT（原子写：PUT .tmp → 校验 → MOVE 覆盖）
   服务端：同样差分合并；MOVE 已支持 ⇒ 原子写照常可用
```

插件既能当"哑客户端"用（M1），也可以在 M2 换成 hub 的 REST 接口（增量游标，更省流量）——两种模式并存，设置里切换。

## 6. 合并引擎（核心）

### 6.1 基线定义

服务端为每个 `(客户端身份, 路径)` 保存**该客户端上一次 PUT 上来的视图** `P_prev`（解析后的规范化快照，不是原始字节）。

| 差集 | 含义 | 动作 |
|---|---|---|
| `P − P_prev` | 该端**新增** | 并入规范状态（已存在则幂等） |
| `P_prev − P` | 该端**删除** | 规范状态打墓碑 |
| 同名元素字段不同 | 该端**修改** | 元素级 LWW（`updatedAt` → 内容哈希 → deviceId） |
| 集合顺序变化 | 该端**重排** | 采纳该端顺序（后写者胜），记日志 |

**首次见到的客户端（无 `P_prev`）**：整份 payload 只当新增，**永不产生删除** ⇒ 换手机、重装、加第三台设备，永远不会误删别人。

**为什么基线是"它上次上报的视图"而不是"我们上次给它的视图"**：不管客户端那一轮 LWW 选了本地还是远端，`P_prev → P` 的差永远是这台设备真实的净变化；它没采纳我们的状态只表现为"没有新增"，而不是"删光了"。

### 6.2 时钟与胜负

- 合并判定**不使用**两端墙上时钟（`T6`）；时间戳只用于展示与冲突记录。
- 客户端侧的 LWW 我们不与之对抗，而是**引导**：渲染给某端时 `playlists.modifiedAt` 填**该端自己上次上报的值**。

| 该端情况 | 它的本地 modifiedAt | 我们渲染的 | 它的 LWW 结果 |
|---|---|---|---|
| 没有新改动 | `== P_prev.modifiedAt` | 相同 → 平局比内容哈希 → 远端胜 | 采纳合并结果 ✅ |
| 刚有本地改动 | `> P_prev.modifiedAt` | 更旧 | 本地胜 → 它把改动 PUT 上来 ✅ |

（若直接填 `now`，两端时钟偏差会导致它刚改完就被远端覆盖、本地改动静默丢失。）

### 6.3 删除、复活与墓碑

- 删除用 `deletedAt` 墓碑表达；**禁物理删除**。
- 墓碑保留 **60 天**；未知元素的墓碑也要留（防长期离线设备复活）。
- 复活守卫：已墓碑的元素，**同一 device** 可以立即重加；其它端只有在 GC 窗口之后才能重加。被挡下的动作记日志。

### 6.4 安全阀（防"整段清空"）

一次上报若将删除超过基线中 **50% 的歌单**或 **50% 的曲目**，**拒绝整轮**并记告警（返回 409/错误码，不落任何变更）。理由：客户端异常、文件被截断、适配器 bug 都可能表现为"整份空视图"，这是插件 0.1.0 事故（云端整歌单被删）的直接防线。

### 6.5 幂等与收敛

- 差分 + 集合并幂等：同一份 `P` 重复上报不改变结果；
- 与到达顺序无关：两端的净变化互相叠加；
- 收敛：任一端 PUT 后拿到的是含双方变化的合并结果，下一轮 `P_prev → P` 差为空 ⇒ 内容哈希稳定。

### 6.6 冲突策略

| 冲突 | 策略 |
|---|---|
| 不同元素各自增删 | 并集，天然无损 |
| 同一元素一端加、一端删 | **删除优先**（确定性、不依赖时钟），记冲突日志 |
| 同一元素字段双改 | 元素级 LWW（`updatedAt` → 哈希 → deviceId） |
| 歌单顺序双改 | 后写者胜，记日志 |

## 7. 统一数据格式 `canonical-v1`

规范文本 [spec/canonical-v1.md](spec/canonical-v1.md)（含 `P/I/T/E/S/V/C/A` 编号规则）、JSON Schema、完整示例、校验器。

**六个要点**

1. **身份只有一对**：曲目 `identity{source, songId}`；歌单 = 规范 `id` + 各端 `nativeId` 映射表。
2. **分层**：身份 / 展示 / 平台能力 / 品质 / 状态 / 扩展。
3. **一首歌可挂多平台**：`platforms{tx:{…}, wy:{…}}`（聚合播放器的核心特性）。
4. **品质归一但保留原生码**：`qualities[].code` 用统一码（`master` > `atmos_plus` > `atmos` > `hires` > `flac24bit` > `flac` > `320k` > `192k` > `128k`），`platforms.<p>.qualitys[].nativeCode` 存原文。
5. **删除是墓碑**（`deletedAt`），不是缺席。
6. **未知字段进 `ext` 且必须带回去**——"加平台不升版本"的唯一保障。

**与现有两端的字段对应（已对着源码核实）**

| 规范 | 栖弦 `sync-v1.json` | 澜音插件 |
|---|---|---|
| `playlist.version/createdAt/updatedAt` | `version: 1` 整数、ISO8601 字符串（`playlist_models.dart:287-292`） | `sync-core.js:356-361` 同 |
| `identity.source/songId` | 顶层 `source` + `musicInfo.meta.songId` | 同 |
| `durationMs` | `musicInfo.interval` = `"03:27"`（零填充） | 同（已有互转实现） |
| `qualities[]` | `musicInfo.meta.qualitys[{type,size}]` | 同 |
| `platforms.tx.*` | `musicId = tx_<songId>`、`albumId`、`strMediaMid` | 同 |

**性能约束已写进规范**（`PF1`–`PF8`）：gzip 5–8×、ETag→304、合并 O(n+m)、单文档 <1 MiB、`ext` <64 KiB、曲目池去重。

## 8. 平台适配与扩展方式

### 8.1 六个扩展点（全部是加法，都不升版本）

| 扩展点 | 加一个平台做什么 |
|---|---|
| 平台 code | 规范 §5.1 加一行（`tx/wy/kw/kg/mg` 已有） |
| 适配器 | 新写 `parse` / `render` |
| 品质映射 | 把该平台原生码 → 归一码的映射表加进适配器（栖弦 `lib/core/sdk/internal/*_quality.dart` 可照抄） |
| 路由 | 门面加一条路径 → 绑到该适配器 |
| 能力声明 | 能否删歌/建歌单、是否 `multi_file`/`needs_propfind`、体积上限 |
| 平台专有字段 | 放 `platforms.<code>` 或 `ext.<code>.<字段>` |

只有**改身份 / 改结构 / 改语义**才升 `schemaVersion`（迁移期服务端同时渲染两版）。

### 8.2 能力声明表（决定"缺失能力"如何表达）

| 能力 | 栖弦 | 澜音插件 | LX（待研究） |
|---|---|---|---|
| 读/写歌单 | ✅ | ✅ | ✅ |
| 删除歌单里的歌 | ✅ | ❌（SDK 无 `removeTracks`） | ✅ |
| 静默新建歌单 | ✅ | ❌（要用户点对话框） | ✅ |
| `PROPFIND` 列目录 | 需新增 | ✅（HTTP 方法不限） | 待确认 |
| 删除表达 | 真删除 | **"待清理清单"**（禁止静默忽略，`A5`） | 待确认 |

### 8.3 加平台的七步流程

1. 规范加 `source` code；2. 写适配器 `parse`/`render`；3. 补品质原生码映射；4. 声明能力；
5. 写往返测试 `parse(render(doc)) ≡ doc`（lossy 必须显式登记）；6. 加示例并过校验器；7. 记变更日志。

### 8.4 LX 接入前要研究的三件事

① 它的目录/文件名与格式版本；② 它用到的 HTTP 方法（是否 `PROPFIND`）；③ 它怎么表达删除。
好消息：栖弦里**已有 LX 歌单导入器**（`lib/features/playlists/lx_playlist_import.dart:265` 把 LX 的 `flac32bit` 归一成 `flac24bit`），品质码映射可直接照抄。

## 10. 性能与规模

**规模假设**：客户端 2–5；歌单 3–20；曲目 10²–10⁴；单客户端文档 10²–10³ KB（实测：云端 245 首 = 237 KB）。

| 指标 | 目标 |
|---|---|
| 单轮正文流量（移动端） | gzip 后 **< 50 KB**；无变化时 **100% 走 304**（0 正文） |
| 合并耗时（10⁴ 曲目） | P95 < 100 ms |
| 渲染耗时 | P95 < 50 ms（带内容哈希缓存） |
| 常驻内存 | < 150 MB |

**措施（按收益排序）**：① gzip + ETag/304；② 曲目池去重 + 字段精简（同样内容体积约减半）；③ 合并 O(n+m) + SQLite 索引 + WAL 单事务；④ 渲染结果缓存（按内容哈希）；⑤ 给有能力的客户端提供增量游标接口；⑥ 墓碑 GC 走后台任务；⑦ 逼近 1 MiB 时切"每歌单一个文件 + index"（适配器 `multi_file`）。

| 项 | 方案 |
|---|---|
| 启停 | 注册为开机自启；`/v1/health` 探活 |
| 备份 | SQLite 每日备份 + 每次"大变更"前自动备份（保留 30 份） |
| 日志 | 每次收/发落 `sync_log`（客户端、方法、路径、字节数、净变化摘要、冲突）；保留 90 天 |
| 观测 | `/v1/stats`：各客户端最后成功同步时间、待处理冲突数、墓碑数、文档大小 |
| 回退 | 两端把地址改回 AList URL；服务端不需要改动 |
| 安全 | Basic over HTTPS、只绑 `127.0.0.1`、日志不含凭据、独立账号 |

## 12. 可行性与失败模式

### 12.1 会被误认为"做不到"的四件事

| 看似的问题 | 实际处理 |
|---|---|
| 各家格式不同 | 适配器在服务端翻译；平台之间**不需要互相理解** |
| 客户端不支持条件写/原子写 | 服务端自己实现 `If-Match`/`If-None-Match`/`ETag`，并支持 `MOVE`（插件的原子写照常可用） |
| 栖弦整段覆盖 | 不把它的 PUT 当最终状态，只取净变化；并按 §6.2 引导它的 LWW |
| 澜音不能删歌 | 能力声明 → 渲染为"待清理清单"，**禁止静默忽略** |

### 12.2 真正会失败的情况

| 情况 | 后果 / 应对 |
|---|---|
| 平台不允许自定义 WebDAV 地址 | 接不上（栖弦、澜音都允许，无此问题） |
| 平台用私有协议而非 WebDAV | 接不上（LX 是 WebDAV） |
| 客户端要求未实现的 WebDAV 细节（`LOCK`、特定 `PROPFIND` 属性、深度语义） | 补实现；**这是唯一需要在真机上逐个验证的部分**，用日志定位 |
| 服务端/隧道不可用 | 两端停止同步但**不丢数据**；可临时切回 AList |
| 客户端上报被截断/异常为空 | §6.4 安全阀拒绝整轮并告警 |

## 13. 里程碑与实施顺序

**顺序原则：合并语义 > 客户端协议兼容 > 部署。先证明"不丢数据"，再接真机，最后上隧道。**

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **M0 设计定稿** | 本文 + `spec/canonical-v1` 定稿 | 文档评审通过（进行中） |
| **M1 服务最小可用** | 门面 + `cyshine-v1` 适配器 + 合并引擎 + SQLite + 两端接入 | 14 条验收用例全过；栖弦/插件零改动 |
| **M2 澜音侧补强** | 插件可选 `hub` 模式（增量游标）；SDK `removeTracks` 到位后自动删歌 | 澜音删歌闭环 |
| **M3 LX 接入** | LX 适配器（先做格式研究） | LX ⇄ 栖弦/澜音 互通 |
| **M4 增强** | 实时推送（SSE/WebSocket）、多端（>2）、可选分片结构 | 秒级跟随 |

**M1 内的执行顺序**（含风险理由）

1. **合并引擎 PoC**（纯逻辑，脚本模拟两个客户端）：唯一"错了就丢数据"的部分，第 14 节的用例全绿再往下；
2. **本机门面**（含 `MOVE`/`ETag`/`PROPFIND`/`MKCOL`/条件写/CAS 探测）：协议兼容性验证；
3. **真机接一端**：先澜音插件（我们自己的代码，随时回退），再栖弦改 URL；
4. **搬到隧道**：`https://yechoy.cn/sync/…`，AList 保持不动；
5. **真实数据演练**：用当前云端文件（237 KB / 245 首）当种子跑首轮"只增不删"，再造三类冲突；
6. **收尾**：墓碑 GC、日志查询、备份、回退开关、性能实测。

## 14. 验收用例（M1）

1. 澜音加歌 → 栖弦出现
2. 栖弦加歌 → 澜音出现（同名歌单已存在时自动）
3. 澜音删歌 → 栖弦消失
4. 栖弦删歌 → 澜音出现"待清理"（SDK 限制；M2 后自动删）
5. 两端离线各加歌 → 恢复后**都保住**，与同步顺序无关
6. 两端同时改同一歌单 → 并集不丢
7. 连续多轮同步 → 收敛（内容哈希稳定）
8. 歌单新增/删除双向传播
9. 服务重启 → 状态与基线保留
10. 新设备（无基线）首轮 → 只增不删
11. 客户端上报"整段空" → 被安全阀拒绝，云端不变
12. 已删元素被长期离线端带回 → 不复活（同一 device 除外）
13. 两端同时写 → 无覆盖、无截断，下一轮收敛
14. 性能：无变化轮询走 304；单轮正文 gzip < 50 KB；10⁴ 曲目合并 < 100 ms

## 17. 通用接入模型：任意支持 WebDAV 的客户端，填一个 URL + 账号密码（补充，需求 m01700 / m01714）

> 这一节把产品目标从"服务两个已知客户端"升级为"**通用 WebDAV 同步枢纽**"：不依赖任何插件，任何支持 WebDAV 的音乐客户端只要在 WebDAV 设置里填 **一个公共 URL + 自己的账号密码**，就能与同一账号下的其它客户端（**无论其数据格式是否相同**）双向同步。

### 17.1 用户视角（一个 URL + 账号密码）

1. 用户在服务上注册一个账号（自助注册页，或管理员用命令行创建）——**一个账号 = 一个同步空间**。
2. 在每个客户端的 WebDAV 设置里填三项：**地址**（全站共用 `https://<主机>/sync/`）、**用户名**、**密码**。与填 AList 的习惯完全一致。
3. 首次同步：服务把它上报的内容当作**新增**并入该账号的空间（**只增不删**）。
4. 之后：同一账号下任意一端的增删改，经服务端合并后出现在其它端。

不需要装插件、不需要改客户端、不需要知道彼此的存在；**不同账号之间互不可见**。

### 17.2 凭据与身份：一个 URL + 账号密码（HTTP Basic over HTTPS）

**地址是共用入口，账号密码才是身份。** 所有用户填同一个 URL，用各自的账号密码进入各自的同步空间。

| 项 | 设计 |
|---|---|
| 认证方式 | **HTTP Basic over HTTPS**（栖弦、LX、AList 用户都熟悉） |
| 身份 | **用户名 = 同步空间**；同一账号下的多台设备 / 多个 App 共享一个空间 |
| 凭据存储 | 服务端只存密码哈希（scrypt/argon2），**绝不存明文**；日志与备份都不含凭据 |
| 账号生命周期 | 自助注册；可改密、可吊销（吊销后旧密码立即失效、数据保留）；可选**共享空间**（多个账号映射同一空间，如家人共用） |
| 客户端填写 | 地址 + 用户名 + 密码（三项）；若客户端支持 URL userinfo，也可写成 `https://user:pass@host/sync/` |
| 可选增强（非必需） | 只读凭据（给"只看不改"的设备）；路径令牌（仅用于不接受 Basic 的极少数客户端） |

> 为什么用账号密码而不是"URL 里带随机令牌"：与用户已有的 AList 使用习惯一致，天然支持多用户隔离与吊销，且客户端普遍原生支持；令牌方案只是兼容性兜底。

### 17.3 方言识别与"未知客户端"降级（可扩展的关键）

服务端按三步判断"这份 payload 是什么"：

1. **路径匹配**：命中已知路由（如栖弦/澜音插件的 `sync-v1.json`、LX 的固定路径）→ 用对应适配器；
2. **内容指纹探测**：未命中路径时解析 JSON 顶层结构，比对指纹表（例：`sections{playlists,appearance,musicSources}` ⇒ `cyshine-v1`）→ 命中即用对应适配器；
3. **未知方言降级**：都识别不了 ⇒ **隔离命名空间**：
   - 原样存储该客户端的数据，**不参与跨格式合并**；
   - 该端 GET 仍拿到它自己那份（保证它正常工作）；
   - 记录"发现新客户端/新格式"事件（路径、User-Agent、顶层字段指纹、样例片段）；
   - 事后补一个适配器，它的数据**自动并入空间**，**用户不需要重新配置任何东西**。

> 这条降级规则是"可扩展"的安全底线：**宁可先不同步，也绝不猜错格式把数据合并坏。**

### 17.4 WebDAV 兼容层清单（要支持"任意客户端"，这些必须齐）

| 项 | 要求 |
|---|---|
| `OPTIONS` | 返回 `DAV: 1` 与 `Allow: OPTIONS, HEAD, GET, PUT, PROPFIND, MKCOL, DELETE, MOVE, COPY` |
| `PROPFIND` | `Depth: 0/1`；标准 `multistatus`；属性至少 `resourcetype`、`getcontentlength`、`getlastmodified`、`getetag`、`displayname`、`creationdate`；支持 `<allprop>` 与具名属性请求 |
| `GET` / `HEAD` | 正确的 `Content-Length`、`Content-Type: application/json`、`ETag`、`Last-Modified` |
| `PUT` | 支持 `If-Match` / `If-None-Match`，返回新 `ETag`；父目录不存在的处理策略（自动创建 or `409`）按真机行为择一 |
| `MKCOL` | 建目录（栖弦启动会调用） |
| `DELETE` | 删文件/目录（客户端"重置同步"会用） |
| `MOVE` / `COPY` | 支持 `Destination` + `Overwrite`（插件的原子写依赖 `MOVE`） |
| `LOCK` / `UNLOCK` | 先返回 `501`（多数客户端可降级）；遇到必须加锁的客户端再实现伪锁 |
| 错误码 | `401` / `403` / `404` / `409`（父目录）/ `412`（条件写失败）/ `423` / `507`（配额） |
| 编码 | 响应支持 gzip；请求接受 gzip 与 identity |

### 17.5 多用户、多空间与配额

- **一个账号 = 一个同步空间**（默认）；所有用户共用同一个入口 URL，靠账号密码区分；
- 空间内可有任意数量客户端，每个客户端一份基线（§6.1）；
- 可选**共享空间**：多个账号映射到同一空间（家人/朋友共用歌单），各自密码独立、可单独吊销；
- 每空间配额：文档数 / 总字节上限，超限返回 `507`；
- 改密或吊销后旧凭据立即失效，数据保留；
- 用户之间不共享数据，也不共享日志。

### 17.6 客户端身份（同一账号内怎么区分"谁"）

`client_key = (账号, 请求路径, User-Agent 家族)`。首次见到某组合即建立新基线；同一台手机上两个 App、或两台设备，因路径/UA 不同而各自身份，互不污染。

### 17.7 这就是"可扩展"的具体含义

| 场景 | 服务端要做什么 | 用户要做什么 |
|---|---|---|
| 已知格式的新客户端（如 LX） | 加一个适配器 + 一条路由 | **什么都不用改** |
| 未知格式的新客户端 | 先隔离可用 → 事后补适配器 → 自动并入 | **什么都不用改** |
| 客户端升级换了格式 | 适配器加版本分支（`cyshine-v1` / `cyshine-v2` 并存） | 无感 |
| 新增音源/平台 | 规范加一个 `source` code（§5.1） | 无感 |
| 用户换设备 | 新客户端首次只增不删（§6.1） | 填一次 URL |

### 17.8 已知限制（诚实）

1. 客户端必须**允许自定义 WebDAV 地址**（多数允许；写死自家服务的接不上，只能 fork）；
2. 采用**私有协议而非 WebDAV** 的客户端接不上；
3. 强依赖 `LOCK` 的客户端需要补伪锁实现（工作量小，但要真机验证）；
4. 未识别方言在补适配器之前**只隔离、不跨格式同步**——这是故意的安全选择；
5. 用户需要填**三项**（地址 + 用户名 + 密码）——这是本设计的既定接入方式，与填 AList 完全一致；只有完全不支持 Basic 的极少数客户端才需要走可选的路径令牌；
6. 与格式无关的元数据（主题、播放源配置等）由各客户端自管，只在**同名 section** 上做整段 LWW。
