# 跨平台歌单同步服务 — 方案（M1：栖弦 + 澜音，为 LX 等后续平台预留）

> 状态：待评审 · 作者：DSH（与 Yecho） · 日期：2026-10-05
> 注：**本文件已并入《[跨平台歌单同步服务-设计说明书.md](跨平台歌单同步服务-设计说明书.md)》**（权威版：含决策记录、部署与 AList 共存说明、可行性核对）；本文件保留作历史记录。
> 关系：本文取代 `真正同步方案.md` 里"让栖弦改合并逻辑 / 让插件停签 modifiedAt"那部分——
> **有了中间服务，两端都不需要改代码，也不需要本地基线。**

## 0. 一句话

在两端之间放一个**自己的同步服务**，它伪装成一个 WebDAV 网盘（客户端只改 URL，不改代码），
内部用**规范模型 + 适配器 + 服务端合并**维护唯一事实：

```
栖弦(Android) ─┐  （以为在跟 WebDAV 说话，写自己的 sync-v1.json）
澜音(插件)    ─┼─→ 同步服务 ─┬─ WebDAV 门面（按路径识别"这是哪种方言"）
LX(将来)      ─┘            ├─ 适配器 ×N（方言 ⇄ 规范模型）
                            ├─ 合并引擎（服务端持有每端基线）
                            └─ SQLite（规范状态 + 墓碑 + 客户端基线 + 日志）
```

**为什么必须这样**：WebDAV 单文件里只有"最终状态"，没有任何一端能区分
"对端没有这首歌"是**他删了**还是**他还没同步**。基线是唯一解。
把基线放在服务端，客户端就永远是"哑的"，加平台 = 加一个适配器。

**M1 的卖点：栖弦和澜音一行代码都不用改。**

| | 内容 |
|---|---|
| **M1 做** | 栖弦 ⇄ 澜音 双向同步：任一端的**歌曲增/删、歌单增/删**，另一端分钟级跟随；两端各自新增自动并集 |

## 2. 组件

| 组件 | 职责 |
|---|---|
| WebDAV 门面 | 处理客户端认的 HTTP 方法、认证、ETag、条件写；按**路径**分发到适配器 |
| 适配器 | `parse(客户端payload) → 规范状态`、`render(规范状态) → 客户端payload`；声明能力与默认值 |
| 合并引擎 | 用"该客户端上次上报的 payload"作基线做差分，把增量落到规范状态；墓碑与冲突策略 |
| 规范存储 | SQLite：规范歌单/曲目、平台身份映射、每客户端基线、墓碑、变更日志 |
| 观测 | 每次收/发都落 `sync_log`，可回放——这是现在最缺的东西 |

## 3. 规范模型（唯一事实）

```jsonc
// Playlist
{
  "id": "p_01H...",              // 规范 id（服务端生成，稳定、不随改名变）
  "name": "Yes",
  "description": null,
  "coverUrl": null,
  "createdAt": "...", "updatedAt": "...", "deletedAt": null,
  "tracks": ["t_...", "t_..."]   // 有序；顺序变化也算更新
}

// Track（曲目身份 = source + songId，跨平台共同身份）
{
  "id": "t_01H...",
  "source": "tx",                 // wy / tx / kw / kg / mg ...
  "songId": "003pgMEF0B7mWV",
  "name": "...", "singers": ["..."], "album": null,
  "durationMs": 207000, "quality": null, "artworkUrl": null,
  "addedAt": "...", "updatedAt": "...", "deletedAt": null,
  "platformRefs": { "cyshine": { "musicId": "tx_003pgMEF0B7mWV" } }
}

// PlaylistIdentity：歌单没有跨平台公共 id，靠映射表
{ "canonicalId": "p_01H...", "platform": "cyshine|cyshine|ceru", "nativeId": "lx-1759...-3", "nativeName": "Yes" }

// Tombstone
{ "element": "track|playlist", "id": "t_...", "deletedAt": "...", "device": "phone-7f3a" }
```

> **曲目身份统一用 `source + songId`**。栖弦是 `music:<source>:<musicId>`，插件是 `${source}\0${songId}`，
> 两边都能落到这一对；绝不能只用 `songId`（网易云/酷我都是纯数字，跨音源会撞车静默丢歌）。
>
> **歌单身份用映射表**，首次按名字配对，之后永远认映射（改名不丢、不重建）。
> 澜音插件目前按名字找本地歌单，所以**在澜音侧改名的歌单需要人工再配一次**（见 §8）。

## 4. 适配器契约（M1 只有一个实现，因为栖弦和澜音用的是同一份 `sync-v1.json`）

```python
class Adapter(Protocol):
    name: str                      # "cyshine-v1" / "lx-v1" / ...
    def match(self, path: str) -> bool
    def parse(self, payload: bytes, ctx) -> CanonicalState      # 客户端写来的
    def render(self, state: CanonicalState, ctx) -> bytes       # 客户端读到的
    def client_modified_at(self, payload: bytes) -> datetime | None
    # 扩展点：能力声明、路径模板、认证、分片（每歌单一文件时用）
```

- 路由：`/dav/sync/cyshine/sync-v1.json` → `cyshine-v1` 适配器（**插件与栖弦都用它**）。
- 将来 LX：`/dav/sync/lx/...` → 新适配器；规范模型、合并引擎、存储、门面**完全不动**。
- 渲染时**每个客户端拿到不同的 `modifiedAt`**（见 §5.4），所以 render 是 per-client 的。

## 5. 合并引擎（核心）

### 5.1 基线：用"该客户端上次上报的 payload"，而不是本地状态

服务端为每个 `(客户端身份, 路径)` 记住它上一次 PUT 上来的原始 payload `P_prev`。

收到新的 `P` 时：

| 差集 | 含义 | 动作 |
|---|---|---|
| `P - P_prev` | 该端**新增** | 加入规范状态（已存在则幂等） |
| `P_prev - P` | 该端**删除** | 规范状态打墓碑（同元素若刚被新增，走 §5.3 冲突策略） |
| 同名元素字段不同 | 该端**修改** | 按 `updatedAt` 元素级 LWW，平局比内容哈希，再平局比 deviceId |

- **首次见到的客户端（`P_prev` 不存在）**：整份 payload 只当"新增"，**永不产生删除**。
  ⇒ 换手机、重装 App、新增一台设备，永远不会误删别人。
- 这个规则**不依赖客户端是否采纳过服务端的状态**，也不依赖两端的墙上时钟是否准：
  无论栖弦的 LWW 选了本地还是远端，`P_prev → P` 的差永远是"这台设备真实的净变化"。

### 5.2 为什么必须在服务端（对照单文件方案）

| 场景 | AList 单文件 | 本方案 |
|---|---|---|
| 栖弦离线加歌后写回（它的 payload 不含桌面端新增） | **桌面端新增被整段覆盖** | 差分只看到"加了歌"，桌面端新增照旧在 |
| 栖弦删了一首歌 | 靠对端猜 | `P_prev - P` 明确的一对删除 |
| 两端同时改 | 谁后写谁赢 | 差分互相叠加，并集 |
| 删了歌又被另一端的旧快照带回 | 复活 | 墓碑 + 差分：没有"新增"事件就不会复活 |

### 5.3 删除 vs 新增冲突（同一元素）

- 默认 **删除优先**（确定性、不依赖时钟），并写一条冲突记录进 `sync_log`，便于排查。
- 理由：用户口径里冲突主要是"各自增删不同元素"（→ 并集，天然无损）；同元素"一边加一边删"极少见，
  选确定性策略比选时钟策略更可靠。

### 5.4 `modifiedAt` 的服务端策略（关键技巧）

栖弦的 `newerSyncSection` 是整段二选一：`modifiedAt` 大的一方整段胜，平局比内容哈希、不同则远端胜。

服务端**渲染给某客户端时**，把 `sections.playlists.modifiedAt` 填成
**该客户端自己上次上报的 `modifiedAt`**（绝不自作主张填"现在"）：

| 该端情况 | 它本地的 modifiedAt | 收到我们的 | LWW 结果 |
|---|---|---|---|
| 没有新的本地改动 | `== P_prev.modifiedAt` | 相同，内容不同 → 平局比哈希 → **远端胜** | 它采纳我们合并后的状态 ✅ |
| 刚有本地改动（尚未上报） | `> P_prev.modifiedAt` | 更旧 | **本地胜** → 它把本地 PUT 上来 → 我们差分合并 ✅ |

两边都不需要相信对方的时钟，也不会出现"本地新改动还没上报就被远端覆盖掉"。
（如果直接填 `now`，时钟偏差会导致栖弦刚改完就被采纳远端、本地改动静默丢失。）

### 5.5 幂等与收敛

- 差分 + 集合并是幂等的：同一份 `P` 重复上来不改变结果；
- 与顺序无关：两端的净变化互相叠加，先后到达结果一致；
- 收敛：任一端 PUT 后收到的是含双方变化的合并状态，下一轮 `P_prev → P` 差为空。

## 6. WebDAV 门面子集

| 方法 | 说明 |
|---|---|
| `OPTIONS` | 返回 `DAV: 1`、允许的方法（客户端探测） |
| `HEAD` | 返回长度与 ETag |
| `GET` | 渲染并返回该客户端的 payload；带 `ETag` |
| `PUT` | 收 payload → 解析 → 差分合并 → 更新基线；返回新 `ETag` |
| `PROPFIND` | depth 0/1，返回目录/文件条目（LX、以及将来多文件结构用；M1 也顺手实现） |
| `MKCOL` | 栖弦启动时会建目录 |
| `DELETE` | 删文件（`sync-v1.json` 的重置/清理） |
| `MOVE` | **必须支持**：澜音插件用「PUT `.tmp` → 校验 → MOVE 覆盖」做原子写 |
| 条件写 | **真正实现** `If-Match` / `If-None-Match`：ETag 不匹配返回 `412`。AList 忽略 `If-Match` 导致栖弦的 412 重试是死代码，在我们这里它活了 |
| 认证 | HTTP Basic（栖弦与插件都支持在 URL 里填用户名密码），走现有 HTTPS 隧道 |

ETag = 该客户端可见 payload 的内容哈希（内容不变则 ETag 不变，避免插件 CAS 探测误判）。

## 7. 存储（SQLite）

```sql
canonical_playlist(id, name, description, cover_url, created_at, updated_at, deleted_at, sort)
canonical_track(id, source, song_id, name, singers_json, album, duration_ms, quality, artwork_url, added_at, updated_at, deleted_at)
playlist_track(playlist_id, track_id, position)
playlist_identity(canonical_id, platform, native_id, native_name)
client_base(client_key, path, payload, etag, modified_at, updated_at)   -- §5.1 的 P_prev
section_blob(name, payload, updated_at, author)                          -- appearance / musicSources 整段 LWW
tombstone(element, element_id, deleted_at, device)
sync_log(id, ts, client_key, method, path, bytes, summary, conflict_json)
```

- 墓碑 GC：`deleted_at` 超过 60 天且所有已知客户端都上报过之后的时间点 ⇒ 清理。
- 部署：本机（与 AList 同机）+ 现有内网穿透；建议**新路径并存**，例如
  `https://yechoy.cn/sync/...` → `localhost:8000`，AList 继续留在 `/dav/...`（随时可退回）。

## 9. 为 LX 及后续平台预留的扩展点

1. **适配器目录**：`adapters/<platform>_<format>.py`，只依赖规范模型接口，不碰合并引擎。
2. **路径路由表**：`/dav/sync/<platform>/...`，一个平台可以有多条路径（多目录/多文件结构）。
3. **能力声明**：`supports_delete` / `supports_create_playlist` / `multi_file` / `needs_propfind`
   ⇒ 合并引擎按能力决定"删除怎么表达"（墓碑从渲染里省略，或保留在清单里）。
4. **身份映射**：`playlist_identity` 表天然支持 N 个平台的原生 id。
5. **多写者共存**：任何数量的客户端都能接，每端一份 `client_base`，互不影响。
6. **格式版本**：适配器内部自行处理（`cyshine-v1` / 将来的 `cyshine-v2` 并存）。

**LX 待研究清单（M3 前）**：它 WebDAV 的目录/文件名、文件格式（schemaVersion？）、
用到的 HTTP 方法（是否 PROPFIND/PUT）、认证方式、删除怎么表达、歌单/曲目 id 体系。

## 10. 风险与边界

| 风险 | 应对 |
|---|---|
| 服务挂了 / 隧道断 | 两端同步停摆但不丢数据（各自本地状态完好）；可临时把 URL 切回 AList（退化为旧行为） |
| 栖弦的未知实现细节（如重试时是否重新 GET） | 差分合并天然幂等，重复上报不产生破坏；`sync_log` 可回放定位 |
| 同元素"一边加一边删" | 删除优先 + 冲突日志 |
| 澜音宿主 SDK 缺失 | §8 的三条人工步骤，或等上游 API |
| 文件变大 / 写截断（AList 实测 ~108 KB 会截断） | 服务端直写 SQLite、自己生成 payload，不存在 PUT 截断；渲染体积可控 |
| 安全 | Basic over HTTPS + 独立账号；服务只暴露必要路径；`sync_log` 不含密码 |

## 12. 验收用例（M1）

1. 澜音加歌 → 栖弦几分钟内出现
2. 栖弦加歌 → 澜音出现（同名歌单已存在时自动；不存在时点一次「立即同步」）
3. 澜音删歌 → 栖弦消失
4. 栖弦删歌 → 澜音进"待清理"（SDK 限制；M2 后自动删）
5. 两端离线各加歌 → 恢复后**都保住**，且与同步顺序无关
6. 两端同时改同一歌单 → 并集，不丢
7. 连续同步多轮 → 内容收敛（哈希稳定，不再互相覆盖）
8. 歌单新增/删除在两端都能传播
9. 服务端重启 → 状态与基线保留（SQLite 持久化）
10. 新设备（无基线）首次同步 → 只增不删，不误删任何东西

**扩展用例（将来加平台时复用）**：11. 新平台首次接入只增不删 12. 三端并发增删收敛 13. 某端长期离线后回归不复活已删元素

## 13. 性能与规模

### 13.1 目标（可测量）

| 指标 | 目标 |
|---|---|
| 单次同步正文流量（移动端） | gzip 后 **< 50 KB**（当前 237 KB 原文 ≈ 35 KB gzip） |
| 304 命中率 | 无变化的轮询 **100%** 走 `304`（不传正文） |
| 合并耗时（10⁴ 曲目） | P95 **< 100 ms** |
| 渲染耗时（单客户端 10³ 曲目） | P95 **< 50 ms**（带内容哈希缓存） |
| 服务端常驻内存 | **< 150 MB** |
| 请求频率 | 每客户端 ≤ 1 次/分钟（澜音插件 60 s 起可配；栖弦按触发点） |

### 13.2 措施（按收益排序）

1. **gzip 压缩 + `ETag`/`304`**（`PF3`/`PF4`）——移动端流量第一优先，实现成本最低。
2. **曲目池去重 + 字段精简**（`PF2`/`PF8`）——同样内容体积约减半；顺手降低 AList 时代的截断风险。
3. **合并 O(n+m) + SQLite 索引**（`PF6`）：`tracks(identity_source, identity_song_id)` 唯一索引、
   `playlist_track(playlist_id, position)`、每客户端基线表主键 `(client_key, path)`；WAL + 批量事务，
   一轮同步只开一个事务。
4. **渲染结果缓存**：以（规范内容哈希 + 客户端 + 适配器版本）为键缓存 payload，避免每轮重新序列化。
5. **增量端点给有能力的客户端**：`GET /v1/changes?since=<cursor>` 只回变更（澜音插件能发任意 HTTP，可直接用）；
   WebDAV 客户端受协议限制仍取全文，但走 gzip+304。
6. **墓碑 GC 走后台定时任务**，不在同步路径上做全表扫描。
7. **分片演进**（`PF1`）：单文档逼近 1 MiB 时切"每歌单一个文件 + index"，适配器声明 `multi_file`。

### 13.3 必须一起决定的权衡：手机端电量

**栖弦当前没有任何同步定时器**：只在「启动 / 切回前台 / 本地变更后 2 s / 手动」时同步
（`lib/core/sync/webdav_sync_controller.dart:13` 的 2 s 只是上传防抖；全库唯一的 Timer）。

所以"分钟级同步到手机"**目前做不到**——不是服务端慢，是手机不会主动拉。两个选项：

| 选项 | 代价 | 效果 |
|---|---|---|
| A（推荐，零耗电） | 口径改为"打开栖弦 / 切回前台即同步" | 拿到手机的那一刻是最新的；离线期间不耗电 |
