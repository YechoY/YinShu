# 澜音 ↔ 栖弦 歌单真正同步方案（本地基线 + 三路合并）

> 目标仓库/项目：`ceru.cyshine-webdav`（澜音插件，v0.2.6）+ CyShineMusic（栖弦，Android/Flutter）
> 传输：WebDAV 上的一份 `CyShineMusic/sync-v1.json`（`schemaVersion` 保持 **1**，**不改文件格式**）
> 本文是给两边开发者、以及自己后续接手用的实现规格。

---

## 0. 验收口径（来自用户）

> 只要能在几分钟内同步成功就行：**任意一端新增/删除歌曲或者歌单，另外一方也会分钟级同步；如果各自都有新增或者删除，就自动合并更改。**

翻译成可验收的行为：

| 任意一端的操作 | 另一端（分钟级） | 要求 |
| --- | --- | --- |
| 新增歌曲 | 出现 | 不丢 |
| 删除歌曲 | 消失 | 且不复活 |
| 新增歌单 | 出现 | 不丢 |
| 删除歌单 | 消失 | 且不复活 |
| 两端各自都增/删 | 自动合并 | 谁的都不丢，**与操作顺序无关** |

**不在范围内**（明确不做，避免过度设计）：曲目顺序/歌单属性的并发冲突、换手机或清了数据后"已删内容不复活"、秒级实时。这三项要 `schemaVersion: 2`（墓碑 + 每元素版本，两端同时上线）或自建同步服务端，需要时再单独立项。

## 1. 为什么必须是"基线 + 三路合并"

WebDAV 上只有一个文件、服务端**零逻辑**：文件里只有"当前状态"，没有历史。

于是必然出现这个歧义：**「对端没有这首歌」，到底是"他删了"还是"他还没同步"？**

- 现有实现（栖弦）用"整段 `modifiedAt` 比大小"来猜 → 猜错就整段覆盖，所以会静默丢数据；
- 澜音插件缺 `removeTracks` 只是"执行不了删除"，**判定问题它一点都解决不了**。

唯一解法：**记住"上次双方确认一致的状态"（base）**，然后比较"各自相对 base 改了什么"，而不是比较"谁更晚"。

- 删除 = **base 里有、某一侧没有**；
- 新增 = **base 里没有**，而某一侧有。

两者永不会混淆 ⇒ 无损 + 删除可传播 + 可收敛。这就是 Git 的 merge base、Unison 的同步思路。

**base 必须存在各端本地**，绝不能写进同步文件：栖弦的 `WebDavSyncSnapshot.toJson()` 只序列化三节、`applyFromSync` 从模型重建 `data`，未知字段迟早被抹掉。

## 2. 数据模型

| 名称 | 存在哪 | 内容 |
| --- | --- | --- |
| `base` | **各端本地**（栖弦 SharedPreferences；插件 `ctx.storage`） | 上次"双方确认一致"的状态：`歌单id → 曲目身份键集合` |
| `local` | 本机 | 栖弦本地歌单库 / 澜音 `playlists.db` |
| `remote` | WebDAV 文件 | `sections.playlists.data` |

**歌单身份 = 云端文件里歌单的 `id` 字段**（栖弦原样带出带进，天然稳定）。
**曲目身份 = `source + songId`**：

- 栖弦：现成的 `PlaylistTrack.identityKey`（`lib/features/playlists/playlist_models.dart:49-65`，形如 `music:tx:003pgMEF0B7mWV`）；
- 插件：`trackKey(source, songId)`（`src/sync-core.js`，取 `musicInfo.meta.songId`，`source` 白名单 `wy/tx/kw/kg/mg`）。

不能只用 `songId`：网易云/酷我都是纯数字，跨音源必撞车。
本地文件曲目（栖弦的 `musicInfo == null` / 插件非白名单源）不参与同步，只留本机。

## 3. 合并规则（歌单级、曲目级同一张表）

对每个元素，只需要 base / local / remote 三个"有/无"：

| base | local | remote | 结论 |
| --- | --- | --- | --- |
| 有 | 有 | 有 | 保留 |
| 有 | 有 | 无 | 远端删除 → **删** |
| 有 | 无 | 有 | 本地删除 → **删**（不复活） |
| 有 | 无 | 无 | 两边都删 |
| 无 | 有 | 无 | 本地新增 → 保留并回写 |
| 无 | 无 | 有 | 远端新增 → 保留（导入） |
| 无 | 有 | 有 | 两端各自新增 → 保留（并集） |

压成一行判定：

```text
keep(K) = (local.has(K) && remote.has(K)) || (!base.has(K) && (local.has(K) || remote.has(K)))
```

两端同时改了**同一首歌的字段**（标题/时长等）时：base 里存该元素的内容哈希，`local == base` 就取远端，`remote == base` 就取本地；两边都偏离 base 才算真冲突，按固定规则收尾（栖弦现有 `mergePreferLocal` 是"远端胜"，可以沿用）。

歌单级与曲目级都要走这张表，顺序：先定歌单去留，再定每个存活歌单里的曲目去留。曲目顺序沿用"本地顺序在前、远端独有追加"。

## 4. 栖弦要改什么（5 项）

文件：`lib/core/sync/webdav_sync_controller.dart`（539 行）、`lib/core/sync/sync_models.dart`、`lib/core/sync/webdav_client.dart`

### ①`_syncOnce:273` 的 playlists 分支换成三路合并（核心）

现在是整段二选一：

```dart
// webdav_sync_controller.dart:271-282
final merged = WebDavSyncSnapshot(
  generatedAt: DateTime.now().toUtc(),
  playlists: newerSyncSection(local.playlists, remote.snapshot.playlists),  // ← 换成 _mergePlaylists
  appearance: newerSyncSection(local.appearance, remote.snapshot.appearance),
  musicSources: newerSyncSection(local.musicSources, remote.snapshot.musicSources),
);
```

`newerSyncSection`（`sync_models.dart:120-127`）是"比 `modifiedAt` → 整段取一边"，而 `_recordLocalChange`（`webdav_sync_controller.dart:361-374`）在**任何**本地改动时就把整节 `modifiedAt` 刷 `now`（`_saveRevision` :407-423、:444-454）。所以"谁赢"取决于两台设备的墙上时钟 —— 这就是丢数据的直接原因。

参考实现（base 传 `Map<String, Set<String>>`，没基线时传空 Map 即退化为"并集止血"）：

```dart
WebDavSyncSection _mergePlaylists(
  WebDavSyncSection local,
  WebDavSyncSection remote,
  Map<String, Set<String>> base,
) {
  final localById = _indexById(local.data);   // id -> Map
  final remoteById = _indexById(remote.data); // id -> Map
  final merged = <Map<String, dynamic>>[];
  final nextBase = <String, Set<String>>{};

  for (final id in {...localById.keys, ...remoteById.keys}) {
    final l = localById[id];
    final r = remoteById[id];
    final b = base[id];
    final hasL = l != null, hasR = r != null, hasB = b != null;

    // 歌单级三路判定
    if (hasB && !hasL && !hasR) continue;            // 两边都删
    if (hasB && !hasL) continue;                     // 本机删了 → 删（不复活）
    if (hasB && !hasR) continue;                     // 云端删了 → 删
    if (!hasL && !hasR) continue;

    final src = (l ?? r)!;
    if (!hasL || !hasR) {                            // 只有一边有 = 新增 → 保留
      merged.add(src);
      nextBase[id] = _trackKeys(src);
      continue;
    }

    // 两边都有：曲目级三路判定，keep 公式见 §3
    final keysL = _trackKeys(l), keysR = _trackKeys(r);
    final kept = <String>{};
    final tracks = <dynamic>[];
    for (final raw in [
      ...(l['tracks'] as List? ?? const []),
      ...(r['tracks'] as List? ?? const []),
    ]) {
      final k = _identityKeyOf(raw);                 // 复用 PlaylistTrack.fromJson().identityKey
      if (k.isEmpty) { tracks.add(raw); continue; }  // 无法判定的曲目：保守保留
      final keep = (keysL.contains(k) && keysR.contains(k)) ||
          ((b?.contains(k) ?? false) == false &&
              (keysL.contains(k) || keysR.contains(k)));
      if (!keep || !kept.add(k)) continue;
      tracks.add(raw);
    }
    merged.add({...l, ...r, 'tracks': tracks});      // 歌单字段沿用现有"远端胜"
    nextBase[id] = kept;
  }

  return WebDavSyncSection(
    // 不再无条件写 now；两边取较新值即可（playlists 的判定已不依赖它）
    modifiedAt: local.modifiedAt.isAfter(remote.modifiedAt)
        ? local.modifiedAt
        : remote.modifiedAt,
    data: merged,
  );
}
```

（`_indexById` / `_trackKeys` / `_identityKeyOf` 是三个小工具函数；`_trackKeys` 返回该歌单的 `identityKey` 集合。）

### ② 在 SharedPreferences 里存 base，并在**写回成功之后**才推进

- key 建议 `webdav_playlists_base_v1`，与现有 `webdav_playlists_hash_v1` / `webdav_playlists_modified_v1`（`_saveRevision` :444-454）同一路数；内容 `{"<playlistId>": ["music:tx:...", ...]}`。
- ⚠️ **现在 `_saveSnapshotRevisions(merged)` 在 `:284`，`client.write(...)` 在 `:288` —— revisions 先于写回推进。写失败（断网）时 base 会领先云端，下一轮就会把云端缺失误判成"远端删除"而误删。** 基线必须放到写回成功（或 `_sameSnapshotData` 判定无需写）之后。
- 合并结果与云端一致时（`:286` 提前 return）也要提交 base（此时本地已 `_applyRemoteSections`，等于双方一致）。

### ③ 写回前重读云端（AList 忽略 `If-Match`，`:288` 的 412 重试是死代码）

两个写者（手机 + 桌面插件）会并发。写之前再 GET 一次：

- 若远端内容哈希与本次合并所依据的一致 → 直接写；
- 若变了 → 用新远端**重新合并**（最多重试 1~2 次），仍冲突就放弃本轮写（下轮再同步），绝不覆盖。

### ④ `_recordLocalChange`（:361-374）不要"整节刷 `now`"

改为：只在内容真变化时更新，或干脆改成"记录本地变更时间"另一路存储，别让一个歌单的改动改写整节的 `modifiedAt`。（`appearance` / `musicSources` 仍可用 LWW，那两节不涉及丢歌。）

### ⑤（小请求）加一个运行期周期拉取，让"分钟级"成立

现在全库没有任何同步定时器（只有 `:13 _uploadDebounce = 2s`），同步只在：App 启动（`lib/app.dart:55`）、切回前台（`lib/app.dart:73-76` → `onAppResumed`）、本地变更后 2 秒、手动 `syncNow`。所以手机 App 一直停在前台不动时，桌面端的改动不会自动出现。加个 3~5 分钟的 `Timer.periodic` 调 `_syncSilently()` 即可（它内部已有 `_syncing` / `_syncAgain` 重入保护，幂等）。

## 5. 澜音插件要改什么（4 项）

插件工程：`ceru-cyshine-webdav`（发布物 = `release/plugin.js`）。**插件的曲目级三路合并与"整轮未落实不提交状态"已经实现**（`src/sync-core.js` 的 `planPlaylistSync` / `appliedBaseline`，状态键 `last-hash.v2`/`playlist-ids.v2`/`deleted-tombstones.v2`），要补的是下面四件事：

### ① 停止替栖弦给 `sections.playlists.modifiedAt` 签字

`src/sync-core.js:386-392`（`buildSnapshot` 里 `playlists: { modifiedAt: now, data }`）与 `src/index.js:958`（`if (section) section.modifiedAt = now`）：内容没变就原样保留远端的 `modifiedAt`；内容变了再写当前时间（甚至可以不写）。目的是让"谁更新"这条基于本机时钟的赛道彻底失效。

### ② 歌单匹配：从"按名字"改成持久化 id 映射

`src/index.js:496-506` 现在是 `p.ref.location === 'local' && p.name === playlistName`。名字一旦改，就会被判成"删一个 + 建一个"。改为新增状态键 `playlist-map.v2`（`云端歌单 id → 澜音歌单 ref`），名字只用于**首次配对**，配对不上时报"待确认"而不是重建。

### ③ SDK 到位后接上"自动删/建"（现在是提示手动）

- `removeTracks` 到位 → `planPlaylistSync` 的 `cleanSongs`（当前显示"待你手动清理"）改成执行删除并复核；
- `create` 到位 → `pending-imports.v1` 里的待导入歌单自动静默创建（不再要用户点「立即同步」）；
- `remove` 到位 → 云端已删的歌单，自动删澜音侧对应歌单（现在只靠 `deleted-remote-playlists.v2` 墓碑抑制复活）。

### ④ 保持现有不变式（别退化）

- `appliedBaseline = (localKeys ∪ importKeys) ∩ remoteKeysAfter`：**基线只记"两端都真正落实"的交集**；
- 一轮里只要取消/冲突/写回失败，就**不提交任何状态**（下轮从旧基线重算，幂等）。

## 6. 澜音宿主需要补什么（3 个方法）

`ctx.library.playlists` 目前只有 `list` / `getTracks` / `import`（v2.2.0 `app.asar` 内 `SERVICE_CAPABILITIES` 实测；`playlists.removeTracks` 全文命中 0 处）。权限目录里 `libraryDelete`（`library.delete`）已定义但没被任何 service 引用，看起来只差桥接：

1. `library.playlists.removeTracks({ target, items })` → 在歌单内移除若干首，返回 `{ removed, skipped }`（对应"手机删歌 → 澜音消失"）；
2. `library.playlists.remove({ target })` → 删除整个歌单（对应"手机删歌单 → 澜音消失"）；
3. `library.playlists.create({ name, items? })` → **静默**创建并返回 `ref`（对应"手机新增歌单 → 澜音出现"；后台任务不能弹 `pickPlaylist`）。

可选：`library.changed` 覆盖用户在界面里的歌单改动（把轮询间隔从 60s 降到"改完几秒"），插件工程里也有对应草稿。

## 7. 三条必须守住的不变量（缺一条就会丢数据）

1. **base 只在写回成功（或确认云端已一致）之后才推进**；任何失败都不推进 —— 否则云端缺失会被误判成删除。
2. **写回前重读云端**：两个写者 + 服务端不支持条件写 ⇒ 必须"读-合并-再读-必要时重合并-写"，宁可放弃本轮也不覆盖。
3. **不再用 `sections.playlists.modifiedAt` 决定胜负**；也不再让一端的本机时钟替另一端签字。

## 8. 实施阶段（每阶段都能独立验收）

| 阶段 | 改动 | 验收结果 |
| --- | --- | --- |
| **0（现在）** | 什么都不改 | 按 `ceru-cyshine-webdav/TESTING.md` §2.5 顺序操作：先手机 → 后桌面 → 再手机 |
| **1 止血** | 栖弦 ①（base 传空 = 纯并集）+ ③ | 任意顺序、两端各自增删**都不丢歌**；代价：删除不传播、被删的会复活 |

## 9. 验收用例（真机，两台设备 + 同一份 WebDAV 文件）

1. 澜音加歌 → 3 分钟内手机出现；
2. 手机加歌 → 3 分钟内澜音出现；
3. 澜音删歌 → 手机消失；
4. 手机删歌 → 澜音消失（阶段 3 前应为"待手动清理"清单出现该曲目）；
5. 断网：两端各加 1~2 首 → 恢复后**两种同步顺序都试** → 都保住；
6. 两端各删不同曲目 → 两边都消失，且下一轮**不复活**；
7. 同一歌单两端各加 → 结果是并集，顺序稳定；
8. 连续同步 3 轮（两端交替手动同步）→ `syncDataHash` 稳定不变（收敛）；
9. 断网状态下同步一轮 → 失败一轮后不推进基线，恢复后结果与第 5 条一致；
10. 手机端新建歌单 → 澜音出现（阶段 3 前需要用户手动点一次「立即同步」建歌单）。

判定"收敛"的方法：连续两轮 `sections.playlists` 的 `syncDataHash`（栖弦）与插件的 `last-hash.v2` 都不再变化。

## 10. 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 曲目顺序 / 歌单属性的并发冲突自动合并 | 用户口径未要求；需要每元素版本号（协议 v2） |
| 换设备 / 清数据后"已删内容不复活" | 需要墓碑写进共享文件（协议 v2，两端同时上线）；本地 base 丢了就退化为"全部当新增" |
| 秒级实时 | WebDAV 无推送；现实上限是"分钟级"（桌面端轮询 + 手机端打开/切回/定时） |
| 自建同步服务端 | 那是换架构（版本向量 + 推送），不是本插件能覆盖的 |
| 往同步文件里塞额外字段 | 栖弦只序列化三节、从模型重建 `data`，未知字段会被抹掉 |
