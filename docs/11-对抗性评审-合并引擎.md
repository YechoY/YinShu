# 11 · 对抗性评审：合并引擎 / 基线 / 墓碑（无代码阶段）

> 评审对象：`docs/05-合并引擎.md`、`docs/03-总体架构.md` §3.5–3.9、`docs/01-需求与验收.md` §1.3–1.6、`docs/09-决策记录.md` D8/D20、`spec/canonical-v1.md`。
> 方法：对每条规则构造"客户端 X 做 Y，然后 Z"的反例；只记**能静默丢/复活数据**或**永不收敛**的洞。
> 结论先行：**I2′ 的"从未交付过 ⇒ 不构成删除"不能保护"两台设备共用一个 client_key"**——那是本设计最深的洞，且 §5.5 用例 19 声称已被覆盖（实际未覆盖）。I7 的"2 年对所有人压制"应改为**无时间 TTL + 确认水位 GC**。

---

## A. 基线语义：差分不是良定义的

### A1 · 归因缺口：所有"删除"都是**假定的**，不是被证明的 ｜ 严重度 **高**（结构性）

- 依据：`docs/05-合并引擎.md:49-53`（`removed = keys(bsrv) - keys(C_new)`）、`:22`（"关键修正：绝不能相对它上次提交的视图判定"）、`:10`。
- 事实：`base_served` 只能证明**枢纽交付过什么**，永远不能证明**客户端本地曾经有过什么**。当同一 `client_key` 被两次运行共用（换机/重装/清数据，甚至只是两台设备），`C_new ⊂ base_served` 会被判为"这个客户端删除了"。
- 场景：`client_key` 已存在（设备 D1 用过）。设备 D2 覆盖同一 App（路径、UA 家族完全相同）后首次 PUT：本地只有 2 个歌单，`bsrv` 有 6 个 ⇒ `removed_pl` = 4（4/6 = 67% ≥ 50% 且 ≥3）⇒ 安全阀挂起（`docs/05-合并引擎.md:59-61`、`:114`）。但若 D2 本地丢的是**子集**（例如 6 个里丢 2 个），比例 33% 不触发安全阀，且"期间无人写过"使 `space.revision == bsrv.served_revision`（`:56`）⇒ **两个歌单连同其曲目被静默删除、写墓碑、`revision+1`**。
- 为什么 I2′ 挡不住：I2′ 只覆盖"该客户端**从未被交付过**的元素"（`:30`）。这两个歌单**被交付过**——交付给了 D1。差异是"同一个逻辑客户端的不同物理运行"，设计里没有这个概念。
- 最小修复：删除必须拿到**正向归因**才生效，否则一律进确认队列。可用的正向证据只有三种，按强度：
  1. 客户端回显我们上次交付的 `ETag`（`If-Match = <etag-of-base_served>`）——但 `docs/01-需求与验收.md:74`、`docs/02-现状调研.md:21` 说明 AList 路径上 `If-Match` 从不触发，栖弦可能发 `*` 或不发，**不可依赖**；
  2. `parse(render(bsrv.view)) ≡ bsrv.element_keys`（适配器无损往返，`spec/canonical-v1.md:296` A3）**且** `space.revision == bsrv.served_revision` **且** `C_new ⊆ bsrv` 是 `bsrv` 的真子集（不是空集/近空集）——即"它确实表示过完整视图，而现在只少了这几项"；
  3. 用户确认。
  建议把 2 写进 §5.3 的 `delta.removed` 前提，并给"本次提交是子集且丢失比例 > 一个更小的阈值（例如 10%）"再套一层风险挂起。**注意这会拦一部分"我今天就是想删 1 个歌单"的正常操作**，所以阈值要按"是否同一 client_key 在 30 天内换过 IP/UA 或者基线建立时间 < 24h"来加权，而不是一刀切。

### A2 · `suspect_removals` 是死路：一旦进入，永远不会被重新应用 ｜ 严重度 **高**

- 依据：`docs/05-合并引擎.md:56-58`（`delta.suspect_removals = delta.removed; delta.removed = {}`）、`:71`（`journal.append(... suspects ...)`）、`:119`（确认通道只讲"待确认删除"）。**算法里没有任何路径把 `suspect_removals` 重新拿出来应用**，`journal` 只是审计记录（`:154`、`:182`）。
- 场景：A 端离线 3 天，期间 B 端加了一首。A 端 PUT 时 `space.revision(R+5) ≠ bsrv.served_revision(R)` ⇒ A 端本次的删除全部转 `suspect_removals`。A 端拿到的渲染里那首歌还在（因为 A 删的是别的歌，且渲染只反映 canonical）。A 端本地重建后，**它删的那首歌又回来了**；下一轮 `space.revision == bsrv.served_revision`，但 `C_new` 里已经没有那首歌——于是"删除"从 `delta.removed` 里**彻底消失**（`C_new` 与 `bsrv` 已在渲染中重新对齐），`suspect_removals` 永远是空的。用户看到的是"我删的歌自己回来了"，且状态页没有任何卡片（卡片只由"待确认删除队列"生成，`:119`）。
- 语义结论：`suspect_removals` 不是"待确认"，而是**静默丢弃**。它同时违反 V7 与 `docs/01-需求与验收.md:51` V9（3 次点击可恢复——这里根本没有入口）。
- 最小修复：把 `suspect_removals` 落成**持久队列**（`pending_removals` 表：`space_id, client_id, kind, key, first_seen_rev, sample_count`），并提供两条出口：① 状态页/CLI 确认后写墓碑；② **下一次**该客户端提交里若该 key 仍然缺席且本轮再无别端写入，则自动生效一次（"两次独立提交都缺席"是唯一廉价可得的加强证据）。没有出口的悬挂项不合法。

### A3 · `base_served` 在事务外推进：I1 被自己的伪代码违反 ｜ 严重度 **中**

- 依据：`docs/05-合并引擎.md:62-73`——`:70` 在事务内推进 `base_submitted`，`:73` 在事务**外**用 `render_for` 的结果推进 `base_served`；而 `:172` 的渲染失败返回 `500`。`:28` 的 I1 声称"基线只在交付/写回成功后推进"。
- 场景：合并提交成功 → 渲染阶段失败（客户端硬要求不满足，`:172`，或超限）→ 返回 `500`，客户端认为整次失败。此时 `base_submitted` 已推进、`space` 已变，`base_served` 未推进 ⇒ `space.revision ≠ served_revision` **永久成立**，直到该客户端下一次 GET。而客户端在 `500` 上不会 GET（栖弦任何非 2xx 都判失败并重试同一 PUT）。`docs/04-数据规范与适配器.md:54` 又说"响应只允许 2xx"——这是硬矛盾。
- 最小修复：渲染必须是**事务内可回滚的一部分**（先 render 预演并校验 `limits()`，再提交并同时写 `base_served`），或者把 `base_submitted` 的推进移到渲染成功之后。渲染失败 ⇒ 整个请求无副作用 ⇒ 允许返回 `500`（此时"无副作用"才是 I4 幂等的前提）。

### A4 · 新装/已知身份只 GET 或 PUT 空视图的路径未定义 ｜ 严重度 **中**

- 依据：`docs/05-合并引擎.md:42-46`（`bsub is None ⇒ adopt_initial`）、`:73`（`base_served` 在渲染后推进）、`:77-82`；`docs/03-总体架构.md:86`（无基线客户端的 GET/PROPFIND 语义"尚未定"，列了三个互斥候选）。
- 场景 1（只 GET）：新设备首次 GET。若走 `docs/03-总体架构.md:86` 候选 ①（返回 404），栖弦把 404 当失败 ⇒ 这个设备**永远不会把本地数据推上来**（用户故事 US3 失效）；若走候选 ②（只返回它自己的隔离副本），它 PUT 回来的内容与 `base_served` 之间的差分是**良定义**的（因为它确实看到过），但"隔离副本"意味着它看不到别端数据，用户会以为同步没生效。两个候选的后果完全不同，而 `docs/10-评审记录与整改.md:113` 已宣布"本轮设计冻结、无待确认项"——**冻结时这一项其实未决**，属于文档自相矛盾。
- 场景 2（首轮 PUT 成功、响应丢失）：`adopt_initial` 推进了 `base_submitted`，但 `base_served` 只在渲染成功后才写。客户端重试同一 PUT（栖弦失败即重试）⇒ 第二次走常规路径，`bsrv` 可能是 `None`：此时 `keys(bsrv.playlists)` 在 `:49-53` 上是**对 None 求 keys**，伪代码会崩。必须显式规定 `bsrv is None ⇒ 与 adopt_initial 同路径`（并注明该状态如何从崩溃恢复）。
- 最小修复：写死一条规则——`bsrv is None ⇒ 禁止产生任何删除，本请求只做并集 + 建立 `base_served` = 本次交付`；并把 `docs/03-总体架构.md:86` 的三个候选收敛为一个（推荐候选 ①′：对无基线客户端 GET 返回 `200` + **该客户端自身隔离副本**，同时状态页出"新设备待并入"卡，用户确认后走 adopt_initial 并入）。

### A5 · `base_served` 只存"键清单 + 内容哈希"不足以重建视图 ｜ 严重度 **中**

- 依据：`docs/05-合并引擎.md:185`（"只持久化元素键清单 + 内容哈希（足以做差分），完整视图按 `canonical_revision` 共享物化、按需重建"）；`docs/03-总体架构.md:150` 同。
- 问题：差分靠键清单没问题，但"重建视图"要靠 `canonical_revision` 指向的历史物化。可是 `space.revision += 1` 之后 `canonical` 变了，若该客户端上次被交付的是 `R-1` 的内容而 `R-1` 的历史已被 GC（`:68` 只 GC 墓碑，没有规定历史保留期），重建就会**用当前内容冒充上次交付内容** ⇒ A1 的归因、A3 的幂等、以及 `modifiedAt` 的"确有变化才推进"（`:94`）全部失真。
- 最小修复：明确 `base_served` 的持久化内容要么包含**足够重建该客户端上次视图的最小充分集**（键 + 每个键的内容哈希 + 渲染模板版本 + `served_revision`），要么规定 `canonical_revision` 历史**按最长基线存活期**保留（> 最久未同步的已注册客户端）。

## B. 客户端身份：`client_key` 定义不足，用例 19 无法通过

- 依据：`docs/03-总体架构.md:138`（`client_key = (账号/空间, 请求路径, 设备标识, User-Agent 家族)`；"设备标识优先取客户端自带的 `Client-Id`；缺失时由枢纽首次签发并在路径中固定"）、`:149`、`docs/04-数据规范与适配器.md:50`、`docs/05-合并引擎.md:157`（用例 19）。
- 已知事实（不必再验）：栖弦**没有设备标识头、没有 cookie jar、URL 由用户手填**；`docs/10-评审记录与整改.md:40`（M5）已确认"URL 规范化丢弃 query ⇒ 不能用 `?cid=`"。
- 因此"由枢纽首次签发并在路径中固定"只有两种实现可能，两者都不成立：
  - **重写 URL**：枢纽不能改客户端配置里的地址（假 WebDAV 服务器无法让客户端改变它请求的路径）；
  - **分配路径**：需要用户手工把地址填成 `https://hub/sync/<device-part>/`——这就是"设置向导"，而本阶段 `docs/01-需求与验收.md:71`（"**共享空间与歌单级共享**"同级的边界）/`spec:62` 把"客户端逻辑改不动"列为第一优先级，用户故事只是"填一个 URL"。**没有向导 ⇒ 两台手机的路径字面相同 ⇒ `client_key` 相同。**
- **已部分实施（P0，2026-10-06）**：设备段 `/d/{device}/`（4 条路由）与 `X-Hub-Device` 头已实现（`src/hub/api.py:665-688` 身份归一化、`:691-728` 路由；非法设备名 400）；**但仍无设置向导** ⇒ 栖弦需手工在 WebDAV 地址后加一段；澜音插件尚不发设备号 ⇒ 两台澜音仍视为同一客户端（残差仍由 R1 + revision 闸门 + 安全阀兜着）。
- 于是 `docs/05-合并引擎.md:157` 的用例 19（"同路径、同 UA 家族"下"两台设备互不丢数据"）在设计上**不可能通过**；该行同时承认了依赖"设备维度 `client_key`"，属于自我否定。

### 失败模式清单（两台栖弦手机 A1/A2，或重装后的同一台，共用同一 `client_key`）

| # | 场景 | 机制 | 结果 | 评级 |
|---|---|---|---|---|
| B1 | A1 加了歌单 P5；A2 未 GET 前 PUT（对 P5 一无所知） | A2 的 `C_new` 缺 P5，P5 ∈ `bsrv`，比例 1/6 不触发安全阀，`space.revision == served_revision` ⇒ 走 `:49-53` 正常删除路径 | **P5 与其曲目被静默删除 + 写墓碑**，A1 那边也会消失 | **高（数据丢失）** |
| B2 | A2 首装/重装后 PUT 空视图或部分视图 | `:49-53` 判定大范围删除；大范围时被 `:56` 或 `:59` 拦下 | 拦下则 A2 的删除**永久卡在 `suspect_removals`**（A2）；更糟：被拦下后 `base_served` 被推进为**缩减后的视图**（`:73`），A1 的本地内容被渲染覆盖 ⇒ 可能反向丢 A1 的本地新增 | **高（数据丢失，且经 I6 间接删本地文件）** |
| B3 | A1 与 A2 交替 PUT（都带着对方的增量） | 每轮 `C_new` 与 `bsrv` 的差集都在变；`drop_tombstones`/`revision` 处理见 E3 | **`revision` 单调增长（E3）**、每轮都触发一次墓碑压制/安全阀检查、渲染缓存全程失效 | 中（写放大 + 无法收敛判定） |
| B4 | A1 删掉一首歌（已写墓碑），A2 之后 PUT 带这首歌 | I7 压制 | A2 的歌被压回状态页"待确认恢复"卡 | 中（多一轮 + 用户困惑；`docs/08-风险与开放问题.md:22` 只把这一条记为"中/低"） |
| B5 | A1 离线 6 个月，其间该 client_key 被 A2 与重装复用多次 | 基线被反复改写 | A1 回来时既可能大范围误删、也可能被误判为新客户端走 adopt_initial | 中 |
| B6 | 两台设备只是轮流只读 | `base_served` 被互相推进 | 无副作用 | 无害 |

### 最便宜的修复（保持"一个 URL + 账号密码"）

1. **把设备身份放进路径、并让它成为默认推荐配置**：文档与状态页统一规定 `https://hub/sync/d-<6位>/`（`d-` 段只做身份，不参与资源定位；服务端在 `clientIdentity()` 里取出后剥离）。`docs/04-数据规范与适配器.md:50` 的 `device_part` 已经预留了这个字段——只要把"缺失时由枢纽签发"改成"缺失时**降级为不信任模式**"即可。
2. **`Client-Id` 优先、UA 次之、路径兜底**：`User-Agent` 只能做家族级粗分（`:138` 已承认分不开），因此**当请求不带 `Client-Id` 且路径不含 `d-*` 段时，该 `client_key` 标记 `unverified=true`**。
3. **不信任模式的语义**（这是真正的最小修复）：`unverified` 客户端**不允许自动删除**——所有 `delta.removed` 一律进确认队列（A2 的队列），同时在状态页强制出"检测到无法区分的设备/可能重装"卡，提供两个按钮：**"这是一台新设备"**（新建 client_key，旧基线保留 30 天——`:116` 已有此设计，只是没接到这条路径上）与**"这是同一台设备恢复"**（沿用旧基线）。用户点完一次，该 client_key 变 `verified`，此后恢复正常删除行为。
> **实现裁决（2026-10-06，多设备同步改造方案 §3.1）**：上面前两条建议的"缺失设备段 ⇒ `unverified`/不信任模式"**未采用**——`identity_verified` 参与了"显式恢复 vs 墓碑压制"的判定（engine.py `_crossed_deletion_point`），一改会让默认单设备用户"删了又想加回来"从直接生效变成弹恢复卡（行为变更）。维持 `identity_verified=True`（密码认证过的空间成员即受信）。设备身份按 `X-Hub-Device` 头 ＞ `/d/{device}/` 路径段 ＞ `default` 实现；同 `default` 身份的多设备误删由 **R1 删除判据**（base_served ∩ base_submitted）封死。

4. **Set-Cookie 不可行**（栖弦无 cookie jar，实际不会回送）；**不要用 IP**（移动网络/家里 NAT 均不稳定）；cookie/服务端签发 id 都需要客户端配合回显，本阶段不可用。
5. 顺手补一条：`docs/03-总体架构.md:116` 的"单次提交替换全部客户端身份"阈值（"全部 `client_key` 变化"）在只有 1–2 个客户端时**永远不触发**（1/1 变化不算"全部变化"还是算——文档没定义），且它检测的是"换了 key"而不是"同一 key 换设备"。

## C. 墓碑策略：I7 的方向对、参数错

### 结论（先给判定，理由在下面）

**保留 I7 的"压制复活"语义，删掉"2 年"这个时间参数，改成"确认水位 + 无时间 TTL"。** 即组合 **(d) 的 GC 条件 × (a) 的窄化**，但 (a) 要窄化成"仅对无法归因的提交者压制"而不是"仅对无基线者压制"。`spec/canonical-v1.md:231` 的 60 天最低保证同样应从"时间保证"改成"确认保证"（否则 60 天与 2 年、与 T3 三者互相打架）。

### 为什么"2 年对所有客户端"是过度扩张

1. **它拦的是同一个人、同一台设备的合法重加**。依据：`:64-65`（`revivable = {k for k in delta.added if not live_tombstone(k, TTL=2年)}`——**没有区分客户端身份**），`spec:281` 的 D20 修订也只说"新身份设备"。后果：用户在栖弦删了《X》→ 三天后想加回来 → 加回被压制、渲染里《X》不存在、状态页出卡。栖弦的本地重建是"缺席即删除"（`:34`、`spec:221`），所以**用户看到的是"我加的歌被删了"**，而不是"有张卡等我点"——这违反 `spec:230` 的 T2 精神（删除必须显式）与 V8。真正需要压制的只有"提交者无法被证明曾看到过那次删除"的情形。
2. **2 年不是上限、而是新的复活窗口**。`:68`（`drop_tombstones_older_than(TTL)`）与 `spec:231`（T3"只有在所有已知客户端都确认过之后才可以 GC"）**互相矛盾**：伪代码只看时间，没看确认。一旦 TTL 到期（或用户按 `docs/08:22` 的缓解措施"必要时手动缩短 TTL"），墓碑消失，一台离线超过 TTL 的设备回来即可合法复活——那正是 D20 要消灭的故障，只是换了触发者（旧设备代替新设备）。
3. **墓碑的代价被高估了**。D20 说每条约 50 B（`docs/09:125`）。三年删 1000 条 = 50 KB，占 `docs/03:140`/`docs/01:80` 的 32 MiB 空间配额不到 0.2%。**没有理由为了省 50 KB 引入一个数据正确性窗口。**

### 与四个候选的对比

| 方案 | 换机/重装（1 周内回来） | 离线 6 个月回来（持有已删歌） | 同设备合法重加 | 存储 | 结论 |
|---|---|---|---|---|---|
| 现状 I7：2 年内对**所有**客户端压制 | 不复活 | 不复活（若墓碑未 GC） | **被拦一次**（`:64` 无身份区分） | 有界（TTL） | 方向对，误伤合法重加 |
| (a) 仅当提交者**无基线**时压制 | 不复活（新身份=无基线） | **复活**（老身份有基线，`live_tombstone` 不再参与？取决于实现） | 自由 | 有界 | 覆盖了 D20 的原始场景，但把"老设备的合法重加"和"老设备的陈旧复活"混在一起 |
| (b) 30 天压制 | 不复活 | **复活**（6 个月 > 30 天） | 30 天后自由 | 有界 | 换机场景够用，长期离线场景失守——而 `docs/05:161` 用例 23 明确要覆盖"离线 90 天" |
| (c) 不压制，只靠安全阀 | **复活** | 复活 | 自由 | 无 | 安全阀只拦"批量"（`:114-115`）：一台设备慢慢把 20 首已删歌加回来，每次 1 首，**永不触发** |

### 我会上线的组合

1. **压制条件（窄化）**：仅当出现下列任一情形时压制复活，否则允许重加并清墓碑（同设备重加走这条）：
   - 提交者 `client_key` 无 `base_served`（新身份，D20 原始场景）；或
   - 该 key 的 `client_key` 是 `unverified`（B 节）；或
   - 该 key 不在"墓碑创建时已注册的客户端集合"内（设备身份被怀疑换过）。
   注意：**栖弦每次 PUT 都会带上整个视图**，所以"同设备重加"与"新设备复活"在 payload 层面确实同形——这是硬约束，无法在协议层区分；因此"窄化"只能靠身份可信度，不能靠内容。
2. **GC 条件（替代 TTL）**：`tombstone.deleted_at_revision ≤ min(served_revision of every client registered at deletion time)`，即**删除发生时已注册的所有客户端都已在成功交付中看到过该墓碑**才 GC。墓碑表加两列：`created_at_revision`、`ack_mask`（或直接对每个 client 比较其 `base_served.served_revision`）。`docs/03:153` 的 `tombstones` 表需要加这两列。
3. **退休客户端的处理**（否则 (d) 永不 GC）：超过 180 天未出现的客户端标记为 `retired`，从 GC 条件中排除，并在状态页显式列出（用户可"恢复"该设备）。这是唯一一处用时间的地方——**时间用于判定"身份是否还活着"，而不是用于判定"删除是否还算数"**。这个区别很关键：前者错判的代价是一张卡，后者错判的代价是数据复活。
4. **恢复通道必须闭环**：`restore_candidates`（`:65`）进状态页后，用户点"恢复"必须 (i) 清除该墓碑、(ii) 重放被压制的 `added`、(iii) `revision+1`、(iv) 在 journal 记 `origin=user`。`spec:160-162` 的 `Tombstone` 结构里没有"被压制次数/待确认"字段，渲染层也无法向栖弦表达"这张卡"（`:119` 明确差异摘要**不进响应体**）——所以**唯一的信息出口是状态页**，必须保证用户不打开状态页时至少不被误导（建议：状态页横幅 + 同步日志里明确写"X 被墓碑压制，等待确认"）。
5. **TTL 参数**：如果一定要留一个时间参数，它的语义应该是"墓碑在**没有**任何确认的情况下最长保留"= 无限（`0 = 永不按时间 GC`）或至少 10 年，并且**绝不允许**通过配置缩短到低于"最久未同步的活跃客户端的离线时长"（否则就是把 A2 的洞重新引进来）。`docs/01:49` 的 V7 措辞"墓碑默认保留 2 年（`spec` T3 的最低保证 60 天，D20）"需要改成单一权威值。

### 离线 6 个月回来、手里有已删歌的具体走向（按推荐方案）

设备 D 离线 6 个月（< 180 天，未退休）→ 墓碑仍在（无时间 GC）→ D 的 PUT 里那首歌命中 `live_tombstone` → 被压制 → `restore_candidates` 出卡 → D 的渲染里那首歌不存在 → D 本地重建后不再持有它 → 状态页显示"你于 2026-04-01 删过《X》，此设备带来了一份旧副本，是否恢复？"。D 的用户看到的是"这首歌没回来"（符合 D20），而不是"这首歌自己回来了"（符合 V10）。若 D 离线 **> 180 天且被退休**，它仍会带着旧副本回来；此时它命中 `unverified`（B3）或"不在删除时已注册集合"（若退休后被重新注册）⇒ 走确认卡，**不会自动复活**。

## D. 安全阀

### D1 · "已安全降级"的错觉：安全阀只挂在一条路径上 ｜ 严重度 **高**

- 依据：`docs/05-合并引擎.md:59-61`（阈值检查）、`:114-115`（两个阈值）、`:173`。
- 事实：安全阀的输入是 `delta.removed`，而 `:58` 已经把 `suspect_removals` 置空。**但真正危险的删除路径（A1：同 key 换设备/重装/清数据的子集丢失）恰恰不经过 `suspect`**，比例又常在 30–45% 之间（低于 50%），于是"看起来有安全阀"的操作区间是**未被覆盖的**。安全阀的 50% 阈值与"栖弦一次重装丢一半歌单"是同一个量级，属于参数选歪。
- 最小修复：把安全阀的输入从"本次 `delta.removed` 比例"改为**双因子**：`(本次删除比例, 该 client_key 的身份可信度)`。`unverified` 客户端一律挂起（见 B3），`verified` 客户端才用 50%/≥3 的阈值；同时把 A1 的"子集但非小比例"单独列为一个告警级（10%–50% 且 ≥2 个歌单）。

### D2 · 可以被拆批绕过 ｜ 严重度 **中**

- 依据：`:59`（阈值按**单次请求**的 `delta.removed` 计），没有任何窗口/累积量。
- 场景 1：栖弦逐轮删除？——栖弦每轮提交的是**全量视图**，且 `_sameSnapshotData` 相等时不写（`:128`），所以它通常不会主动拆批。**但服务端不能把这个假设写进安全模型**：错误/恶意客户端（或未来 LX 之类）可以每次只删 2 个歌单，`2 < 3` 且 `2/20 = 10% < 50%`，连发 10 次 ⇒ 20 个歌单全灭，**安全阀一次都不触发**。
- 场景 2：清空单个歌单。`:115`"单次删除曲目比例（单歌单）≥ 50% 且 ≥ 10 首"——对 20 首的歌单删 9 首不触发（`9 < 10`），删 10 首才触发；而 9 首已经丢了 45%。更细的绕过：分两次各删 9 首，第一次 9/20，第二次在第一次的基础上 `base_served` 只剩 11 首，再删 6 首即 55% 但 < 10 首 ⇒ 又不触发。**同一歌单可以被"每轮删除量刚好低于两条阈值"地逐步清空。**
- 最小修复：阈值判定改为**窗口累积**：`sum(本空间最近 T 分钟/最近 K 轮内所有客户端的删除量) / 窗口开始时的空间规模`，并对同一 `(playlist, 短时间窗)` 的连续删除做累积计数。实现成本很低（`journal` 已在 `:154` 记录每次 delta）。

### D3 · 阈值定义与伪代码不一致 ｜ 严重度 **中**

- 依据：`:59` 只出现一个 `SAFETY_LIMIT`（"默认 50%"），而 `:114-115` 定义了两个**布尔组合**阈值（歌单：`≥3 或 ≥50%`；曲目：`≥50% 且 ≥10`）。伪代码无法表达"或/且"以及"≥3 这个绝对值"。
- 具体后果（值得单独指出）：`:114` 的 `≥3 或 ≥ 50%` 意味着**在 143 个歌单的空间里删 3 个（2.1%）也会挂起**。这不是安全阀，是阻碍（`spec:315` 的量级假设是"歌单 3–20 个"，那么在 3 个歌单的空间里"删 1 个"就 ≥50%⇒ 挂起，"删 2 个"也挂起——**小空间里的正常删除 100% 被拦**）。
- 最小修复：阈值改为**百分比主导、绝对数只做下限**：歌单 `ratio ≥ 50% 且 count ≥ 2`；曲目 `ratio ≥ 50% 且 count ≥ 10`。并把"挂起"与"确认卡"的 `pending_id` 写进伪代码的返回结构（目前 `:71` 只写 journal，`:74` 的 `return 200 rendered` 没有携带待确认项，状态页无从知道该给用户看什么）。
- **修复状态**：已修复——`src/engine/engine.py:_safety_trigger` 按 D3 语义实现（歌单 `count ≥ SAFE_PL_DELETE_COUNT(2) 且 ratio ≥ 50%`；曲目 `ratio ≥ 50% 且 count ≥ SAFE_TR_DELETE_MIN(10)`；`n_live==0` 时按绝对数判定，删到 0 张不绕过）；第四轮 D25 起安全阀仅对**不可信端**挂起，可信端直删生效。

### D4 · 挂起的删除在客户端侧等于"复活"，且会永久丢失 ｜ 严重度 **高**（与 A2 同源）

- 依据：`:60-61`（`deferred = delta.removed; delta.removed = {}`）、`:74`（返回 `200` + 正常交付合并结果）、`:119`。
- 场景：用户在栖弦删了 4 个歌单（4 ≥ 3）⇒ 挂起 ⇒ 渲染里 4 个歌单**都还在** ⇒ 栖弦"缺席即删除"的反向操作——它以远端为准重建本地（`:128` 的 `_sameSnapshotData` 不适用，因为远端内容确实变了）⇒ **4 个歌单在用户手机上全回来了**。下一轮 `base_served` 已包含这 4 个歌单，用户的删除操作**在客户端不再产生任何差异**，于是 `pending_removals` 里的 4 条成为**只有状态页能撤销的孤儿**。用户不去状态页 ⇒ 删除意图永久丢失（违反 `docs/01:49` V7 的"用户可见删除的可恢复窗口"——这里是"用户可见删除被静默撤销"）。
- 最小修复：挂起时必须让客户端**仍能感知删除被暂缓**，可行手段只有两个（栖弦不能用响应体扩展，`:119`）：
  - 渲染时把被暂起的元素**从渲染结果里去掉**（即对客户端表现为删除已生效），而 canonical 保留 ⇒ 但这样客户端本地就真的删了，用户的删除意图已经实现，安全性靠服务端 canonical + 墓碑保证（**这实际上更符合"宁可少同步，不可错删除"**：canonical 不删，客户端删了也不丢，因为服务端还留着，用户还可以在状态页看到"这 4 个歌单的删除待你确认"）；
  - 或者渲染时**保留元素但把歌单元数据标记**……栖弦会报错，不可行。
  推荐第一种，但它改变了"挂起"的对外语义（对客户端而言删除已生效），`docs/05:152` 用例 14 的期望需要重写为"canonical 无损 + 客户端侧删除已生效 + 状态页出确认卡（确认后写墓碑，放弃则下一轮渲染把元素加回客户端）"。

### D5 · 确认动作本身未定义 ｜ 严重度 **中**

- `:119` 说 `hub confirm-delete --space X --pending <id>`，但 CLI/状态页确认时要做什么没有定义：写墓碑需要 `origin`（`spec:161` 有 `device` 字段），而 `pending_id` 背后的"删除者"可能是一个已经不可信的 client_key（A1）。建议：确认动作必须记录 `origin=user:<account>` 与 `pending_id`，并在 journal 里保留触发它的原始 `delta`，以便回滚（`:154`/`:174` 的回放能力依赖这个）。

## E. 合并规则与收敛

### E1 · `revision` 无条件自增 ⇒ 永久破坏 I2′ 版本闸门 ｜ 严重度 **高**

- 依据：`docs/05-合并引擎.md:69`（`space.revision += 1`）、`:56`（I2′ 的闸门 `space.revision != bsrv.served_revision`）、`:94`（`modifiedAt = f(served_revision)`）、`:183`（渲染缓存键含 `canonical_revision`）。
- 场景：某次请求 `delta` 为空（客户端只是回写了完全相同的视图，或只做了字段级变更、或所有变更都被安全阀挂起）⇒ `canonical` **一点没变**，但 `revision += 1`。后果三连：① `docs/05:158` 用例 20 要求的"`revision` 不无限增长"**失败**；② 之后每一个客户端的 `space.revision != bsrv.served_revision` 条件在被交付前都为真 ⇒ **所有客户端的自动删除都被永久转入 `suspect_removals`**（A2 的死路），删除功能整体瘫痪，只能靠状态页；③ `modifiedAt` 随 `served_revision` 推进（`:94` 声称"仅当确有变化才推进"——但如果 `f` 输入是 `served_revision` 而 `served_revision` 每轮都变，这条修正就自相矛盾），缓存键含 `canonical_revision` 也随之每轮失效。
- 另有一个更隐蔽的版本：`:22` 描述反例时说的是"若用 `base_submitted` 求差集……反复并入、`revision` 无限增长"——这条修正本身是对的，但 `:69` 的无条件自增让**同一个 bug 以另一种形式复活**。
- 最小修复：`if canonical_mutated: space.revision += 1`（并在无变化时连同 `base_served.served_revision` 一起保持），`modifiedAt` 由 `f(canonical_epoch)` 生成，其中 `canonical_epoch` 只在 canonical 真正变化时自增；渲染缓存键用 `canonical_epoch` 而非 `revision`。

### E2 · 删除优先与"只并集"分支的相互作用未定义 ｜ 严重度 **中**

- 依据：`:56-58`（禁止删除、只并集）、`:67`（`apply_removals`，I3 删除优先）、`:84-89`（I3 的定义）、`:30`（I2′）。
- 场景：A 端与 B 端同时操作同一首歌，A 删、B 加。A 的 PUT 先到（`space.revision == served_revision`）⇒ 删生效 + 写墓碑。B 的 PUT 后到（`space.revision != served_revision`）⇒ **禁止删除只并集** ⇒ B 的加要不要再加回？`delta.added` 里包含它，`:64` 的 `live_tombstone` 会拦住（I7）——**这是 I7 唯一真正必要的应用场景，设计里没写出来**（`:35` 只说"任何客户端提交时都不得复活"，`:64` 的实现里 `revivable` 的判断确实覆盖了它，但 §5.2/§5.3.2 的散文里没有把"删除优先"与"墓碑压制"的关系讲清）。留在这里的风险是：实现者若照 `:87-89` 的 `keep(key)` 公式做（该公式里没有墓碑项），会把 B 的加写回去。
- 最小修复：把 `keep(key)` 改成显式引用墓碑：`keep(key) = ((本地有 && 远端有) || (!base 有 && (本地有 || 远端有))) && !live_tombstone(key)`，并在 §5.3.2 点名"删除优先的最终裁决者是墓碑，不是集合差分"。

### E3 · 无界增长/乒乓的具体来源清单 ｜ 严重度 **中**

- `revision` 无界：E1。
- 墓碑无界：`:68` 的时间 GC 与 T3 冲突（C 节）；若无时间 GC 又不做退休客户端（C 节第 3 点），墓碑只增不减——但 50 B/条，可接受，应在文档里承认这是**有意的权衡**，而不是留一个"TTL"字样让人以为有界。
- 渲染字节抖动：`trackIds` 顺序（`spec:95` 必须有序、`T5` `spec:233` 说不参与合并）。若 `PF5`（`spec:327`）的规范化哈希覆盖数组顺序，而某客户端每次 GET→PUT 会重排（客户端自身的排序），则 `content_hash` 每轮变化 ⇒ `modifiedAt` 每轮推进（`:94` 的"确有变化"被触发）⇒ **永久乒乓 + ETag 永不相等 + `docs/05:128` 的"相等则不写"优化失效**。修复：`ordered-lists-in-hash` 必须排除，或规定 `trackIds` 的渲染顺序权威=枢纽（按 `addedAt` 稳定排序）且**顺序差异不得导致 `modifiedAt` 推进**（与 T5 一致）。

### E4 · `(source,songId)` 去重与 `tr_<ULID>` 记录键冲突 ｜ 严重度 **中**

- 依据：`spec:104-105`（`id` 是记录键、`identity` 才是身份）、`spec:218`（I3：`tracks[]` 内身份键必须唯一）、`docs/05:66`（`apply_additions` 用 `(source,songId)` 去重）、`docs/04:62`（歌单 id"枢纽分配后回填"）。
- 场景：栖弦客户端 A 渲染后本地保留 `tr_AAA`，新增了同一首歌（来自不同入口，或者用户从"最近播放"又加了一次）标记 `tr_BBB`，而两者 `identity` 相同 ⇒ 客户端 PUT 的文档里同一 `(source,songId)` 出现两条不同 `tr_*`。此时是**客户端文档非法**（`spec:218`：`tracks[]` 内身份键必须唯一）⇒ 按 `:41`（"结构坏 → 抛错，不猜"）应当 `400`。但栖弦是自有格式（不是 canonical），适配器要做一次"身份键去重 + trackIds 重写"的归一化，这一步在 `docs/04` 的适配器契约里**没有规定**（`:48` 只说 `parse` → `CanonicalView` + 警告列表）。
- 最小修复：在适配器契约里明确"`parse` 必须对同 `(source,songId)` 的多条记录做**记录键合并**（保留最早 `addedAt` 的 `tr_` id，把所有 `trackIds` 引用重写为它，并记警告）"；否则要么 `400` 让同步死，要么产生重复曲目。
- 另外，歌单身份（`docs/04:36`：别名匹配"只在新建时使用一次"）与墓碑键（`docs/04:30`：`element=playlist` 的墓碑按什么键？canonical `pl_<ULID>` 还是别名？）需要写死：**歌单墓碑必须同时按 canonical id 与所有别名建立抑制索引**，否则重装设备把"我的喜欢"匹配成一个新 `pl_<ULID>` 后，`live_tombstone(新id)` 为假 ⇒ I7 失效、歌单复活。

### E5 · I6 不透明透传：跨设备污染与哈希归属矛盾 ｜ 严重度 **中**

- 依据：`:34`（I6）、`spec:221`（I6）、`spec:255`（放进 `ext.<client>.opaque.*`）、`docs/04:39`、`:185`（基线存内容哈希）、`:94`（"确有变化才推进 modifiedAt"）。
- 场景：手机 A 有 3 个本地文件曲目（进 `ext.cyshine.opaque.tracks`），桌面 B 有 5 个（进 `ext.ceru.opaque...`，但 A 与 B 是**同一个客户端家族**时命名空间相同）。由于不透明块不参与合并，**枢纽拿哪一份渲染给谁**没有定义：若都渲染，A 会看到 B 的本地文件条目——而 B 的 `file://` 路径在 A 上不存在，栖弦 `applyFromSync` 会把它们当成"远端有的歌"写进本地库 ⇒ 用户在手机上看到一堆打不开的幽灵曲目；若只渲染该客户端自己的，则**枢纽必须按 client_key 分别存储多份不透明块**，这与 `docs/03:150`（基线只存键清单与哈希、视图共享物化）不兼容。
- 更糟的是缓存/时间戳：`ext.opaque` 每次变化都会改内容哈希（`:185`），从而推进 `modifiedAt`，触发别的设备整表替换（`docs/04:65` 描述的正是这个失败模式），**间接删除**正是 I6 想避免的（`:34`）。
- 最小修复：① 不透明块按 **client_key** 分桶存储与渲染（`ext.<client>.<device_part>.opaque`），绝不相邻设备共享；② 内容哈希与"是否推进 `modifiedAt`"的判定**必须排除 `ext.*.opaque.*`**；③ 把 `spec:221` 的 "不参与合并判定、不参与去重" 补成"不参与合并判定、不参与去重、**不参与跨设备交付**"。
- **已实施（2026-10-06，多账户共用歌单 D23）**：`rt.opaque_by_client[cid]`（`src/hub/store.py:97`）+ 渲染只取本客户端那份（`src/hub/api.py:897`）——①③ 落地。
- **文档冲突必须写清（防止下一个 AI 按 ② 改错代码）**：本条 ② 要求"内容哈希必须排除 `ext.*.opaque.*`"，而 `docs/10:159`（E5 被采纳时的处置）决定"opaque **进** `view_hash`"；**当前实现 = 每客户端一份 opaque 并计入其自身 `view_hash`**（`src/engine/engine.py:245-246`）——分桶后各客户端的哈希互不影响，语义上**不必再排除**。最终口径见 D23（`docs/09`）：opaque 按 `client_key` 分桶存储与渲染、不跨设备交付，且计入**本客户端自身**的 `view_hash`。

## G. Top 5（按"修它的收益 / 不修的代价"排序）

1. **给删除加正向归因闸门，并把所有被压制的删除变成有出口的持久队列。**
   合并 A1/A2/D4/F11。规则：只有当"`bsrv` 是本次 `C_new` 的严格超集且 `space.revision == bsrv.served_revision` 且适配器往返无损 且 该 `client_key` 身份可信"时，`delta.removed` 才允许直接生效；否则进 `pending_removals`（**不是** journal），并保证下一轮该客户端提交仍缺席时可自动生效一次。**不修**：两台手机/一次重装（丢 33% 歌单）就能静默删数据；且一旦进入 `suspect` 分支，用户在某处删的歌永远回不来。
2. **`client_key` 必须能区分设备，否则拒绝自动删除。**
   合并 B 节 + F5 + F10。把 `docs/03:138` 的"缺失时由枢纽首次签发并在路径中固定"改成"缺失时该身份标记 `unverified`，`unverified` 一律不许自动删除，状态页强制出'这是一台新设备 / 同一台设备恢复'卡"，并把 `docs/05:157` 用例 19 拆成"带 `d-*` 路径段（必须通过）"与"不带（必须走确认卡，不得自动删）"两个用例。**不修**：用例 19 声称覆盖的故障仍然存在，而评审会以为已经修好了。
3. **`revision` 只在 canonical 真正变化时自增。**
   E1。否则第一步修好的 I2′ 闸门会被一次空提交永久打开，全空间删除功能退化为"必须去状态页点确认"。**不修**：`docs/05:158` 用例 20 直接失败，且失败方式极隐蔽（只在"有人做了空回写"之后才出现）。
4. **墓碑 GC 改为"确认水位 + 客户端退休"，删除时间 TTL。**
   C 节 + F1 + F8。墓碑加 `created_at_revision` 与 `ack_mask`；`retired` 只用于"身份是否还活着"（180 天），不用于"删除是否还算数"。**不修**：`docs/08:22` 的缓解措施"必要时手动缩短 TTL"会在某天被触发，而那一刻 D20 承诺的"不要自己回来"就失效了，且失效路径比原来更难诊断（是旧设备而不是新设备）。
5. **超限/渲染失败的路径必须是"无副作用"的，并且单一权威表述。**
   合并 A3/A5/F3/F12 + E5 的哈希归属。渲染失败 ⇒ 整个请求回滚 ⇒ 返回 `500` 且基线不动（把 `render` 移进事务或把 `base_submitted` 的推进移到渲染之后）；GET 超限时的行为写死（推荐：返回 `200` + 该客户端上一次成功交付的视图 + 状态页横幅"数据量超过该客户端上限，请导出或启用分片"，绝不返回裁剪过的新视图）。**不修**：一次渲染失败就让某客户端永久卡在"基线已推进但视图未交付"，且 GET 超限会在客户端侧静默删除。

## H. I7 / TTL 的明确判定

- **保留"墓碑压制复活"这个机制**（D20 的用户意图明确，且它解决的是一个真实故障）。
- **删掉"2 年"作为压制窗口**：压制应当由"提交者的身份是否可信"决定，而不是由时间决定。
- **删掉"2 年"作为 GC 唯一条件**：GC 必须由"删除发生时已注册的所有客户端都已在成功交付中看到该墓碑"决定（T3 原义），并对 >180 天未出现的客户端走"退休"（时间只用于判断身份存活，不用于判断删除是否还算数）。
- **兜底 TTL 语义**：如果一定要留一个数字，它应当是"墓碑在**完全没有确认**时的最长保留期"，建议值 = 无限（永不按时间 GC）；若运营上需要上界，取 **10 年**并写入 `spec:231` 作为唯一权威值，替换现在的"60 天/2 年"两套数字。绝不推荐 30 天或更短：它与 `docs/05:161` 用例 23（离线 90 天）和 B5（离线 6 个月）直接冲突。
- **对"离线 6 个月回来、拿着已删歌副本"的最终行为**：不复活；出确认卡；用户点恢复才加回；若该设备已被退休或身份不可信，仍然走确认卡而不走自动删除。
